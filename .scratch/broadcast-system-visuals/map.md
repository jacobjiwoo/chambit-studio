# 방송 시스템 시각화

Label: `wayfinder:map`

> 이 문서를 다루는 에이전트는 먼저 [`app/docs/broadcast-system/CLAUDE.md`](../../app/docs/broadcast-system/CLAUDE.md)와 [ADR 0001](../../docs/adr/0001-signal-flow-from-data.md)을 읽는다. 문서 자체의 결정은 [broadcast-system map](../broadcast-system/map.md)에 있다.

## Destination

`/docs/broadcast-system`에 방송실 구조를 그림으로 보이고 만질 수 있게 한다. 장비·연결은 데이터 모듈 하나가 원천이고, 장비 목록표·신호 흐름도·확인 필요 목록이 모두 거기서 나온다. 장비가 늘거나 미확인이 풀리면 데이터 한 곳만 고친다. 바뀌지 않는 원리와 안정된 공간은 anatomy skill로 공들여 그린다.

## Notes

**그림이 답할 질문은 셋이다.**

1. 큰 그림 익히기 — 입력 → 처리 → 출력이 어떻게 이어지나
2. 트러블슈팅 — 이 장비가 꺼지면 무엇이 끊기나, 증상이 나면 어디부터 보나
3. 원리 이해 — Fill/Key로 CG가 얹히는 방식 등

**그림은 두 종류다.** 둘은 다른 문서다.

- **신호 흐름도**: 장비와 장비 사이의 논리적 연결(SDI, XLR, HDMI…). 실제 자리와는 상관없다. 1·2를 맡는다.
- **배치도**: 영상 데스크·음향 데스크·랙 위에 장비가 실제로 어디 놓였나. 1을 맡고, 방송실에서 장비를 찾게 한다.

**anatomy skill** — `~/.claude/skills/anatomy` (https://github.com/wheresryan22/anatomy). 실물 하나를 부품 40–150개로 손수 짜는 isometric SVG다. MIT 라이선스라 `kit/`을 복사해 쓸 수 있고 라이선스 고지를 함께 둔다. React/Next.js에서는 정적 그림을 서버 컴포넌트로, 움직임을 `"use client"` 컴포넌트 하나로 나눈다(`references/react.md`).

## Decisions so far

- **모두 확정될 때까지 기다리지 않는다.** 바뀌는 것(장비, 연결)은 데이터에서 그리고, 굳은 것만 anatomy로 그린다. 확정되는 순서대로 anatomy 그림을 하나씩 더한다.
- **신호 흐름도는 데이터에서 React Flow로 그리고 생김새만 anatomy를 따른다.** [ADR 0001](../../docs/adr/0001-signal-flow-from-data.md). 모두 확정된 뒤 전체를 anatomy로 손수 그리는 개요 그림은 버리지 않고 Fog에 둔다.
- **데이터는 장비와 연결이다.**
  - 장비: `id`(용어집 이름), 파트(전원, 영상·온라인 송출…), 제조사·모델, 위치, 용도, 비고, `toConfirm: string[]`(확인할 거리)
  - 연결: 출발, 도착, 포트(선택), 신호 종류, 근거(사용자 확인·선임 설명·추정… 글자 그대로), 미확인 여부, `toConfirm`
  - 문장 중간의 `<Unconfirmed>`는 `toConfirm`으로 옮긴다. 그래야 확인 필요 목록을 데이터에서 모은다.
  - 포트는 선택이다. 뒷면 확인이 보류라 대부분 비어 있다.
- **데이터는 TypeScript 모듈이고 옆에 테스트를 둔다.** 연결의 양 끝이 실제 장비인지, 장비 `id`가 용어집 이름과 맞는지, 아무 연결에도 없는 장비가 있는지를 `pnpm test`가 잡는다. 봉사자가 직접 고치지 않고 에이전트와 함께 고치는 파일이라 타입의 이득이 크다.
- **배치는 빌드 시점에 서버 컴포넌트에서 elkjs로 계산한다.** 브라우저는 좌표를 받아 상호작용만 한다. `output: "export"`와 맞는다.
- **트러블슈팅 인터랙션은 단순하게 시작한다.** 장비를 누르면 하류 전체를 "영향 받을 수 있음"으로, 상류를 "여기부터 확인"으로 칠한다. 장비마다 필수 입력을 정하는 정밀 모델은 직렬 구조부터 미확인이라 미룬다. 데이터에 `required` 같은 필드를 나중에 더할 여지를 둔다.
- **미확인은 그림에서도 보인다.** anatomy 규칙상 점선은 쓰지 않으니 흐린 톤과 배지 아이콘으로 구분한다. 누르면 확인할 거리가 보인다.
- **anatomy 첫 그림은 CG 출력 원리다.** 문자발생기 보드 설정까지 확인됐고, 방송실 구성이 바뀌어도 원리는 같다. 온라인 송출 직렬 구조는 실물 확인(장비 목록표 확인 필요 3번) 뒤로 미룬다.
- **배치도는 공간마다 anatomy 그림 하나다.** 그림 속 장비에 데이터 `id`를 달아 누르면 장비 정보가 열린다. 모양은 손으로 그린다. 그 공간의 장비 구성이 안정된 뒤 그린다. 영상 데스크는 확인 필요 2번(영상 hub)과 3번(직렬 구조)이 풀린 뒤다.
- **페이지 배치.** 신호 흐름도는 새 페이지이고, 장비 목록표의 "온라인 송출 신호 흐름" 절이 그리로 옮겨 간다. CG 출력 원리 그림은 장비 목록표의 해당 절 안에 넣는다. 배치도는 나중에 새 페이지다.
- **데이터 모듈은 `app/docs/broadcast-system/_lib/system.ts`다.** 장비 `toConfirm`은 배지 자리를 정하려고 `{ cell, what }[]`로 넓혔고, 끝점은 `{ id, unit?, port? }` 또는 `{ unknown, candidates? }`다. 확인 필요 목록 대응표와 옮기며 찾은 어긋남 8건은 [01](issues/01-system-data.md) Answer·Comments에 있다.
- **anatomy kit 복사본은 `_lib/anatomy/`와 `_components/anatomy/`에 있다.** CG 출력 원리 그림이 이것으로 그려진다. lint 규칙 셋을 이 두 폴더에서만 껐고, 그림은 실제와 다른 점 셋을 캡션에 밝힌다. [04](issues/04-cg-output-figure.md) Answer.

## Fog

- **전체 개요 anatomy 그림** — 방송실 구성이 안정되면 방송실 전체를 손수 그린 개요 그림을 더할지. ADR 0001의 버리지 않은 대안이다.
- **온라인 송출 직렬 구조 anatomy 그림** — 확인 필요 3번이 풀린 뒤. "백업 장비가 꺼지면 주 송출도 끊긴다"를 움직임으로 보일 수 있다.
- **정밀 영향 모델** — 장비별 필수 입력. 직렬 구조가 확인된 뒤 다시 본다.
- **운영 체크리스트·문제 해결 FAQ와 그림의 연결** — FAQ의 "확인할 곳"을 신호 흐름도 경로 강조로 열지.
