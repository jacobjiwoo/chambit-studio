# 정적 사이트에서 한글 전문 검색

Type: research
Status: resolved

## Question

**서버 없이(정적 배포) 한글 문서를 제대로 검색하게 만들 수 있는가 — 어떤 방법이 있고 무엇을 포기해야 하는가.**

"모르는 게 있을 때 **찾아본다**"가 목적지의 동사다. 검색이 부실하면 이 사이트는 존재 이유가 절반 사라진다. 그런데 물려받은 제약이 **Cloudflare Pages + `output: 'export'`, 서버 없음**이라, 검색은 브라우저 안에서 끝나거나 인덱스를 미리 구워야 한다.

**조사할 것**

1. **한글이 왜 어려운가** — 영어와 달리 공백으로 단어가 안 갈리고, 조사가 붙고("자막을", "자막이"), 초성 검색 관습이 있다. 정적 검색 도구들이 이걸 어떻게 다루는가(형태소 분석 / n-gram / 자모 분해). 각 접근이 무엇을 잘하고 무엇을 놓치는지.
2. **후보 도구 실사** — Pagefind, Orama, FlexSearch, Lunr, MiniSearch, Fuse.js, 그리고 문서 프레임워크가 기본 제공하는 검색(Nextra/Fumadocs 등). 각각에 대해:
   - **한국어를 공식 지원하는가**, 아니면 설정으로 되게 만드는가, 아니면 안 되는가
   - **인덱스 크기** — 정적 배포라 인덱스가 클라이언트로 내려온다. 한글 n-gram은 인덱스를 부풀리는 것으로 알려져 있다. 이 사이트 규모(수십~백 페이지 남짓)에서 실제로 몇 MB인가, 청크 단위로 나눠 받는가
   - 유지보수 상태(최근 커밋, 이슈)
3. **호스팅 제약과의 궁합** — Cloudflare Pages 정적 배포에서 빌드 타임 인덱싱이 성립하는가. Cloudflare Workers/Pages Functions를 쓰면 열리는 길이 있는가, 그리고 그건 "서버 없음"을 깨는가.
4. **검색 대상의 범위** — 스크린샷이 답인 매뉴얼이라, 이미지 캡션·alt 텍스트가 검색에 걸려야 할 수 있다. 후보 도구들이 본문 외 필드를 인덱싱하는 방법을 지원하는가.

**판단 기준** — 도구를 고르는 게 아니라 **가능한 길과 각 길의 대가**를 표로 만들어 오는 것이 임무다. `앉을 자리와 프레임워크`가 이 표를 보고 고른다. "된다/조건부/안 된다"를 명시하고 1차 출처(공식 문서·저장소)를 인용한다. 추측으로 채우지 않는다.

**산출물** — `.scratch/nabi-cg-docs/research/korean-static-search.md`.

## Answer

**전문: [`research/korean-static-search.md`](../research/korean-static-search.md)** (551줄, 브랜치 `research/korean-static-search`, 커밋 `cbd0737`). 경로 7개(A~G) × 대가 표가 맨 앞에 있다.

**조사가 문서를 읽는 데 그치지 않았다.** 실제 `NABI_2.5.pdf`를 뽑아 **153페이지 / 본문 105,846자**짜리 한국어 사이트를 만들고 후보 도구를 전부 그 위에 돌렸다 — **인덱스 크기·재현율·지연시간이 전부 실측이다.** 아래 수치는 추정이 아니다.

### 1. "CJK 지원"은 한국어에 거의 아무것도 안 해준다

이게 이 조사의 핵심 발견이고, **코드로 확인됐다.**

- **Pagefind의 분절 대상은 `zh|ja|th` — `ko`가 빠져 있다.** 그런데 **공식 문서는 "applies to Chinese, Japanese, and Korean"이라고 쓰고 있다.** 문서와 코드가 어긋난다
- Orama/ZBSearch의 한국어 토크나이저도, Fumadocs 기본 `multilingual` 모드도 전부 `Intl.Segmenter` = **공백 분리**다. Node 24/ICU 78.2에서 직접 확인: `"화면송출이"`가 통째로 한 토큰(일본어는 `東京|大学`로 쪼갠다)
- **FlexSearch `Charset.CJK`의 전문은 `{ split: "" }`** — 음절 1-gram이다. 실측으로 `화면송출` 질의가 153쪽 중 **101쪽**을 반환한다. **쓰면 안 된다**
- **lunr-languages의 한국어 스테머는 항등함수**(`return word`), 토크나이저는 주석 처리돼 있다

**"한국어 지원"이라 적힌 것을 믿고 고르면 안 된다.** 고를 때 반드시 이 절을 근거로 쓸 것.

### 2. 진짜 문제는 조사가 아니라 복합명사다

티켓은 조사 변화("자막을"/"자막이")를 걱정했는데 **그건 싸게 풀린다** — 조사는 접미라서 prefix 확장이 거의 공짜로 처리한다(Pagefind가 양방향 접두 매칭을 한다).

**막히는 건 복합명사 안쪽이다:**

| 방식 | 재현율 | 인덱스(gzip) |
|---|---|---|
| 어절 정확일치만 | **60%** | — |
| + prefix 확장 | **92%** | 52 KB |
| + 2-gram | **100%** | 83 KB (+31) |
| 형태소(garu-ko) | 100% | 인덱스는 **36 KB로 최소**, 다만 **브라우저에 1.6 MB**(모델 1.4 MB 비압축) |
| **절충안 C′** | **99%** | **총 76 KB, WASM 없음** |

실패 사례가 전부 복합명사 안쪽이다 — `모드` 46%, `화면` 63%, `크롤` 44%.

**조사가 찾아낸 C′가 흥미롭다** — 형태소 분석을 **빌드에서만** 돌리고, 코퍼스에서 뽑은 **어절→형태소 사전(gzip 22 KB)**만 내려보낸다. WASM 없이 99% 재현율.

### 3. 초성 검색은 기성 도구 중 지원하는 것이 하나도 없다

전부 실측 0건. **자작만이 길이고 대가는 인덱스 +23 KB.**

### 4. 지형이 최근에 바뀌었다 — Orama는 지금 고르면 안 된다

**Orama 팀 전원이 이탈해 ZBSearch로 포크했다(2026-07-08).** `@orama/*`는 2025-12-19 이후 배포가 없고, 한국어 토크나이저는 소스에만 있고 **npm 미출시**다. Fumadocs 16.14.0은 이미 `zbsearch`로 옮겼다.

다만 ZBSearch 한국어 인덱스는 **291 KB gzip(청크 분할 없음)**으로 Pagefind 195 KB보다 크면서 검색 품질은 같은 경로다.

### 5. Cloudflare 궁합은 문제 없다 — 단 청크 분할은 기대하지 말 것

빌드 타임 인덱싱 전부 성립(Pagefind 색인 **0.104초**, 파일 수·크기 한도에 여유). **다만 Pagefind의 청크 분할이 이 규모에서 작동하지 않는다** — 기본 청크가 20,000이라 153페이지는 **1청크 109 KB**로 통째로 내려온다. Workers/Pages Functions는 길을 열지만 `output:'export'`의 "호스트 갈아타는 비용 0"을 깬다.

### 6. `스크린샷 406장`이 알아야 할 함정

**Pagefind는 `h1` 직후 첫 이미지의 alt만 메타로 잡고 두 번째부터는 색인하지 않는다**(실험으로 확인). 모든 `<img>`에 `data-pagefind-index-attrs="alt"`를 붙여야 한다. **그림이 거의 모든 페이지에 있는 매뉴얼에서, 모르면 조용히 새는 지점이다.** `figcaption`은 전부 잡힌다.

### 후속 티켓에 넘기는 것

- **`앉을 자리와 프레임워크`에게** — 경로 7개와 조합 7개가 총 전송량/재현율/자작량/위험으로 정리돼 있다. 도구 이름이 아니라 **이 표를 보고** 고를 것
- **`카테고리를 무엇 기준으로 가를 것인가`에게** — 그 티켓의 4번 축("검색이 구조를 얼마나 대신하는가")의 답: **아무것도 안 하면 재현율 60%**, prefix만으로 92%, 제대로 하면 99~100%. **검색은 공짜로 좋아지지 않는다** — 트리의 무게를 덜어 주는 대신 자작 비용을 받아 간다
- **`스크린샷 406장`에게** — alt 함정(위 6번)
