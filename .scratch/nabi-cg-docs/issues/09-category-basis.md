# 카테고리를 무엇 기준으로 가를 것인가

Type: grilling
Status: resolved
Blocked by: 05

## Question

**사이트의 카테고리를 나비CG의 기능(메뉴)별로 가를 것인가, 방송부가 하는 작업별로 가를 것인가.**

이 티켓은 **트리를 실제로 긋지 않는다** — 목적지가 스펙이므로 트리는 실행이다. 여기서 정하는 건 **가르는 기준** 하나이며, 그 기준이 본문 생산 비용을 통째로 좌우한다.

`매뉴얼의 실제 목차와 섹션 구조`가 안개에서 이 질문을 끌어올렸다. 그 전까지는 "매뉴얼이 어떻게 생겼는지"를 몰라 질문을 날카롭게 쓸 수 없었는데, 이제 대가가 수치로 보인다.

**드러난 대가 — 이게 이 티켓의 핵심 사실이다**

- 매뉴얼은 **압도적으로 메뉴를 따라간 기능 레퍼런스**다. `§3`의 하위 절 제목이 나비CG 풀다운 메뉴 이름 그 자체(편집/보기/삽입/도구/창)이고, `3.7.6 옵션`은 체크박스를 `3.7.6.3.1`~`3.7.6.4.9`까지 빠짐없이 나열한다
- ~~따라서 **기능별 트리는 공짜다** — 344항목 5단 차례가 그대로 트리가 된다~~ → **`공개 범위`가 이 공짜를 없앴다.** 아래 참조
- **작업별 트리는 본문 재작성을 수반한다** — 재료가 될 절차형 서술이 `Ch1 §3`, `Ch2 §2`, `Ch3 §1.2` **세 군데뿐**이다

**`공개 범위`가 건 제약 — 시작하기 전에 읽을 것**

경로 B(거리를 벌린다)로 확정되면서 **원 목차 트리는 저장소에서 멈춘다**. 344항목 5단 차례는 작업 자료로만 쓰고 **사이트 구조로 그대로 옮기지 않는다.** 제2조18호가 편집저작물을 `소재의 선택ㆍ배열 또는 구성에 창작성이 있는 것`으로 정의하므로 **차례야말로 매뉴얼에서 가장 보호가 두꺼운 단일 산출물**이고, 사이트가 그 배열을 그대로 걸으면 가장 값비싼 것을 복제하는 셈이 된다.

**주의 — 이 제약이 금지하는 것은 배열의 복제이지 기능이라는 기준이 아니다.** 기능별을 고르는 것은 여전히 가능하다. 다만 **우리가 새로 그어야 하고**, 따라서 "344항목이 그대로 트리가 된다"는 공짜가 사라졌다. **두 갈래의 비용 차가 좁혀진 상태에서 다시 재라.**

**`방송부가 쓰는 범위 확정`이 넘긴 재료 — 다만 결정을 대신하지는 않았다**

그 티켓은 **범위의 경계**를 작업에 그었지 **카테고리**를 작업별로 정한 것이 아니다. 둘은 다른 결정이다. 넘어온 것은 셋:

- **작업 목록 13개**(설교 자막 / 크기 조절 / 템플릿 수정 / 송출 조작 / 광고·공지 / 파일 관리 / 배경·CG / 사고 대처 / 프롬프터·PC 화면 송출 — 성경·찬송·교독문은 ❌). **작업별 트리를 고른다면 이 목록이 곧 1단이다** — 재작성 분량을 추정할 근거가 처음 생겼다
- **범위가 1차 35p / 2차 67p / 나감 34p로 끊겼다.** 트리 기준의 대가는 이제 136p가 아니라 **1차 35p에 대해** 계산된다
- **원본과 무게 배분이 정반대라는 사실.** 원본 최대인 `§3 편집` 52p에서 1차는 14p만 가져오고, 원본이 4p만 준 `§6 송출`은 통째로 1차다. **기능별 트리를 그대로 쓰면 이 반전이 사라진다** — 사이트가 원본의 무게를 물려받으면 "쓰는 범위만"이라는 목적지의 동사가 눈에 보이지 않게 된다

**갈라야 할 것**

1. **사람이 실제로 찾는 방식이 어느 쪽인가** — 막혔을 때 "삽입 메뉴에 뭐가 있더라"로 찾는가, "성경 구절을 띄우려면"으로 찾는가. 나비CG를 쓰는 본인의 경험이 근거다
2. **매뉴얼이 기능별인 것이 근거인가 관성인가** — compix가 그렇게 썼다는 사실은 "그게 옳다"의 근거가 아니다. 원본이 기능별이라 옮기기 쉽다는 것과, 사람이 그렇게 찾는다는 것은 다른 얘기다
3. **섞을 수 있는가** — 기능별 레퍼런스를 뼈대로 두고 자주 하는 작업 몇 개만 절차형 진입로로 얹는 형태. 이러면 재작성 분량이 작업 몇 개로 한정된다. 다만 **한 사이트에 두 가지 조직 원리가 서면 어디를 봐야 할지 모르게 되는** 위험이 있다
4. **검색이 구조를 얼마나 대신하는가** — `정적 사이트에서 한글 전문 검색`의 결과에 따라, 찾기가 검색으로 해결되면 트리 기준의 무게가 줄어든다. 반대로 검색이 약하면 트리가 유일한 길이 된다
5. **`§7 단축키`처럼 원본보다 나아지는 구간** — 표 5페이지가 곧 치트시트다. 이런 구간이 트리 어디에 붙는가

**판단 기준** — 작업별을 고른다면 **재작성 분량을 추정 없이 넘기지 말 것.** "작업별로 간다" 한 줄만 스펙에 남으면 `본문 생산 방식`이 감당 못 할 크기를 물려받는다. 기능별을 고른다면 **"사람이 그렇게 찾지 않는데도 그렇게 만든 이유"**를 적어 둘 것 — 나중에 뒤집힐 때 근거가 된다.

**이 티켓의 답이 `본문 생산 방식`을 구속한다.** 순서를 지킬 것.

## Answer

**둘 중 하나가 아니었다. 층위를 나눈다 — 진입은 검색, 1단 트리는 기능, 페이지 안쪽은 작업.**

### 1. 질문이 두 번 바뀌었다

티켓은 "기능별이냐 작업별이냐"로 열렸는데, 첫 두 답이 질문 자체를 갈아치웠다.

**첫째 — 실제 행동은 트리가 아니다.** 매주 하는 작업(자막이 길어져 크기 조절) 중 이 사이트가 있었다면 첫 클릭이 어디로 갔겠느냐에 **"검색창에 `자간` 치고 끝"**이 나왔다. 이유는 분명하다 — 나비CG 화면을 이미 띄워 놓고 패널을 보고 있는 상태라 **화면에 보이는 단어가 곧 검색어**가 된다. 매일·매주 경로는 검색이 가져간다.

**둘째 — 그러면 트리의 임무는 찾기가 아니라 발견이다.** 검색이 못 하는 일이 정확히 하나 있다: **모르는 단어는 못 친다.** 그리고 `05`가 범위의 기준으로 채택한 것이 *"만져야 하는데 몰라서 못 만지는 것"*이다. 1차 8개 중 `§3.4 Style Catalog`(어떤 작업에도 직접 안 걸리지만 "더 나은 방법"으로 들어옴)와 `§3.2`의 `Ctrl+B` 일괄지정(05에서 **"아마 쓸걸...? 확실하진 않아"**가 나온 자리)은 **검색으로는 영영 안 만난다.** 트리가 그걸 맡지 않으면 05가 34페이지를 잘라내면서까지 남긴 기준이 사이트에서 배신당한다.

### 2. 그리고 티켓의 전제가 뒤집혔다 — **작업별 1단은 발견이 0이다**

티켓은 작업별 트리를 "본문 재작성을 수반하는 비싼 쪽"으로만 봤다. 실제로는 **비싸기 전에 목적을 못 이룬다.**

`05`가 작업 목록을 만든 정의가 *"방송부가 **이미 하고 있는 작업**을 열거한다"*였다. 그래서 1단이 작업이면 트리 전체가 **이미 아는 것의 목록**이 된다 — `자막 크기 조절` / `템플릿 수정` / `송출 조작`을 훑어야 새로 알게 되는 것이 없다. 그 안에서 `Style Catalog`를 만나려면 페이지를 열고 안쪽을 읽어야 하는데, **그건 트리가 아니라 프로토타입 42가 이미 하고 있는 일**이다.

기능별 1단은 반대다. `속성 편집` 밑에 `Color`가 보이면 "그런 게 있었네"가 된다. 대신 약점이 명확하다 — **이름이 뭘 해주는지 안 알려준다**(`Style Catalog`, `Char Unit`, `Exclude`). 이건 **1단 항목마다 우리 문장 한 줄**로 값싸게 갚는다. 훑는 면은 기능 이름(발견), 읽히는 건 우리 문장(무엇을 해주는지)이고, 그 한 줄이 검색 색인에도 들어간다.

### 3. 층위 표 — 이 티켓의 결론

| 층위 | 축 | 근거 |
|---|---|---|
| **진입** | **검색이 1급** | 실제 행동이 "검색창에 `자간`" |
| **1단 트리** | **기능** (배열은 흐름, §5) | 검색이 못 하는 일 = 발견. 작업별 1단은 발견 0 |
| **페이지 안쪽** | **작업** | 프로토타입 42가 이미 이 형태 |

**두 축은 경쟁하지 않는다. 층위가 다르다.** 티켓이 3번으로 갈라 두고 *"한 사이트에 두 조직 원리가 서면 어디를 봐야 할지 모르게 된다"*고 경고한 "섞기"는 **같은 층위에 둘을 세울 때**의 위험이었다. 층위를 나누면 그 위험 없이 섞기의 이득을 갖는다.

**프로토타입 42가 우연이 아니었다.** 제목은 기능(`글자 속성`, 원본 §4.2와 1:1)인데 안쪽 H2가 전부 작업(`자막이 한 줄에 안 들어갈 때` / `글씨가 잘 안 보일 때` / `나머지 속성`)이다. 06은 이 티켓이 묻기 전에 한 층위의 답을 이미 찾아 놨고, 이 세션은 그 형태를 위로 한 층 확장했을 뿐이다.

### 4. 기능 축에 안 붙는 것 — 서랍을 만들지 않는다

1차 8개를 나비CG 화면에 대면 **2개가 안 붙는다**: `§7 단축키`(화면이 아니라 표), `Ch1 §4 이상증상 대처법`(기능이 아니라 상황). `05`의 안내문 3~4개도 마찬가지다.

"기타" 서랍은 금지다 — 발견의 값이 가장 높은 둘(단축키 = 원본보다 나아지는 유일한 구간, 이상증상 = 보는 순간이 방송 사고 중)이 서랍 속으로 들어간다.

**해법: 같은 층위에 단일 페이지로 세운다.** 기준점 `code.claude.com/docs`가 실제로 그렇게 한다 — 기능 카테고리들 **옆에** `Reference`·`Troubleshooting`이 최상위로 선다. 하위가 아니라 옆이다.

기각: **기능 축에 욱여넣기** — 단축키를 각 기능 페이지로 쪼개면 05가 1차로 올린 이유(*"표 5p가 곧 치트시트"*)가 파괴되고, 이상증상을 `송출` 밑에 넣으면 **사고 중에 클릭이 두 번**이 된다. **트리 밖 고정 링크** — 발견 면에서 사라지므로 §1의 결정과 어긋난다.

### 5. 배열 — 흐름 순. **이게 `공개 범위` 위반을 막는 자리다**

순서를 안 정하면 실행은 원본 순서로 늘어놓는다. 가장 쉬운 길이기 때문이고, 그게 정확히 `04`가 금지한 것이다 — 제2조18호가 편집저작물을 `소재의 선택ㆍ배열 또는 구성`으로 정의하므로 **선택은 이미 우리 것이 됐지만(154p → 8개) 배열이 원본이면 절반을 그대로 가져오는 셈**이다.

실용적으로도 손해다. 원본 순서(`§1 이해 → §2 파일 → §3 편집 → §4 속성 → §6 송출`)면 **매일·급한 `§6 송출`이 맨 뒤로 가고 매주 여는 `§4.2`가 중간에 묻힌다.** 05가 확인한 *"원본과 무게 배분이 정반대"*가 사이트에서 다시 사라진다.

**흐름 순으로 간다.** 세션 중 제기된 "흐름 순은 원본과 거의 같아진다"는 우려는 **실제 8개로 재 보니 과했다**:

| | 흐름 순 | 원본 순 |
|---|---|---|
| 1 | 파일 열기 | 파일 |
| 2 | **텍스트 임포트 `Ctrl+T`** | **객체 편집** |
| 3 | **크기 조절(글자·도형 속성)** | **Style Catalog** |
| 4 | **객체 편집 일괄** | **텍스트 임포트** |
| 5 | Style Catalog | **크기 조절** |
| 6 | 송출 | 송출 |
| 7 | **사고 대처** | 단축키 |
| — | | (`Ch1 §4 이상증상`은 원본 **맨 앞 챕터**) |

**절반이 자리가 다르고 이상증상은 맨 앞↔맨 뒤로 정반대다.** 원본이 `§3 편집`을 `§4 속성편집`보다 앞에 둔 탓인데 실제 매일 작업은 임포트 → 크기 조절이 먼저다. 겹치는 것은 거친 뼈대(`파일 → 편집 → 송출`)뿐이다.

**그리고 흐름 순이 빈도 순보다 §1의 답과 일관된다.** 빈도 순은 *찾기*를 빠르게 하는 배열인데 찾기는 이미 검색에 넘겼다. 남은 임무가 발견이라면 흐름 순은 트리를 훑을 때 *"내 일의 이 단계에서 내가 안 써본 게 뭐지"*가 단계째로 보인다. 빈도 순에는 그 맥락이 없다.

**배열의 출처를 못 박는다 — 매뉴얼 챕터 순서가 아니라 `05`의 작업 목록 13개 중 매일 작업 1·7의 실제 순서다.** 근거가 원본이 아니라 우리 운영이므로 `04`의 "구조는 새로"를 실제로 이행한다.

### 6. 흐름이 하나가 아니다 — 흐름 뒤에 사전(辭典)을 잇는다

위 표는 **작업 1(설교 자막 만들기)의 흐름**이다. 13개 중 매일은 1과 7뿐이고 나머지는 흐름이 다르다 — 작업 3(템플릿 수정, 시작점이 파일이 아님), 작업 8(광고·공지, Crawl 모드라 만드는 법이 다름), 작업 10(배경·CG, 삽입 계열), 작업 12(프롬프터·PC 화면 송출, 송출인데 §6이 아님).

**1단 앞쪽은 하루의 순서, 뒤쪽은 재료와 도구를 잇는다.**

기각: **매일 흐름 하나만 두고 나머지는 단계 안쪽에** — 작업 10(2차 6p)이 1단에서 안 보이면 영영 안 만나므로 발견을 죽인다. **흐름을 여러 줄로**(설교 자막 / 광고 자막 / 템플릿 수정 각각 1단) — §2에서 기각한 작업별 1단으로 되돌아가는 길이고, 같은 섹션이 여러 흐름에 중복으로 걸린다(`크기 조절`은 셋 다에 나온다).

### 7. 산출물 — 1단 구성 규칙 (트리 자체는 긋지 않는다)

```
[ 하루의 순서 ]   파일 → 텍스트 임포트 → 크기 조절 → 객체 편집 → Style Catalog → 송출
[ 재료와 도구 ]   배경·이미지 / 효과 / …
[ 단일 페이지 ]   단축키 · 사고 대처
```

- 모든 1단 항목에 **우리 문장 한 줄** — `Style Catalog — 같은 서식을 저장해 두고 재사용`
- 배열의 출처는 **작업 목록 13개**(매일 작업 1·7의 순서). 매뉴얼 챕터 순서가 아니다
- 안내문 3~4개는 1단에 **없음** — `05`가 목차로 남기지 않기로 이미 닫았고, 검색으로만 만나게 한다
- 페이지 안쪽은 작업별 — 프로토타입 42의 형태

### 8. 티켓이 요구한 기록 — **왜 기능인가, 그리고 뒤집힐 조건**

티켓의 판단 기준이 *"기능별을 고른다면 '사람이 그렇게 찾지 않는데도 그렇게 만든 이유'를 적어 둘 것"*이라고 요구했다.

**이유는 매뉴얼이 기능별이어서가 아니다 — 그건 관성이다.** 이유는 **검색이 찾기를 가져갔고, 남은 임무인 발견은 기능 축에서만 일어나기 때문**이다.

**뒤집힐 조건: 검색 재현율이 92% 아래로 떨어지면.** 그때는 트리가 다시 찾기를 맡아야 하고, 찾기가 목적이면 축이 달라진다. 이 결정을 다시 열 것.

### 9. 세션이 잡아낸 것 — 검색 키를 흘리고 있었다

"검색창에 `자간`"이 나온 직후 확인한 두 사실:

- **원본 매뉴얼은 한글 용어를 괄호로 달아 놨다** — `4.2.2.8. Kerning(자간)`, `4.2.2.7. Leading(줄 간격)`, 단축키 설명도 *"자간 벌리기 `Ctrl+H`"*
- **프로토타입 42에는 `자간`이 한 번도 안 나온다** — "글자와 글자 사이 간격"으로 풀어 썼다. 더 읽기 좋은 문장인데 **방금 말한 그 검색은 0건**이다

**원본과 거리를 벌리다가 색인을 깎았다.** 검색이 1급 진입로가 된 지금 이건 치명적이고, 트리 기준과는 다른 층위의 제약이라 아래로 넘긴다.

### 10. 뒤따르는 티켓에 넘기는 것

- **`본문 생산 방식` (07) — 검색 키를 흘리지 말 것.** §9. `Kerning`과 `자간` **두 이름이 본문에 다 있어야 한다.** 프로토타입 42가 이미 이걸 어겼으므로 07은 이 사례에서 시작할 것
- **`앉을 자리와 프레임워크` (08) — 재현율 60%는 이제 허용 불가.** `03`이 *"검색은 공짜로 좋아지지 않는다 — 트리의 무게를 덜어 주는 대신 자작 비용을 받아 간다"*고 정확히 이 거래를 예고했다. 이 세션이 그 거래를 했으므로 **99% 경로(절충안 C′, 총 76 KB)를 전제로** 고를 것. 아무것도 안 하면 60%다. **초성 검색(+23 KB)은 별개 문제이고 이 규모에선 값이 낮아 보인다** — 검색어가 `ㅈㄱ`이 아니라 `자간`이었다
- **`사람이 어떻게 찾아 들어가는가` (10) — 발견 면이 사이드바냐 개요 페이지냐.** 문서 프레임워크 사이드바는 보통 제목만 보여 준다. §7의 "한 줄 설명"이 살 자리가 사이드바가 아니라 **개요 페이지의 카드**일 수 있고, 그건 화면 결정이라 10의 몫이다. 더해 **검색이 1급 진입로로 확정됐으므로 10의 "화면이 몇 개인가"에 검색 UI의 자리가 들어온다**
- **`05`의 안내문 — 너무 짧으면 검색에 안 걸린다.** 검색으로만 만나기로 했으므로 `교회DB`·`성경`·`찬송`·`설치`·`오디오`가 안내문 본문에 실제로 박혀 있어야 한다. 05의 *"이유 없이 사실만"*과 긴장이 있고, 07이 문장을 쓸 때 조정할 것
