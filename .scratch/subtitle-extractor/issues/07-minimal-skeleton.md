# 확장을 감당할 최소 뼈대 — 라우팅과 모듈 경계

Type: grilling
Status: resolved
Blocked by: (없음 — 01, 02, 04, 05, 06 모두 resolved)

## Question

방송부 도구가 계속 붙을 그릇으로서, **지금 그어야 할 경계는 무엇이고 긋지 말아야 할 경계는
무엇인가.** 라우팅 구조와 모듈 경계를 정한다.

맵의 안개에 있던 **확장 뼈대 구조**를 승격시킨다. 승격 조건이었던 "첫 기능의 형태가 정해질
것"이 `화면 구성과 조작 흐름`으로 충족됐다 — 이제 이 기능이 실제로 무엇을 요구하는지 다
보이므로 "얼마나 최소인가"를 판단할 수 있다.

## 앞선 결정이 이미 그어 놓은 경계

새로 발명할 것이 아니라 **이미 서 있는 것들을 확인하고 그 사이만 채우는** 작업이다.

- `parseHwp(bytes) => StyledRun[]` — `입력 파일 포맷 정책`이 **함수 하나**로 긋고 포맷
  추상화는 만들지 않기로 한 경계. `StyledRun`은 `{text, color, paragraph}` 셋
- **규칙 층은 hwp를 전혀 모른다** — `StyledRun[]`만 받아 자막·걸러낸 것·모르는 색 셋을
  뱉는다. 참조 구현 [`prototypes/subtitle_rules.py`](../prototypes/subtitle_rules.py)의
  파서 층/규칙 층 구분이 그대로 옮겨온다
- **나비CG 출력** — `나비CG 임포트 파일 규격 확정`이 정한 UTF-8 BOM + CRLF + 빈 줄 구분
- **서버 없음** — `브라우저에서 hwp/hwpx의 색상 포함 텍스트를 추출할 수 있는가`가 정적
  배포로 성립함을 확인했다. API 라우트도 서버 액션도 필요 없다

## 정할 것

- **라우팅** — 자막 추출기가 `/`인가 `/subtitle-extractor`(가칭)인가. `/`를 도구 목록으로
  두는 것은 **지금 필요한가, 두 번째 도구가 붙는 날 필요한가**
- **모듈 경계** — 위 세 층(파서 / 규칙 / 출력)이 어느 디렉터리에 어떤 이름으로 앉는가.
  자막 추출기 전용인 것과 앞으로 공용이 될 것을 지금 가르는가
- **UI 층의 경계** — 06이 정한 화면(드롭존 ↔ 결과 2단, 칩 줄, 미리보기 모달)을 컴포넌트로
  어떻게 자르는가. 상태를 어디에 두는가
- **테스트가 붙을 자리** — 04가 남긴 입력→출력 정답 쌍 9개와 원고 3편 전체 대조를 어디서
  돌리는가. 테스트 러너를 지금 넣는가

## 넘지 말 것

맵의 Notes가 못 박은 원칙 — **뼈대는 첫 기능이 실제로 요구하는 만큼만.** 미래 기능을 위한
선제적 설계는 하지 않는다. "나중에 문서 기능이 붙으면 좋을 구조" 같은 판단이 나오면 그건
이 티켓 밖이다. 지금 있는 기능 하나가 요구하지 않는 경계는 긋지 않는다.

Out of scope로 이미 밀려난 것들(찬양 가사, 문서·FAQ, 로그인)을 위한 자리를 미리 비워 두는
것도 여기 포함된다 — **비워 두지 않는다.**

## 이 티켓 밖

- **배포 방식과 저장소 셋업** — 맵의 안개에 그대로 남아 있다. 별개 문제

## Answer

**뼈대는 도구 폴더 하나다.** 자막 추출기의 전부 — 라우트·파서·규칙·출력·화면·테스트 —
가 `app/subtitle-extractor/` 한 폴더에 앉고, 그 밖에 새로 그은 경계는 **없다**.

### 확정된 구조

```
app/
  layout.tsx
  page.tsx                        ← / : 도구 목록 (지금은 링크 한 개, 서버 컴포넌트)
  subtitle-extractor/
    page.tsx                      ← "use client". 문서 상태 useState 하나
    _lib/
      parse-hwp.ts                ← parseHwp(bytes) => StyledRun[]   (05)
      rules.ts                    ← StyledRun[] → 자막·걸러낸 것·모르는 색  (04)
      nabi-cg.ts                  ← toNabiTxt: BOM + CRLF + 빈 줄   (01, 프로토타입에서 이식)
      rules.test.ts               ← 04의 정답 쌍 9개 (항상 실행)
      corpus.test.ts              ← 원고 3편 대조 (fixture 없으면 skip)
    _components/                  ← 06이 그은 자름 그대로, 더 잘게 자르지 않음
      drop-zone.tsx / header.tsx / chips.tsx
      script-pane.tsx / subtitle-pane.tsx / preview-modal.tsx
```

### 결정 일곱

**1. 라우팅 — `/` = 도구 목록, `/subtitle-extractor` = 자막 추출기.**
차팅 당시엔 "도구 목록은 두 번째 도구가 붙는 날 필요한 것"으로 보였으나, 담당 개발자가
**자막 추출기 완성 직후 방송실 다른 도구를 계속 만들 것**임을 확정했다. 두 번째 도구가
가정이 아니라 예정이면 목록은 미래 대비가 아니라 **현재 요구**다. 목록 화면은 지금
링크 한 개짜리이며 별도 설계가 필요 없다.

**2. 공용으로 빼는 것은 없다.** 파서·규칙·나비CG 출력 셋 다 자막 추출기 전용에 둔다.
"두 번째 도구가 온다"는 사실이 **"두 번째 도구가 이 코드를 이 모양 그대로 쓴다"를 뜻하지
않는다.** `toNabiTxt`는 지금 `(subtitles: string[]) => Blob` 한 줄이고, 찬양 가사 도구가
같은 시그니처를 요구할지는 아무도 모른다. 두 번째 사용처가 **실제로** 생긴 날 끌어올리는
비용은 파일 이동 한 번이지만, 지금 틀린 모양으로 공용에 앉히면 두 번째 도구가 거기에
맞춰 휜다. (기각한 갈래: 나비CG 출력만 공용으로 — 규격이 앱이 아니라 나비CG가 정한
외부 지식이라는 논거는 진짜였으나, 그 지식은 파일 위치와 무관하게 보존된다.)

**3. 콜로케이션.** 한 도구의 모든 것이 한 폴더에 있는 것이 결정 2의 물리적 표현이다 —
도구를 지우면 폴더를 지우고, 도구를 추가하면 폴더를 추가한다. 저장소가 이미 쓰는 밑줄
폴더(`app/prototype/_components/`) 관습을 그대로 따르며 새 규약을 발명하지 않는다.
`src/`는 만들지 않고 `lib/` 별도 트리도 만들지 않는다.

**4. 상태는 `page.tsx`의 `useState` 하나.** 06이 화면을 **읽기 전용**으로 확정했으므로
상태를 바꾸는 경로가 문자 그대로 하나다 — 파일이 들어온다. 결과가 한 번 만들어진 뒤로는
변하지 않고 트리 깊이가 2단이라 prop drilling이 생기지 않는다. Context·reducer·store는
값을 치를 대상이 없다. 상호작용 상태 넷(선택된 장 / 열린 칩 패널 / 미리보기 모달 /
드래그 오버)은 프로토타입처럼 각자 쓰이는 컴포넌트 안에 산다. 훅으로 빼는 갈래는
`File → ArrayBuffer → parseHwp → 규칙`이 15줄이고 파서·규칙이 이미 순수 함수로
테스트되므로 기각.
**컴포넌트 자르기는 새로 정하지 않았다** — 06이 이미 그었고 프로토타입이 갖고 있다.

**5. Vitest를 지금 넣는다.** **규칙 층의 회귀가 조용하기 때문**이다 — 자막이 8장이어야
하는데 7장이 나와도 화면은 멀쩡해 보인다(06이 모르는 색으로 8장→7장을 눈으로 본 그
현상). 눈으로 세는 검사는 방송 준비 중에 성립하지 않는다. 04의 정답 쌍 9개가 **이미
만들어져 있어** 넣는 비용은 발명이 아니라 옮겨 적기다. `node:test`는 TS + JSON fixture에
손이 더 간다.

**6. 설교 원고는 저장소에 넣지 않는다.** 작업 중 드러난 사실 — `app/prototype/subtitle-
screen/fixtures.json`(270KB)에 **설교 3편의 전문**(파일명·제목·문단 113/109/132개)이
그대로 들어 있고, 저장소는 아직 git 초기화 전이라 아무것도 커밋되지 않았다. 결정:
`fixtures.json`은 **gitignore**하고 로컬에만 두며, 원고 3편 대조 테스트는 **있으면 돌고
없으면 skip**한다. 근거 셋 — (a) 개발자가 1명이라 "CI에서도 돌아야 한다"는 이점이 값을
못 낸다, (b) 커밋하는 갈래는 **저장소를 private으로 두겠다는 결정을 여기서 미리 묶는데**
배포·저장소 셋업은 아직 안개에 있다, (c) 04의 정답 쌍 9개는 짧은 `StyledRun` 리터럴이라
설교 내용이라 할 것이 없고 **규칙 층의 회귀는 이 9개가 이미 다 잡는다** — 원고 3편
대조는 규칙을 확정할 때 필요했던 검증이지 매일 돌 회귀 테스트가 아니다.
합성 hwp fixture를 만들어 파서까지 항상 테스트하는 갈래는 **한글로 파일을 만들어 줄
사람이 필요한 새 작업**이 생겨 기각했다. 필요해지면 나중에 붙인다.

**7. 프로토타입은 삭제하되 확인된 것은 옮긴다.** `app/prototype/`은 지금 **라우트로 살아
있어** 이대로 두면 배포된 앱에 `/prototype/subtitle-screen`이 노출되고 그 안에 설교
전문이 붙어 있다. 통째로 삭제한다. 단 `toNabiTxt`(01이 담당자 실전 파일과 대조해 확정한
규격)와 `variant-f.tsx`(06이 여섯 갈래를 나란히 놓고 고른 화면)는 `app/subtitle-
extractor/`로 **옮겨 출발점으로 삼는다** — 프로토타입은 던져버릴 코드가 맞지만,
**사람이 눈으로 확인하고 확정한 결과물을 "프로토타입이니까"라는 이유로 다시 타이핑하면
확인된 것을 미확인으로 되돌리는 셈**이다. 옮기면서 `// PROTOTYPE` 주석, 지어낸
`SCENARIOS`, `fixtures.json` 의존은 떼어낸다.
**단 `Doc`/`Block`/`Verdict` 타입은 다시 본다** — 프로토타입이 화면을 그리려고 발명한
모양이라 규칙 층의 진짜 출력과 일치하는지 검증된 적이 없다. 확정된 타입은 05가 정한
`StyledRun {text, color, paragraph}` 하나뿐이다.

### 긋지 않은 경계 (의도적으로)

공용 라이브러리 디렉터리 · 포맷 추상화 · 상태 관리 계층 · `src/` 트리 · Out of scope
항목들(찬양 가사, 문서·FAQ, 로그인)을 위한 빈자리. **하나도 비워 두지 않았다.**
