# 빨간색 판정 규칙과 자막 쪼개는 단위

Type: grilling
Status: resolved
Blocked by: 01, 02



## Question

원고에서 무엇을 "자막 하나"로 볼 것인가? 그 규칙을 기계가 실행할 수 있을 만큼 정확하게 정한다.

`나비CG 임포트 파일 규격 확정`(출력의 제약)과 `설교 원고 실물 확보 및 파일 포맷 판별`(입력의 실제 모습)이 모두 해소되어야 답할 수 있다. 두 끝단을 모르면 규칙이 공상이 된다.

**정할 것**

- **빨간색의 정의** — 정확히 한 가지 색값인가, 아니면 여러 빨강 계열이 섞여 있는가. 후자라면 어디까지를 빨강으로 받아들이는가. 원고에 다른 색이 등장한다면 그것들과 어떻게 구분하는가
- **자막의 경계** — 빨간 덩어리 하나가 자막 한 장인가? 문단이 기준인가, 문장이 기준인가, 아니면 연속된 빨간 글자 구간이 기준인가. 중간에 검은 글자가 끼어들면 자막이 나뉘는가 이어지는가
- **길이 초과 처리** — 나비CG의 글자 수 제한을 넘는 자막이 나오면 자동으로 쪼갤 것인가, 사람에게 알리고 맡길 것인가. 쪼갠다면 어디서 끊는가
- **정리 규칙** — 앞뒤 공백, 따옴표, 성경 장절 표기, 원고에만 필요한 기호 등 자막에 그대로 나가면 안 되는 것들을 어떻게 다룰 것인가
- **순서** — 원고에 등장하는 순서가 곧 자막 순서인가

**결과 기록** — 실제 샘플 원고의 빨간 텍스트 몇 개를 예시로 들어, 그것이 어떤 자막들로 변환되어야 하는지 **입력→출력 쌍**으로 적는다. 이 쌍들이 나중에 그대로 테스트 케이스가 된다.

## 실증 데이터 (2026-07-31 추가)

`설교 원고 실물 확보 및 파일 포맷 판별`에서 실제 원고 한 편을 추출해본 결과, 이 티켓이 답해야 할 문제가 구체적으로 드러났다. 아래는 추측이 아니라 실물에서 관찰된 것이다.

- **빨간색은 정확히 `#FF0000` 하나였다.** 빨강 계열이 여러 색으로 흩어져 있지 않았으므로 판정 규칙이 단순해질 가능성이 높다. 다만 원고 한 편만 확인한 것이라 다른 원고에서도 그런지는 미확인
- **인접 구간 병합이 필수다.** 같은 빨간색이어도 문자 모양 ID가 다르면 구간이 갈라진다. 실제로 한 인용문이 `"다른 이들도 …"` / `"그러나 우리가 …"` / `"(고린도전서 9:12)"` 세 조각으로 났고, `둘째,`와 그 뒤 문장도 따로 떨어졌다. **원본에서 붙어 있던 것을 어떤 기준으로 다시 이어붙일 것인가**가 이 티켓의 최대 난제다
- **길이 초과 자막이 실제로 나온다.** 성경 본문 여러 절(`4 우리가 먹고 마실 권리가 없겠느냐 5 …`)이 한 구간에 담겨 자막 한 장에 들어갈 수 없다. 절 번호를 기준으로 쪼갤 수 있을지 검토할 것
- **큰따옴표와 출처 표기가 그대로 딸려온다.** `"이와 같이 주께서도 …" (고린도전서 9:14)` 형태다. 자막에 출처를 넣을지, 넣는다면 같은 장에 넣을지 분리할지 결정이 필요하다
- 추출된 빨간 구간의 성격은 네 가지였다 — 설교 제목, 대지(첫째/둘째/셋째), 성경 인용, 기도제목. **이들을 같은 규칙으로 다룰지 종류별로 다르게 다룰지**도 정해야 한다

## 정답 쌍 확보 (2026-07-31 추가)

`나비CG 임포트 파일 규격 확정`을 해소하면서 **담당자가 직접 만들어 실전에 쓴 임포트 파일과 그 원본 hwp 짝**을 확보했다. 이 티켓이 정하려는 규칙의 **정답이 이미 존재한다** — 추측으로 규칙을 세울 게 아니라, 담당자가 실제로 무엇을 했는지 읽어내면 된다.

- 원본: `~/Downloads/0118-25고전20260531십자가의 도 하나님의 능력.hwp`
- 담당자 최종 출력: `~/Downloads/0118-25고전20260531십자가의 도 하나님의 능력-nabi.txt`

`extract_red.py` 결과 **10구간** vs 담당자 최종 **8장**. 순서·문구 완전 일치, 차이는 아래 하나뿐이다.

### 1. 꺾쇠 연출 지시문은 자막이 아니다 — 확인된 필터 규칙

담당자가 버린 2개는 **둘 다 `<사진을 띄운다.>`**였다. 빨간색이지만 자막이 아니라 담당자 자신에게 남긴 **연출 지시문**이고, 꺾쇠 `<...>`로 감싸여 있다.

**"빨강이면 자막"이 거짓이라는 실물 반례다.** 이 티켓은 이제 빨강 판정만이 아니라 **빨강 중에서 무엇을 버리는가**까지 답해야 한다. 꺾쇠로 감싼 줄을 버리는 규칙이 일반적으로 성립하는지, 다른 형태의 지시문은 없는지 확인이 필요하다.

### 2. 중복 자막을 제거하면 안 된다

최종 파일의 1번과 3번 자막이 **글자 그대로 동일**하다(고린도전서 1:18 인용이 두 번 등장). 설교 흐름상 같은 구절을 두 번 띄우는 것이므로 **dedupe는 명백한 버그다.**

### 3. 따옴표와 출처 표기는 그대로 둔다 — 이미 답이 나왔다

앞선 실증에서 "결정이 필요하다"고 남겼던 항목인데, 정답이 나왔다. 담당자의 최종 자막이 이렇다.

```
“십자가의 도가 멸망하는 자들에게는 미련한 것이요 구원을 받는 우리에게는 하나님의 능력이라” (고린도전서 1:18)
```

**큰따옴표 유지, 출처 표기 유지, 같은 자막 장 안에 유지.** 정리(cleanup) 규칙은 생각보다 훨씬 소극적이어야 한다.

### 4. 길이로 쪼갤 근거가 약하다

나비CG 규격에 **문서화된 글자수 제한이 없다**. 넘치면 Word Wrap이 단어 단위로 흘리고 페이지까지 넘긴다. 그리고 결정적으로 **담당자 실물 파일의 최장 자막이 91자인데 쪼개지 않고 그대로 나갔다.**

따라서 "길이 초과 처리"의 기본값은 **쪼개지 않는다**가 되어야 하며, 쪼갠다면 그 근거는 규격상의 제한이 아니라 **가독성 판단**이다. 앞서 관찰된 "성경 여러 절이 한 구간에 담긴 자막"을 절 번호로 쪼갤지도 이 관점에서 다시 볼 것.

### 5. 쪼개짐은 원고마다 편차가 있다

이 원고는 10구간이 **모두 온전한 문장**으로 쪼개짐이 전혀 없었다. 반면 `복음을 위하여` 원고는 한 인용문이 3조각 났다. **인접 구간 병합 규칙은 여전히 필요하지만, 모든 원고에서 발동하는 것은 아니다.**

### 출력 형식 (확정, 참조용)

이 티켓이 정하는 "자막 한 장"이 그대로 아래 형식의 한 블록이 된다.

- 순수 `.txt`, **UTF-8 with BOM**, **CRLF**, 파일 끝 개행 없음
- **자막 장 사이에 빈 줄 하나.** 연속된 비어있지 않은 줄은 같은 장의 여러 줄
- 컬럼·헤더·순번 필드 없음. 순서는 파일 등장 순서

### 세 번째 원고

`~/Downloads/0401-09잠20260510지혜와 명철을 얻으라.hwp`가 있다(짝 출력 없음). 규칙을 세운 뒤 **검증용**으로 돌려볼 수 있다. `입력 파일 포맷 정책`에서 이 원고까지 포함해 3편 전부 추출에 성공했다 — 빨간 구간 10 / 19 / 22개.

## `입력 파일 포맷 정책`이 넘긴 것 (2026-07-31 추가)

**최대 난제였던 "인접 구간 병합"은 파서 층에서 풀린다.** "같은 빨강인데 문자 모양 ID가 달라 구간이 갈라진다"는 **참조 구현이 만든 문제이지 데이터의 한계가 아니다.** 파서는 `charShapeID → 색` 표와 `위치 → charShapeID` 배열을 **둘 다** 쥐고 있으므로, shapeID가 아니라 **색으로 묶으면** 글자 단위 색상을 언제든 계산할 수 있다. `extract_red.py`가 조각을 내는 건 그 참조 구현이 shapeID 단위로 그룹핑하기 때문이다.

즉 **"무엇을 한 덩어리로 볼 것인가"는 순수하게 이 티켓의 결정**이며, 파일 포맷이 강제하는 제약이 아니다. 색 기준으로 묶을지, 문단 경계까지 볼지, 검은 글자가 끼어들 때 어떻게 할지 — 파서에 원하는 대로 시킬 수 있다.

**경계를 통과하는 데이터의 최종 형태는 이 티켓이 확정한다.** `입력 파일 포맷 정책`은 경계가 `parseHwp(bytes) => StyledRun[]` 함수 하나라는 것과, 최소한 **텍스트 / 색(RGB) / 문단 인덱스 / 문단 내 시작 위치**가 통과해야 한다는 것까지만 정했다. 뒤의 둘은 "두 조각이 원본에서 붙어 있었는가"를 판단하는 데 필수다. 필드 이름과 추가 필드는 규칙을 세우면서 정하면 된다.

**입력→출력 정답 쌍은 파일이 아니라 `StyledRun` 배열 리터럴로 적는 것이 좋다.** 그래야 자막 규칙 테스트가 hwp 파일 없이 돌고, 파서 테스트와 분리된다.

## Answer

**문단이 자막의 단위다.** 최대 난제로 꼽았던 "인접 구간 병합"은 병합 규칙을 발명할 문제가 아니라 **경계를 어디에 그을 것인가**의 문제였고, 답은 원고에 이미 있었다 — 쪼개진 조각은 **예외 없이 같은 문단 안에서만** 갈라진다. 문단을 경계로 삼으면 병합은 "그 문단의 조각을 순서대로 이어붙인다"로 끝난다.

### 규칙 (확정)

```
1. 빨강 = #FF0000 정확히 일치. 그 외의 색은 자막이 아니다
2. 한 문단의 (공백만인 조각을 뺀) 모든 조각이 빨강이면 → 그 문단이 자막 한 장
3. 그 문단의 조각을 전부 순서대로 이어붙이고, 앞뒤 공백만 자른다. 안쪽은 원고 그대로
4. 남은 것 중 <...>로만 이루어진 자막은 버린다
5. 쪼개지 않는다. 중복을 제거하지 않는다. 원고 등장 순서가 곧 자막 순서다
6. 검정도 #FF0000도 아닌 색이 원고에 있으면 화면에 알린다 (자막으로는 쓰지 않는다)
```

### 실증 — 담당자 정답 파일과 바이트 단위 완전 일치

위 규칙을 그대로 구현해(`prototypes/subtitle_rules.py`) 담당자가 실전에 쓴 임포트 파일과 대조했다.

| 원고 | 빨간 구간 | 규칙 적용 → | 담당자 정답 |
|---|---|---|---|
| 십자가의 도 하나님의 능력 | 10 | **8장** | **8장 — 바이트 완전 일치** ✅ |
| 지혜와 명철을 얻으라 | 19 | 16장 | (정답 없음) |
| 복음을 위하여 | 22 | 19장 | (정답 없음) |

정답 파일이 있는 한 편에 대해 **BOM·CRLF·빈 줄 구분까지 포함해 바이트가 동일**하다. 규칙이 담당자의 실제 판단을 재현한다.

### 각 항목의 근거

**빨간색의 정의 — `#FF0000` 정확히.** 원고 3편의 색을 전수 조사한 결과 **검정 `#000000`과 빨강 `#FF0000` 두 개뿐**이었다. 빨강 계열이 흩어져 있지도, 제3의 색이 등장하지도 않았다. `extract_red.py`의 느슨한 범위(`R>120, G<100, B<100`)는 실증용 임시값이었고 정본이 아니다.

엄격한 판정의 실패 방식은 **자막이 소리 없이 사라지는 것**이고, 이건 담당자가 원고를 대조하기 전엔 모른다. 그래서 6번 조항을 붙였다 — 판정은 엄격하게 가되 **모르는 색을 만나면 침묵하지 않는다.**

**자막의 경계 — 문단.** 실증 데이터가 "최대 난제"로 남긴 것이 여기서 풀렸다.

- `복음을 위하여` 문단 30: `"다른 이들도 …` / `그러나 우리가 …` / `" (고린도전서 9:12)` **3조각 → 전부 같은 문단** → 한 장
- 같은 원고 문단 51: `둘째, ` / `복음을 위하여 기꺼이 종이 되어야 합니다.` **2조각 → 같은 문단** → 한 장
- **문단을 넘어가는 병합이 필요한 경우는 3편 어디에도 없었다**

이어붙일 때 **각 조각을 strip한 뒤 join하면 안 된다.** 문단 30의 첫 조각은 `… 우리일까보냐 `로 공백이 끝에 붙어 있고, 그걸 잘라내면 단어가 붙어버린다. **날것 그대로 concat → 전체를 한 번만 strip.**

**"검은 글자가 끼어들면 어떻게 되는가"** — 티켓이 물었던 이 질문의 답은 **그 문단은 자막이 아니다**이다. 그리고 이게 그대로 지시문 필터가 된다(아래).

**길이 초과 — 쪼개지 않는다.** 나비CG에 문서화된 글자수 제한이 없고(넘치면 Word Wrap이 흘림), 유일한 정답인 담당자 파일의 최장 자막 **91자가 쪼개지지 않고** 나갔다. 다른 원고의 122자·153자에 대한 정답은 없으므로, **근거 있는 유일한 기본값은 "그대로 둔다"**이다. 짧게 나가야 하는 날은 목사님이 원고에서 문단을 나누면 된다 — 규칙을 추측으로 채우는 것보다 정확하다.

**정리 규칙 — 앞뒤 공백만.** `나비CG 임포트 파일 규격 확정`이 이미 답을 줬다: 큰따옴표 유지, 출처 표기 유지, 같은 장 안에 유지. 여기에 실물 조사로 둘을 더했다.

- **문단 내부 줄바꿈은 3편에 한 건도 없다.** 자막 한 장은 항상 한 줄이다. 규칙을 만들 필요가 없다
- **연속 공백 한 건 발견** (`지혜와 명철`의 `… 있다.” /  허브 브룩스`, 원고 자체 오타). **그대로 내보낸다** — 정리를 최소로 유지하는 편이 "넣은 것은 넣은 대로 나간다"는 예측 가능성을 지킨다

**순서 — 원고 등장 순서.** 정답 파일과 순서가 완전히 일치했다. 별도 정렬 없음.

### 지시문 필터 — 두 규칙을 겹쳐 건다

담당자가 버린 `<사진을 띄운다.>` 2개는 **둘 다 검은 글 한복판에 낀 빨간 조각**이었고, 살린 8장은 **전부 문단 전체가 빨강**이었다. `지혜와 명철`의 지시문 3개도 모두 검은 문단 속에 있다. 즉 2번 규칙이 지시문을 **구조만 보고** 전부 잡아낸다.

그렇다면 4번(꺾쇠)은 왜 남기는가 — 두 규칙이 **서로 다른 방식으로 뚫리기 때문**이다.

| 앞으로 이런 게 오면 | 2번 (문단 전체 빨강) | 4번 (꺾쇠) |
|---|---|---|
| 검은 글 속 `【사진】` 등 다른 기호의 지시문 | **잡음** ✅ | 샘 ❌ |
| 문단 하나를 통째로 차지한 `<사진을 띄운다.>` | 샘 ❌ | **잡음** ✅ |
| 진짜 자막인데 꺾쇠 인용 `<나는 왕이로소이다>` | 살림 ✅ | **잃음** ❌ |

2번은 구조를, 4번은 글자를 본다. 겹쳐 걸어 서로의 구멍을 메운다.

**검증 상태를 정직하게.** 세 원고에서 **2번이 지시문을 전부 처리하므로 4번은 한 번도 발동하지 않는다.** 4번은 실물로 검증된 적 없는 방어 조항이며, 위 표의 마지막 줄이 그 대가다. 발동하는 날까지 옳은지 알 수 없다.

### 두 개의 미발동 조항 (알고 넣는 것)

3편 전체에 대해 발동 여부를 측정했고, 둘 다 **0회**다.

| 조항 | 발동 | 방향 | 위험 |
|---|---|---|---|
| 2번의 "공백만인 조각을 뺀" 예외 | 0회 | 자막을 **늘리는** 쪽 | 낮음 — 없으면 문단 끝의 검은 공백 하나에 자막이 통째로 사라진다 |
| 4번 꺾쇠 필터 | 0회 | 자막을 **줄이는** 쪽 | 있음 — 꺾쇠 든 진짜 자막을 잃는다 |

공백 예외는 **자막을 잃지 않는 방향**으로만 작동하므로 미검증이어도 안전하다. 꺾쇠 필터는 반대 방향이므로, 실전에서 자막이 사라지는 일이 생기면 **여기를 가장 먼저 의심할 것.**

### `StyledRun` 최종 형태 (`입력 파일 포맷 정책`이 04에 넘긴 것)

05는 경계가 `parseHwp(bytes) => StyledRun[]`이고 최소 **텍스트 / 색 / 문단 인덱스 / 문단 내 시작 위치**가 통과해야 한다고 정한 뒤, 최종 형태를 이 티켓에 넘겼다. 규칙이 실제로 쓰는 것은 **셋뿐이다.**

```ts
type StyledRun = {
  text: string;       // 원고 그대로. trim·정규화 없음 (앞뒤 공백이 병합에 필요하다)
  color: string;      // "#RRGGBB" 대문자 6자리
  paragraph: number;  // 0부터. 문서 전체를 통틀어 단조 증가
};
// 문서 등장 순서대로 담긴다
```

**"문단 내 시작 위치"는 뺀다.** 05가 그 필드를 요구한 이유는 "두 조각이 원본에서 붙어 있었는가"를 판단하기 위해서였는데, 문단 경계로 묶기로 하면서 그 판단 자체가 사라졌다 — 같은 `paragraph` 값이면 붙어 있는 것이고, 순서는 **배열 순서**가 보장한다. 쓰지 않는 필드는 파서가 채워야 할 부채이므로 넣지 않는다.

`text`를 파서가 손대지 않는 것이 중요하다. 조각별 trim은 문단 30의 `… 우리일까보냐 ` + `그러나 우리가 …`를 붙여버린다.

### 입력 → 출력 정답 쌍 (테스트 케이스)

05의 권고대로 **파일이 아니라 `StyledRun` 배열 리터럴**로 적는다. 자막 규칙 테스트가 hwp 파일 없이 돌고 파서 테스트와 분리된다. 아래는 전부 실물에서 그대로 뜬 것이다.

```ts
const R = "#FF0000", K = "#000000";

// [1] 문단 전체 빨강 — 그대로 한 장  (십자가의 도, 문단 12)
[{ text: "“십자가의 도가 멸망하는 자들에게는 미련한 것이요 구원을 받는 우리에게는 하나님의 능력이라” (고린도전서 1:18)\n", color: R, paragraph: 12 }]
→ ["“십자가의 도가 멸망하는 자들에게는 미련한 것이요 구원을 받는 우리에게는 하나님의 능력이라” (고린도전서 1:18)"]
// 끝의 \n이 잘리는 것 외에 손대지 않는다

// [2] 문단 안 3조각 병합 — 최대 난제의 핵심 케이스  (복음을 위하여, 문단 30)
[{ text: "“다른 이들도 너희에게 이런 권리를 가졌거든 하물며 우리일까보냐 ", color: R, paragraph: 30 },
 { text: "그러나 우리가 이 권리를 쓰지 아니하고 범사에 참는 것은 그리스도의 복음에 아무 장애가 없게 하려 함이로다", color: R, paragraph: 30 },
 { text: "” (고린도전서 9:12)\n", color: R, paragraph: 30 }]
→ ["“다른 이들도 너희에게 이런 권리를 가졌거든 하물며 우리일까보냐 그러나 우리가 이 권리를 쓰지 아니하고 범사에 참는 것은 그리스도의 복음에 아무 장애가 없게 하려 함이로다” (고린도전서 9:12)"]
// 첫 조각 끝의 공백이 살아 있어야 한다. 조각별 strip 금지

// [3] 2조각 병합  (복음을 위하여, 문단 51)
[{ text: "둘째, ", color: R, paragraph: 51 },
 { text: "복음을 위하여 기꺼이 종이 되어야 합니다.\n", color: R, paragraph: 51 }]
→ ["둘째, 복음을 위하여 기꺼이 종이 되어야 합니다."]

// [4] 검은 글 속 지시문 — 문단째 탈락  (십자가의 도, 문단 5)
[{ text: "사도 바울은 2차 전도여행 중 고린도를 방문하여 복음을 전했고, …", color: K, paragraph: 5 },
 { text: "<사진을 띄운다.>", color: R, paragraph: 5 },
 { text: " 고린도는 그리스 남쪽의 항구도시로, …\n", color: K, paragraph: 5 }]
→ []

// [5] 문단 맨 앞의 지시문 — 마찬가지로 탈락  (지혜와 명철, 문단 70)
[{ text: "<사진과 함께 글을 띄운다.>", color: R, paragraph: 70 },
 { text: " 그때 허브 브룩스(Herb Brooks) 감독은 이런 말을 했습니다. \n", color: K, paragraph: 70 }]
→ []

// [6] 중복 자막 — 둘 다 유지 (dedupe 금지)  (십자가의 도, 문단 12 & 34)
[{ text: "“십자가의 도가 … 하나님의 능력이라” (고린도전서 1:18)\n", color: R, paragraph: 12 },
 { text: "“너는 무엇을 능력이라고 생각하느냐?”\n",                  color: R, paragraph: 40 },
 { text: "“십자가의 도가 … 하나님의 능력이라” (고린도전서 1:18)\n", color: R, paragraph: 34 }]
→ 3장. 1번과 3번이 글자 그대로 같아도 둘 다 나간다
// 주의: 정답 파일에서는 두 인용이 1번·3번 자리에 있다(문단 34가 40보다 앞). 순서는 paragraph 오름차순

// [7] 153자 — 쪼개지 않는다  (지혜와 명철, 문단 53)
[{ text: "“6 지혜를 버리지 말라 … 그가 너를 영화롭게 하리라” (잠언 4:6~8)\n", color: R, paragraph: 53 }]
→ 한 장. 절 번호 6/7/8이 있어도 쪼개지 않는다

// [8] 연속 공백 — 그대로 내보낸다  (지혜와 명철, 문단 71)
[{ text: "“나는 최고의 선수를 찾는 것이 아니라, …” /  허브 브룩스(Herb Brooks)\n", color: R, paragraph: 71 }]
→ ["“나는 최고의 선수를 찾는 것이 아니라, …” /  허브 브룩스(Herb Brooks)"]
// "/" 뒤 공백 두 칸이 살아 있다

// [9] 미발동 방어 조항 — 실물에 없음. 규칙의 의도를 고정하기 위한 케이스
[{ text: "“자막 본문입니다”", color: R, paragraph: 3 },
 { text: "  ",              color: K, paragraph: 3 }]   // 문단 끝 검은 공백
→ ["“자막 본문입니다”"]                                   // 공백 예외가 없으면 이 자막이 통째로 사라진다

[{ text: "<사진을 띄운다.>\n", color: R, paragraph: 7 }]  // 지시문이 독립 문단인 경우
→ []                                                     // 4번 꺾쇠 규칙이 여기서 발동한다
```

### 이 티켓이 화면 쪽에 남기는 조건

규칙 자체는 **완전 자동**이고 정답 파일을 100% 재현한다. 다만 화면에 두 가지를 요구한다. 상세 설계는 `화면 구성과 조작 흐름과 사람 검수` 몫이다.

- **6번 — 모르는 색 경고.** 검정도 `#FF0000`도 아닌 색을 만나면 알린다
- **걸러낸 것을 보여준다.** 2·4번이 버린 빨간 조각(`<사진을 띄운다.>` 등)을 "빨갛지만 뺐습니다"로 노출한다. 규칙이 틀린 날 담당자가 알아챌 유일한 통로이며, 특히 위에 적은 꺾쇠 필터의 위험을 여기서 흡수한다

### 남은 미확인

- 색 외의 서식(**굵게·형광펜**)이 의미를 갖는지는 여전히 확인되지 않았다. 규칙은 색만 본다
- 4번 꺾쇠 필터와 공백 예외는 **실물 발동 사례가 0건**이다. 실전 운용 중 검증될 것
