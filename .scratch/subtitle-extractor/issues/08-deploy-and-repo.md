# 배포 방식과 저장소 셋업

Type: grilling

## Question

**담당자가 매일 여는 주소는 어디이고, 이 코드는 어디에 사는가.** 정적 배포처와 git
저장소를 정한다.

맵의 안개에 있던 **배포 방식과 저장소 셋업**을 승격시킨다. 승격 조건이 두 번에 걸쳐
채워졌다 — `브라우저에서 hwp/hwpx의 색상 포함 텍스트를 추출할 수 있는가`가 **서버가
아예 필요 없음**을 확인해 정적 배포로 성립함을 확정했고, `확장을 감당할 최소 뼈대 —
라우팅과 모듈 경계`가 저장소에 요구사항 둘을 얹었다(아래).

## 앞선 결정이 이미 그어 놓은 경계

- **서버 없음** — API 라우트도 서버 액션도 없다. 파일 처리는 전부 브라우저 안에서
  일어나고, 설교 원고는 어디로도 올라가지 않는다. `next.config.ts`에 정적 출력 설정이
  아직 없다(`output: 'export'` 미설정)
- **인증 없음** — 사용자 1명. 서버에 저장되는 데이터가 없어 지킬 대상이 없다
- **`fixtures.json`을 커밋하지 않는다** — 07이 정했다. 설교 3편 전문(270KB)이 들어 있고
  gitignore 대상이다. **git 초기화 시점에 이게 이미 처리돼 있어야 한다** — 한 번
  커밋되면 되돌리기 어렵다
- **저장소 공개 여부는 열려 있다** — 07이 이 결정을 묶지 않으려고 원고 커밋을 피했다.
  여기서 정한다
- **`/`는 도구 목록** — 07이 정했다. 방송실 도구가 계속 붙을 것이므로 배포처는 도구
  하나가 아니라 **이 그릇 전체**를 받는다

## 정할 것

- **배포처** — 어디에 올리는가. 정적 산출물이므로 선택지가 넓다(Vercel / Cloudflare
  Pages / GitHub Pages / 교회 내부 서버 등). **담당자가 매일 여는 주소가 무엇이 되는지**가
  실질 판단 기준이다. 도메인을 사는가
- **git 저장소** — 어디에 여는가(GitHub 등), 공개인가 비공개인가. `.gitignore`에 무엇이
  들어가는가. **첫 커밋 전에 `fixtures.json`과 원고 실물이 확실히 제외돼 있는가**
- **배포 트리거** — push하면 자동으로 올라가는가, 손으로 올리는가. 개발자 1명 기준에서
  어느 쪽이 값을 하는가
- **`output: 'export'`를 쓰는가** — 정적 export로 못 박는가, 아니면 배포처가 Next를
  그대로 받는가. 이 선택이 앞으로 붙을 도구들의 선택지를 좁히는지

## 넘지 말 것

맵의 원칙 — **뼈대는 첫 기능이 실제로 요구하는 만큼만.** 스테이징 환경, 프리뷰 배포,
모니터링, 커스텀 CI 파이프라인은 지금 도구 하나와 개발자 1명이 요구하지 않는다.

## 이 티켓 밖

- **구현 자체** — 이 맵은 계획이 기본이다. 저장소를 실제로 열고 배포를 붙이는 것은
  맵이 걷힌 뒤 `/implement`의 몫이다. 다만 **첫 커밋 전에 원고가 제외돼야 한다**는
  제약은 이 티켓이 스펙에 명시적으로 남긴다

## Answer

**`chambitstudio.com`을 사서 Cloudflare Pages에 정적으로 올리고, 코드는 public GitHub
저장소에 산다. `main`에 push하면 자동 배포된다.**

### 0. 전제 확인 — 방송실 PC

배포처를 고르기 전에 **차팅 이후 한 번도 실물로 확인된 적 없던 전제**를 먼저 세웠다.
"인터넷에 배포한다"는 결정이 방송실 환경 위에 서 있는데 맵에 그 환경 얘기가 한 줄도
없었다. 확인 결과 — **작업은 방송실 PC에서 일어나고, Windows에 최신 Edge/Chrome이
깔려 있으며, 설치·접속을 막는 IT 정책이 없다.** hwp 바이너리를 브라우저에서 파싱하는
03·05의 결정이 실물 환경에서 그대로 성립한다. 전제가 섰으므로 이 축은 닫혔다.

### 1. 주소 — `chambitstudio.com`

무료 서브도메인(`*.pages.dev`)을 추천했으나 **도메인 구입으로 결정.** 되돌릴 수 있는
쪽을 버리고 값을 치르기로 한 선택이다.

- **명의·결제** — 개인 명의, 개인 카드. 교회 행정 절차를 지금 밟는 것보다 빠르고,
  나중에 교회로 이전(transfer)할 수 있다
- **갱신 위험은 돈으로 산다** — **자동갱신을 켜고 등록 연수를 최대로 잡는다.** 이 앱은
  매일 예배에 걸려 있어서, 도메인이 조용히 만료되면 담당자가 그날 밤 손으로 자막을
  만들어야 한다. 무료 서브도메인에 없던 새 고장점을 만드는 것이므로 그 값을 선결제로
  치른다. 실제 가능 연수는 결제 화면에서 확인할 값
- **이름 선정** — NS 레코드로 가용성을 훑었다. `chambit.app`/`.com`/`.org`는 등록됨,
  `chambit.studio`/`.church`/`.tools`는 비어 있어 보이고, `chambitstudio.com`과
  `chambit-studio.com`은 whois 상 사용 가능. `chambit.studio`를 추천했으나 `.com`의
  **3배 값**(연 3~4만원대 vs 1만원대, 다년이면 30~40만원 대 10만원)을 하지 않는다고
  보고 `chambitstudio.com`으로. 하이픈이 없어 말로 불러주기 좋다
- **교회 정체성 네임스페이스는 비워 둔다** — `chambit.church`가 가장 예쁘게 읽히지만
  기각했다. 이건 교회 홈페이지가 아니라 **방송부 도구 하나**이고, 언젠가 교회가 그
  이름을 원할 때 개인 명의 도구가 자리를 차지하고 있으면 곤란하다
- 곁가지 — `chambit.org`의 네임서버가 `rootnet.kr`(국내 호스팅)이라 **참빛교회 본체
  도메인일 가능성이 있다.** 지금 결정을 바꾸지는 않지만 나중에 교회로 넘길 때의 참고 사실

### 2. 배포처 — Cloudflare Pages

**이 결정을 가볍게 만든 사실 하나**: 07이 앱 전부를 브라우저 안에 앉혔으므로
`output: 'export'`가 공짜다. 순수 정적 파일 뭉치가 나오고 세 호스트가 전부 똑같이 받는다.
**잠긴 문이 아니라 열린 문**이라 갈아타는 비용이 거의 0이고, 오래 고민할 값이 없었다.

그럼에도 CF Pages를 고른 이유 둘:

- **약관** — Vercel Hobby는 약관상 비상업·개인 용도다. 교회 자원봉사 도구는 수익을
  내지 않으니 비상업이 맞지만 회색지대이고, **매일 예배에 걸린 도구를 약관 해석 위에
  앉히는 값을 하지 않는다.** CF Pages 무료 플랜에는 그 구분이 아예 없다
- **Vercel의 강점이 여기선 안 쓰인다** — "Next를 그대로 받는다"는 이점은 서버가 있을 때
  값을 한다. 정적 산출물에는 해당 없음
- **GitHub Pages는 뺐다** — private 저장소로 쓰려면 유료 플랜이 필요해서 **호스트가
  저장소 공개 여부 결정을 인질로 잡는다.** 나머지 둘은 private이어도 무료

**`output: 'export'`를 쓴다.** 서버가 없으니 어댑터 없이 그대로 성립한다.

### 3. 저장소 — `jacobjiwoo/chambit-studio`, **public**

private을 추천했으나 **public으로 결정.** 결정 전에 `.scratch/` 1,097줄 전체를 훑어
공개해도 새는 게 없음을 확인했다:

- 개인정보·연락처·실명 **0건**
- 로컬 절대경로(`/Users/jiwoo/...`) 유출 **0건** — `~/Downloads/` 형태의 틸드 경로뿐이라
  사용자명이 안 나간다
- `prototypes/` 파이썬 3개는 참조 구현이라 공개 무방

**`.scratch/`는 커밋한다.** CLAUDE.md가 이걸 이 저장소의 이슈 트래커 자체로 정의하므로,
gitignore하면 클론했을 때 맵과 티켓이 통째로 사라진다.

### 4. 이 티켓이 발견한 것 — 07이 막은 구멍 옆의 두 번째 구멍

07은 `fixtures.json`(설교 3편 전문)을 커밋하지 않기로 해서 원고 유출을 막았다. 그런데
파보니 **`04-red-text-rules.md` 안에 설교 원고 문장이 그대로 들어 있다** — 정답 쌍 9개가
`StyledRun` 리터럴로 박혀 있고, 고린도전서 인용·설교 소제목·`<사진을 띄운다.>` 같은
연출 지시문까지 실물에서 뜯어온 것이다.

그리고 **이건 실수가 아니라 필요해서 거기 있다.** 04가 그 9개를 규칙의 정답 쌍으로
못박았고 07이 Vitest를 넣기로 했으니, **그 9개가 곧 유닛 테스트다.** 테스트는 커밋돼야
하므로 원고 조각은 저장소에 들어갈 수밖에 없다.

그래서 07의 "원고는 커밋하지 않는다"를 **두 겹으로 가른다**:

| | 무엇 | 처리 | 근거 |
|---|---|---|---|
| **전문** | `fixtures.json`의 설교 3편 통째 (270KB) | **커밋 안 함** | 목사님의 미공개 저작물. 테스트에 전문이 필요하지도 않다 |
| **조각** | 04의 정답 쌍 9개 (합쳐 몇 줄) | **커밋함** | 없으면 규칙 층에 테스트가 없고, 07이 Vitest를 넣은 이유("8장→7장은 눈으로 못 잡는다")가 무너진다 |

조각을 공개해도 되는 근거: **빨간 텍스트는 정의상 회중 앞 대형 화면에 띄우는 문장이다.**
설교 중 가장 공개적인 부분이므로, 미공개 저작물이라는 우려는 전문에만 해당하고 조각에는
약하게 걸린다.

### 5. 원고 차단 — 스펙에 남기는 강제 제약

08이 "한 번 커밋되면 되돌리기 어렵다"고 썼는데 **public이 되면서 '어렵다'가
'불가능하다'로 바뀌었다.** fork·검색 인덱스·캐시가 남는다. 그래서 gitignore를 믿지 않고
**순서 자체를 안전장치로 쓴다**:

1. **`git init` 전에** 07이 정한 `app/prototype/` 삭제를 **먼저** 수행한다. 그러면
   `fixtures.json`이 애초에 존재하지 않는 상태에서 저장소가 시작된다 — gitignore가
   실패해도 커밋될 파일이 없다. (07의 "`toNabiTxt`와 `variant-f` 화면은 옮긴다"는
   삭제 전에 처리)
2. 그 위에 `.gitignore` 이중 방어: **`*.hwp`, `*.hwpx`, `*-nabi.txt`** 를 추가한다.
   원고 실물이 나중에 실수로 들어오는 경로를 막는다
3. 기존 `create-next-app` 기본 `.gitignore`는 그대로 유지 (`/node_modules`, `/.next/`,
   `/out/`, `*.tsbuildinfo`, `.env*` 등). `/out/`이 이미 있어 export 산출물은 자동 제외

### 6. 배포 트리거 — Git 연동 자동 배포

CF Pages를 GitHub 저장소에 묶고, `main`에 push하면 CF가 빌드·배포한다.

- **손으로 배포(wrangler)를 기각한 이유** — 개발자 1명한테는 "배포를 까먹음"(고쳤는데
  안 올라가 있는 상태가 조용히 며칠 감)이 "실수 커밋"보다 훨씬 자주 일어난다. 실수
  커밋 쪽은 07이 넣은 Vitest가 빌드 앞에 서서 규칙 층 사고를 걸러낸다
- **설정이 한 번이고 그 뒤로 0이다** — 08의 "첫 기능이 요구하는 만큼만"에 맞는다
- **브랜치 프리뷰 URL은 딸려 온다.** 08이 "프리뷰 배포는 요구하지 않는다"고 했지만
  이건 우리가 짓는 게 아니라 자동으로 생기는 것이라 **무시한다** — 없애려고 손대는 게
  오히려 비용이다
- 08의 "넘지 말 것"대로 스테이징·모니터링·커스텀 CI 파이프라인은 만들지 않는다

### 넘기는 것

도메인 결제 화면에서 확인할 값 둘 — **실제 다년 등록 가능 연수**, 그리고 CF Registrar가
`.com` 신규 등록을 받는지(받지 않으면 아무 등록기관에서 사서 CF로 네임서버만 넘긴다).
둘 다 이 티켓의 결정을 바꾸지 않는 실행 세부다.
