# 입력 파일 포맷 정책 — hwpx로 받을 것인가, hwp를 직접 파싱할 것인가

Type: grilling
Status: resolved

## Question

앱이 받아들일 입력 파일 포맷을 무엇으로 할 것인가? 이것이 구현 난이도와 목사님의 작업 방식 양쪽에 걸쳐 있는 결정이라 기술만으로 정할 수 없다.

`브라우저에서 hwp/hwpx의 색상 포함 텍스트를 추출할 수 있는가`가 해소되면서 **세 갈래 모두 기술적으로 가능**하다는 것이 확인됐다. 따라서 이 티켓은 "무엇이 가능한가"가 아니라 **"무엇을 감당할 것인가"**를 묻는다.

### 갈래 A — hwpx 규약

원고를 `.hwpx`로 받는 것을 약속으로 삼는다. 한글에서 `도구 → 환경 설정 → 파일`에서 기본 저장 형식을 바꾸면 이후로는 자동이다.

- 구현이 압도적으로 간단하다 — ZIP 해제(`fflate` 약 8KB) + `DOMParser`면 끝. 바이너리 해석도 압축 해제도 필요 없다
- 색상이 `header.xml`에 `textColor="#RRGGBB"` 평문으로 들어 있다
- 2026년 10월부터 공공기관 hwpx 의무화가 예정돼 있어 시간이 갈수록 유리해진다
- **대가:** 목사님께 설정 변경을 부탁해야 한다. 그분이 쓰는 한글 버전이 hwpx를 지원하는지도 확인이 필요하다. 잊고 hwp로 보내는 날의 대응도 필요하다

### 갈래 B — hwp 직접 파싱 (자체 구현)

지금 그대로 `.hwp`를 받는다. 목사님 쪽 변화가 전혀 없다.

- **알고리즘이 이미 실증됐다** — [`prototypes/extract_red.py`](../prototypes/extract_red.py)가 실제 원고에서 빨간 구간 22개를 뽑아냈다. 브라우저로 옮기려면 OLE2 복합 파일 리더와 raw inflate만 있으면 되고, 우리가 필요한 건 스트림 두 개뿐이라 전체 구현이 필요 없다
- **대가:** 바이너리 파싱 코드를 우리가 짊어진다. 한글 버전이 바뀌어 포맷이 달라지면 우리 문제가 된다

### 갈래 C — hwp를 기존 WASM 라이브러리로

`@rhwp/core`(Rust+WASM, 활발히 유지보수 중)를 쓴다.

- 남이 관리하는 파서를 얻는다
- **대가:** WASM 번들 7.7MB. 색상 조회가 글자 오프셋 단위 API라 run을 다시 조립해야 한다. 조사 문서는 이 경로를 폴백으로만 권했다

## 정할 것

- **어느 갈래로 갈 것인가.** 조사 문서의 권고는 A(주) + C(폴백)이지만, 갈래 B가 이미 실증됐다는 점은 그 조사에 반영되지 않았다
- **목사님께 저장 형식 변경을 부탁하는 것이 현실적인가.** 이것이 A의 성패를 가른다. 기술이 아니라 사람 문제이므로 담당자만 답할 수 있다
- 그분이 쓰는 한글 버전이 무엇인지 확인이 필요한가
- **두 포맷을 다 받을 것인가.** 받는다면 hwp 경로를 v1에 넣을지, "hwpx로 저장해 주세요" 안내로 대체할지
- hwp를 hwpx로 다시 저장했을 때 **빨간색이 그대로 보존되는지** 확인이 필요하다 (미검증)

## 참고

- 조사 전문: [`research/hwp-color-extraction.md`](../research/hwp-color-extraction.md)
- 어느 갈래든 **서버는 필요 없다.** 정적 배포로 성립한다는 점은 확정됐다
- 조사 문서의 설계 권고: 포맷별 파서를 `parseHwpx(file): Promise<StyledRun[]>` 같은 공통 인터페이스 뒤에 두어, 나중에 다른 포맷을 붙일 수 있게 seam을 그을 것

## Answer

**갈래 B — `.hwp` 바이너리를 브라우저에서 직접 파싱한다. v1은 hwp 전용.**

목사님 쪽에도, 담당자 쪽에도 새로운 수작업을 만들지 않는다. 사람의 일과는 그대로 두고 앱이 hwp를 그대로 받는다.

### 조사로 확정된 사실 (원고 3편 실물)

이 티켓이 "확인이 필요하다"고 남겼던 것들이 조사로 해결됐다. 담당자에게 물을 필요가 없었다.

| 항목 | 값 |
|---|---|
| 목사님 한글 버전 | **11.0.0 (한글 2020), Windows 10** — 3편 모두 (빌드 8969 / 9083) |
| hwp 포맷 버전 | **5.1.0.1** — 3편 모두 동일 |
| 플래그 | `압축`만 ON. **암호·배포용·DRM 전부 없음** |
| 문서 내 이미지 | 1~4개씩 (`BinData`) |
| 담당자 Mac | Hancom Office HWP **12.30.0** 설치됨 (hwp/hwpx 양방향) |

`extract_red.py`를 **원고 3편 전부**에 돌려 예외 없이 추출됨을 확인했다 (빨간 구간 10 / 19 / 22개).

### 갈래 A(hwpx 규약)를 접은 이유

한글 2020은 hwpx를 지원하므로 A는 **기술적으로는 열려 있었다.** 접은 이유는 사람 쪽이다 — **담당자가 목사님께 저장 형식 변경을 부탁할 수 있는 상황이 아니다.** 규약이 성립하지 않으면 A는 갈래가 아니다.

파생안이었던 **A′(담당자가 매일 직접 hwpx로 변환)**도 접었다. 이 앱의 존재 이유가 담당자의 반복 작업 제거인데 매일 변환 한 단계를 새로 심는 건 방향이 반대다.

### 갈래 C(`@rhwp/core` WASM)를 접은 이유

- 서버 없는 정적 사이트에 **7.7MB WASM**은 균형이 맞지 않는다.
- C의 유일한 매력처럼 보였던 것 — 글자 단위 색상 API라 `빨간색 판정 규칙과 자막 쪼개는 단위`의 최대 난제인 "인접 구간 병합"이 공짜로 풀린다 — 은 **착시였다.** 아래 "04 티켓에 넘기는 관찰" 참조.

### 갈래 B가 조사 문서의 평가보다 가벼운 이유

조사는 "hwp 바이너리 파싱"을 하나의 큰 덩어리로 봤지만, 실제로 필요한 것은 이만큼이다.

- 스트림 **2개**: `DocInfo`, `BodyText/Section*`
- 레코드 **3종**: 21 `CHAR_SHAPE`(글자색), 67 `PARA_TEXT`(본문), 68 `PARA_CHAR_SHAPE`(위치→모양ID)
- 압축 해제: `inflateRaw` (wbits=-15)
- 의존성: `cfb`(SheetJS, OLE 리더) + `fflate` — 파이썬 80줄이 TypeScript 120줄 남짓

이미지·표 서식·수식·스타일·글머리표는 전부 태그가 달라 **그냥 지나친다.** "HWP 5.0을 구현한다"가 아니라 "레코드 3종을 읽는다"이다.

**B가 오히려 표에 강하다.** hwp 바이너리에서는 표 셀 안의 문단도 같은 `BodyText` 스트림에 `PARA_TEXT` 레코드로 평평하게 들어오므로 레코드를 순서대로 훑기만 하면 저절로 딸려온다. hwpx 경로는 `<hp:tbl>/<hp:tr>/<hp:tc>/<hp:subList>`를 재귀로 내려가야 한다. `Not yet specified`의 "표가 든 원고" 위험에 대해 B가 더 안전한 쪽이다.

**B의 대가 (정직하게).** 바이너리 파싱 코드를 우리가 짊어진다. 감당 가능하다고 본 근거는 셋 — (1) 원고 3편이 모두 `5.1.0.1`이고 이 포맷은 한글 2010부터 안정적, (2) 목사님이 한글 2020에 고정돼 있어 포맷이 바뀌려면 한글을 새로 사야 함, (3) 파서가 깨지는 날의 실제 대응은 **"그날은 손으로 한다"**(= 지금의 방식)이다. 앱이 하루 안 돌아도 예배는 멈추지 않는다.

> 논의 중 "깨지면 담당자가 hwpx로 변환해 올린다"를 비상구로 검토했다가 **기각했다.** 앱이 hwpx를 안 받으면 그 비상구는 존재하지 않고, 설령 넣더라도 **한 번도 돌려본 적 없는 경로**는 주일 아침에 믿을 게 못 된다. 미검증 비상구는 비상구가 아니다.

### hwpx를 v1에서 뺀 이유

- 목사님이 hwpx를 보낼 경로가 **없다**(부탁이 안 되므로). 들어올 일이 없는 포맷이다.
- 검증할 실물이 없다. 보유한 hwpx는 `입법예고(울산광역시 남구 구세 조례…)` 하나뿐이고 설교 원고가 아니라 테스트 케이스가 못 된다.
- 필요해지는 날 그때 개발한다. 아래 경계 덕에 붙이는 비용이 작다.

### 입력 판정 정책 — 3단

**1단 · 이게 hwp인가.** 확장자를 믿지 않고 **내용으로** 판정한다. 셋 다 통과해야 hwp다.

1. OLE 매직 8바이트 `D0 CF 11 E0 A1 B1 1A E1`
2. `FileHeader` 스트림 존재
3. 그 스트림 오프셋 0의 32바이트 시그니처 `HWP Document File`

확장자만 바꾼 파일이나 카톡이 파일명을 뭉갠 경우에도 정확히 갈라진다.

**2단 · 읽을 수 있는 hwp인가.** `FileHeader` 오프셋 36의 플래그 비트를 본다.

| 비트 | 의미 | 처리 |
|---|---|---|
| 0 | 압축 | **거부 아님** — ON이면 `inflateRaw`, OFF면 그대로 읽음 |
| 1 | 암호 설정 | 거부 |
| 2 | 배포용 문서 | 거부 |
| 4 | DRM 보안 | 거부 |

이 셋은 본문이 우리가 읽을 수 없는 형태이므로 파싱을 시도하기 전에 **미리, 명확하게** 갈라낸다.

**3단 · 버전 가드를 두지 않는다.** major가 5면 minor와 무관하게 **일단 시도**하고, 실제로 깨지면 그때 실패를 보고한다. `hwp.js`는 `major==5 && minor<=1`을 강제하고 아니면 `throw`하는데, 조사가 이를 위험으로 짚었다 — 한글이 5.2를 내는 순간 **읽을 수 있는데도** 거부하게 된다. 우리가 읽는 레코드 3종은 5.0 초기부터 바뀌지 않은 것들이라 관대함에 손해가 없다. major 3(한글 97 시절)은 구조가 아예 달라 거부한다.

**빨간 글자 0개는 오류가 아니다.** 파싱 성공 + 결과 0장이며, 성공 / 실패 / 빈 결과 **셋을 구분**해서 다룬다. 문구와 화면은 `화면 구성과 조작 흐름`의 몫이다.

### 모듈 경계 — 긋되, 포맷 추상화는 만들지 않는다

조사 문서는 포맷별 파서를 공통 인터페이스 뒤에 두라고 권했으나, 그건 포맷을 여럿 받는다는 전제의 권고다. **인터페이스도 팩토리도 포맷 레지스트리도 만들지 않는다** — 구현체가 하나뿐인 추상화는 추측이다. 함수 하나면 된다.

```ts
parseHwp(bytes: ArrayBuffer): StyledRun[]
```

hwpx가 필요해지는 날 `parseHwpx`를 짜고 호출부에서 분기한다. 그게 미리 만든 추상화보다 싸고 읽기 쉽다.

**그러나 경계 자체는 실재한다.** "hwp 바이트 → 색 붙은 텍스트 조각 배열"은 포맷이 하나든 셋이든 존재하는 선이며, 긋는 이유는 확장성이 아니라 이 둘이다.

- **위쪽이 hwp를 전혀 모른다.** 자막 규칙·병합·꺾쇠 필터·나비CG 출력 전부가 OLE도 레코드 태그도 몰라도 된다.
- **테스트가 갈라진다.** 파서는 실물 hwp 3편으로, 자막 규칙은 `StyledRun` 배열 리터럴로 hwp 파일 없이 검증한다. 04가 만들 입력→출력 정답 쌍이 **파일이 아니라 데이터**가 되므로 테스트가 빠르고 잘 깨지지 않는다.

경계를 통과하는 데이터는 최소한 **텍스트 / 색(RGB) / 문단 인덱스 / 문단 내 시작 위치**를 담아야 한다. 뒤의 둘은 04의 인접 구간 병합이 "두 조각이 원본에서 붙어 있었는가"를 판단하는 데 필수다. **정확한 필드 이름과 최종 형태는 04가 규칙을 세우며 확정한다** — 이 티켓은 경계의 위치와 반드시 통과해야 할 것까지만 정한다.

### 04 티켓에 넘기는 관찰 — 병합 난제는 파서 층에서 풀린다

`빨간색 판정 규칙과 자막 쪼개는 단위`가 최대 난제로 꼽은 "같은 빨강인데 문자 모양 ID가 달라 구간이 갈라진다"는 **파서가 만든 문제이지 데이터의 한계가 아니다.** 우리는 `charShapeID → 색` 표와 `위치 → charShapeID` 배열을 **둘 다** 쥐고 있으므로, shapeID가 아니라 **색으로 묶으면** 글자 단위 색상을 언제든 계산할 수 있다. `extract_red.py`가 조각을 내는 건 그 참조 구현이 shapeID 단위로 그룹핑하기 때문이다.

즉 갈래 C가 준다던 "글자 단위 색상 API"의 정보를 우리는 이미 상위집합으로 갖고 있다. **어떤 기준으로 묶을지는 04의 결정**이며, 여기서 정하지 않는다.

### 여기서 함께 닫은 것

- **"hwp를 hwpx로 다시 저장하면 빨간색이 보존되는가"** — hwpx를 받지 않기로 했으므로 검증할 이유가 사라졌다. 별도 티켓 없이 닫는다.
- **"목사님 한글 버전 확인이 필요한가"** — 조사로 해결(11.0.0 / 한글 2020). 담당자에게 물을 일이 아니었다.
