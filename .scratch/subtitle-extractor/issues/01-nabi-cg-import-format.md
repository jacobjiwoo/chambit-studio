# 나비CG 임포트 파일 규격 확정

Type: task
Status: resolved

## Question

compix `nabi-cg`가 자막을 임포트할 때 먹는 파일의 **정확한 규격**은 무엇인가?

이 앱의 출력이 곧 나비CG의 입력이므로, 이 규격이 확정되지 않으면 스펙은 완성될 수 없다. 임계 경로에 있다.

교회에 나비CG 매뉴얼/문서가 있다고 확인되었으므로, 조사가 아니라 **확인**으로 해결된다. 매뉴얼에서 임포트 관련 항목을 찾아 아래를 답한다.

**확인할 것**

- 파일 형식과 확장자 — 엑셀(`.xls`/`.xlsx`)인가, CSV인가, 탭 구분 텍스트인가, 자체 포맷인가
- 컬럼(필드) 구조 — 각 열이 무엇을 의미하는가. 자막 본문 외에 필요한 필드(순번, 채널, 템플릿 이름, 표시 시간 등)가 있는가
- 헤더 행이 필요한가, 있다면 정확한 이름은 무엇인가
- 문자 인코딩 — UTF-8인가 EUC-KR/CP949인가. 한글 깨짐과 직결된다
- 한 자막의 **글자 수 제한**과 **줄 수 제한**. 줄바꿈을 어떻게 표현하는가 (셀 안 개행? 별도 컬럼? 특수문자?)
- 임포트 시 제약이나 흔한 실패 원인 (빈 행, 특수문자, 최대 행 수 등)

**결과 기록** — 매뉴얼의 해당 부분과, 가능하면 실제 임포트 파일 예시 한 장을 이 티켓에 첨부하거나 경로를 남긴다. 뒤따르는 티켓들이 이 규격을 그대로 참조한다.

## Answer

**규격은 확정됐다. 그리고 기대 이상이다 — 매뉴얼뿐 아니라 담당자가 실제로 만들어 쓴 임포트 파일 실물을 확보했고, 그 원본 hwp까지 짝으로 갖고 있다.** 규격을 문서로 확인한 데서 그치지 않고 **입력→출력 정답 쌍으로 검증**했다.

### 결론 한 줄

나비CG 임포트 파일은 **엑셀도 CSV도 아니다. 컬럼이 없는 순수 텍스트(`.txt`)이며, 자막 한 장은 빈 줄로 구분한다.**

### 확보한 실물 (저장소에 커밋하지 않음)

| 역할 | 경로 |
|---|---|
| 나비CG 매뉴얼 | `~/Downloads/NABI_2.5.pdf` (154p, NABI-CG V2.5, 2024-05) |
| **실제 임포트 파일** | `~/Downloads/0118-25고전20260531십자가의 도 하나님의 능력-nabi.txt` |
| 그 중간 산출물 | `~/Downloads/0118-25고전20260531십자가의 도 하나님의 능력-텍스트.txt` |
| **짝이 되는 원본 원고** | `~/Downloads/0118-25고전20260531십자가의 도 하나님의 능력.hwp` |

세 번째 원고 `~/Downloads/0401-09잠20260510지혜와 명철을 얻으라.hwp`도 있다(짝 출력은 없음).

### 규격

임포트 경로는 매뉴얼 **3.6.5. 텍스트 파일 「Ctrl+T」** — "텍스트 편집프로그램에서 텍스트파일(*.txt)로 저장한 문서 파일을 읽어 들이거나 (…) 영화 자막이나 노래 가사 자막 등을 작성할 때 유용하게 사용된다."

**파일 형식** — 순수 텍스트 `*.txt`. 엑셀/CSV/자체 바이너리가 아니다.

**컬럼 구조 — 없다.** 순번·채널·템플릿·표시시간 같은 필드가 파일에 들어가지 않는다. 그런 것들은 임포트 시점에 나비CG UI에서 서체·색상·위치·템플릿으로 지정한다(3.6.5, 3.6.5.1). **파일이 나르는 것은 자막 텍스트와 그 순서뿐이다.** 순서는 파일에 등장하는 순서 그대로다.

**헤더 행 — 없다.** 대신 **정렬 제어문자**를 문서 첫 줄에 단독으로 한 번 쓸 수 있다(3.6.5.2).

| 제어문자 | 기능 |
|---|---|
| 빈 줄 | 새 페이지(자막 장 구분) |
| `//` | 새 페이지 |
| `<<` | 왼쪽 정렬 |
| `>>` | 오른쪽 정렬 |
| `<>` | 가운데 정렬 |
| `&&` | 영화자막 정렬(긴 문장 중앙정렬 기준 왼쪽정렬) |

실제 파일은 정렬 제어문자를 **쓰지 않았다.** 정렬은 나비CG 쪽 Text Attribute 설정에 맡기고 있다.

**자막 장 구분 — 빈 줄.** 매뉴얼 3.6.5.1 "①. 페이지 넘김 설정 → **빈 줄** : 불러온 텍스트 상의 빈 줄을 기준으로 다음 페이지로 넘김". 실물 파일이 정확히 이 방식이다.

**줄바꿈 표현** — 빈 줄이 페이지를 가르므로, **연속된 비어있지 않은 줄들은 같은 자막 장의 여러 줄**이 된다. 즉 여러 줄짜리 자막이 표현 가능하다. 실물 파일은 전부 한 줄짜리 자막이었다.

**인코딩 — UTF-8 with BOM, CRLF 개행, 파일 끝 개행 없음.** 매뉴얼은 인코딩을 명시하지 않는다. 이 값은 실물 파일의 바이트를 직접 검사해 확정한 것이다.

```
BOM: EF BB BF (있음)     개행: CRLF 14개, bare LF 0개     끝: 개행 없이 텍스트로 끝남
```

주의 — 중간 산출물 `-텍스트.txt`는 **BOM 없음 + LF + 빈 줄 없음**이었다. 즉 담당자는 그 파일을 그대로 넣지 않고 **빈 줄을 끼우고 BOM+CRLF로 바꾸는 변환을 거친다.** 우리 앱이 대신해야 할 일이 정확히 이 변환이다.

**글자 수·줄 수 제한 — 문서화된 상한이 없다.** 매뉴얼 전체를 뒤져도 임포트 텍스트의 글자수/줄수 제한 규정이 없다. 제한은 **숫자가 아니라 기하학**이다 — 담당자가 잡아둔 텍스트 영역의 크기가 실질적 한계이고, 넘칠 때의 동작은 **Word Wrap 옵션**(3.7.6.3.4)이 정한다.

> Word Wrap 켬: 지정 영역을 넘어가면 음절이 아닌 **단어 단위**로 다음 줄로 내려가고, 한 페이지에 다 안 들어가면 **다음 페이지로 넘어간다**.
> Word Wrap 끔: 파일 길이를 무시하고 불러와 작업창을 벗어나 정렬된다.

**실물이 말해주는 것: 91자 자막이 쪼개지지 않고 그대로 실전에 나갔다.** 담당자가 만들어 실제 예배에 쓴 파일에서 가장 긴 자막이 91자였고 손대지 않았다. 나비CG가 알아서 흘려보낸다는 뜻이며, **우리가 길이로 자막을 쪼갤 근거가 약해진다.** 이 판단은 `빨간색 판정 규칙과 자막 쪼개는 단위`가 최종 결정한다.

**제약과 실패 원인**

- **`//` 옵션이 전역 설정이다** (3.7.6.3.5 `Use "//" as Page delimiter when Importing Text`). 체크하면 `//`가 구분자가 되고 **빈 줄은 더 이상 페이지를 가르지 않는다.** 교회 PC는 실물 파일이 빈 줄 방식으로 동작했으므로 **옵션이 꺼져 있다**고 볼 수 있다. 우리는 빈 줄 방식으로 출력한다
- 자막 본문이 우연히 `//`, `<<`, `>>`, `<>`, `&&`와 정확히 일치하는 한 줄이 되면 제어문자로 먹힌다. 설교 자막에서 현실적 위험은 낮지만 이스케이프 수단이 없다는 점은 알아둘 것
- 조각그림이 있는 페이지에서 텍스트를 불러오면 불러들인 **모든 페이지에 같은 조각그림이 복사**된다(3.6.5)
- 서체·위치·템플릿은 파일에 없다. 임포트 전에 나비CG에서 먼저 설정해야 한다

### 입력→출력 정답 쌍 검증 (예상 밖의 수확)

원본 hwp에 [`prototypes/extract_red.py`](../prototypes/extract_red.py)를 돌려 담당자의 실제 출력과 대조했다.

추출된 빨간 구간 **10개**, 담당자 최종 파일 **8개**. 순서와 문구가 **완전히 일치**했고, 차이는 딱 하나였다.

> **담당자가 버린 것: `<사진을 띄운다.>` 2개** (추출 결과의 1번, 7번)

빨간색이지만 자막이 아니라 **담당자 자신에게 남긴 연출 지시문**이다. 꺾쇠 `<...>`로 감싸여 있다. **빨강 = 자막이 아니다**라는 반례가 실물로 확인된 것이며, 이 필터 규칙은 `빨간색 판정 규칙과 자막 쪼개는 단위`가 반드시 다뤄야 한다.

또 하나 — **1번과 3번 자막이 글자 그대로 동일하다**(고린도전서 1:18 인용이 두 번). 설교 흐름상 같은 구절을 두 번 띄우는 것이므로 **중복 제거를 하면 안 된다.**

그리고 이 원고는 `설교 원고 실물 확보 및 파일 포맷 판별`의 원고와 달리 **구간 쪼개짐이 전혀 없었다**(10구간이 모두 온전한 문장). 원고마다 편차가 있다는 뜻이다.

### 남은 미확인

- 교회 PC의 Word Wrap 옵션 상태와 담당자가 쓰는 텍스트 영역의 실제 크기. 91자가 통과한 실적이 있으므로 급하지 않다
- 매뉴얼은 V2.5 기준이다. 교회가 쓰는 버전이 이것인지는 확인하지 않았다. 텍스트 임포트는 기본 기능이라 버전 간 차이 위험은 낮다
