# 설교 자막 추출기

> **맵이 걷혔고 스펙이 나왔다 → [`spec.md`](spec.md)** (`ready-for-agent`).
> 스펙이 구현 티켓 9개로 쪼개졌다 → [`build/`](build/). 다음은 `/implement`.

## Destination

참빛교회 방송부 담당자가 **설교 스크립트 파일(hwp/hwpx)을 올리면 빨간 텍스트만 자막으로 추출되어 나비CG 임포트 파일로 떨어지는** 흐름을, 매일 예배 준비에 실전 투입할 수 있는 수준으로 짓기 위한 **구현 가능한 스펙**.

이 앱은 앞으로 방송부 자동화 도구가 계속 추가될 그릇이므로 **그 확장을 감당할 최소 뼈대 결정**까지 포함한다. 단 뼈대는 첫 기능이 실제로 요구하는 만큼만 — 미래 기능을 위한 선제적 설계는 하지 않는다.

## Notes

**도메인** — 참빛교회 방송부. 매일 예배를 방송하며, 자막·CG 송출은 compix `nabi-cg`가 담당한다. 목사님의 설교 스크립트가 한글 파일로 넘어오면, 담당자가 그 안의 **빨간색 텍스트만** 골라 자막으로 만들어 나비CG에 넣는 작업을 매일 반복한다. 이 앱이 없애려는 고통이 정확히 그 반복 작업이다.

**경계** — 이 앱은 **방송 전 준비 단계까지만** 담당한다. 나비CG를 대체하지 않으며, 방송 중 실시간 자막 조작은 나비CG 몫이다. 앱의 출력은 나비CG가 임포트하는 파일이고, 거기서 앱의 역할은 끝난다.

**차팅 단계에서 확정된 결정**
- 출력은 나비CG가 임포트하는 파일 — **규격 확정됨**: 컬럼 없는 순수 `.txt`, 자막 장은 빈 줄로 구분 (`나비CG 임포트 파일 규격 확정`)
- 인터넷에 배포하되 **파일 처리는 브라우저 안에서만** 한다. 설교 원고가 서버로 올라가지 않으므로 원고 민감성 문제가 발생하지 않는다
- **인증 없음**, 사용자 1명(방송부 자막 담당자)으로 시작. 로그인은 내부 문서가 붙는 시점에 재검토
- 나비CG 매뉴얼이 교회에 존재한다 → 규격은 조사가 아니라 확인으로 해결 가능

**기술 스택** — Next.js 16.2 App Router, React 19.2, Tailwind v4, TypeScript strict, pnpm. 현재 `create-next-app` 스캐폴드 상태이며 git 저장소는 아직 초기화되지 않았다.

**최대 위험 — 해소됨.** 차팅 당시 이 맵을 죽일 수 있다고 본 위험은 "브라우저에서 hwp 색상을 못 뽑으면 어쩌나"였다. 실물 파싱 실증과 기술 조사로 **양쪽 다 가능**하다는 것이 확인됐고, "브라우저에서만 처리" 결정은 유지된다. **서버가 아예 필요 없어 정적 배포로 성립한다.** 뒤이어 `입력 파일 포맷 정책`이 **입력을 `.hwp` 하나로 확정**하면서 이 축의 선택도 끝났고, `빨간색 판정 규칙과 자막 쪼개는 단위`가 **담당자 실물 파일과 바이트 단위로 일치하는 규칙**을 확정하면서 마지막 무게도 내려놨다. **입력·규칙·출력 세 끝단이 전부 확정됐다.** 그 사이에 사람이 어떻게 서느냐도 `화면 구성과 조작 흐름`이 **읽기 전용 2단 화면**으로 닫았다. **이제 무엇을 만들지는 다 정해졌고, 남은 것은 어디에 어떻게 앉히느냐다** — 뼈대와 배포 둘이었는데, `확장을 감당할 최소 뼈대 — 라우팅과 모듈 경계`가 **뼈대를 도구 폴더 하나로** 닫고, 마지막으로 `배포 방식과 저장소 셋업`이 **주소·호스트·저장소·트리거를 전부** 닫았다. **맵이 걷혔다 — 열린 티켓이 없다.**

**세션 운영** — 매 세션 `/grilling`과 `/domain-modeling`을 참조한다. 기술 조사는 `/research` 서브에이전트로. 이 맵은 **계획이 기본**이며 구현하지 않는다. 맵이 걷히면 `/to-spec` → `/to-tickets` → `/implement`로 넘긴다.

## Decisions so far

- [설교 원고 실물 확보 및 파일 포맷 판별](issues/02-sermon-script-sample.md) — 원고는 구형 `hwp`(HWP 5.0, 암호·DRM 없음). 빨간색은 정확히 `#FF0000` 하나이며, 실제 원고에서 빨간 구간 22개 추출에 성공해 **색상 추출 가능성이 실증**됨. 참조 구현은 [`prototypes/extract_red.py`](prototypes/extract_red.py)
- [브라우저에서 hwp/hwpx의 색상 포함 텍스트를 추출할 수 있는가](issues/03-hwp-color-extraction-research.md) — **브라우저에서 가능하며 서버가 필요 없다**(정적 배포로 성립). hwpx는 ZIP+XML이라 매우 간단하고, hwp 바이너리도 자체 구현 또는 `@rhwp/core`(WASM 7.7MB)로 가능. 어느 경로를 택할지는 `입력 파일 포맷 정책`으로 넘김
- [입력 파일 포맷 정책](issues/05-input-format-policy.md) — **갈래 B: `.hwp` 바이너리를 브라우저에서 직접 파싱, v1은 hwp 전용.** 목사님께 hwpx 저장을 부탁할 수 없는 상황이라 hwpx 규약이 성립하지 않고, 담당자가 매일 변환하는 것도 이 앱의 목적과 반대다. 조사로 확정: 목사님은 **한글 2020(11.0.0) / Windows 10**, 원고 3편 모두 **HWP 5.1.0.1**, 암호·배포용·DRM 없음. 필요한 건 스트림 2개·레코드 3종뿐이라 구현이 얇고, 표 셀 텍스트가 저절로 딸려와 hwpx보다 오히려 안전하다. 판정은 확장자가 아닌 **내용 3단**(OLE 매직 → `HWP Document File` 시그니처 → 플래그), **버전 가드는 두지 않는다.** 경계는 `parseHwp(bytes) => StyledRun[]` **함수 하나**로 긋고 포맷 추상화는 만들지 않는다
- [빨간색 판정 규칙과 자막 쪼개는 단위](issues/04-red-text-rules.md) — **문단이 자막의 단위다.** 최대 난제였던 "인접 구간 병합"은 병합 규칙을 발명할 문제가 아니라 경계를 어디에 그을지의 문제였고, 쪼개진 조각은 **예외 없이 같은 문단 안에서만** 갈라진다. 규칙 여섯 줄 — 빨강은 `#FF0000` 정확히 / **문단의 모든 조각이 빨강이면 그 문단이 자막 한 장** / 날것으로 이어붙이고 앞뒤만 trim / `<...>`만인 것은 버림 / **쪼개지도 dedupe하지도 않고 등장 순서 그대로** / 모르는 색은 화면에 경고. 담당자 실물 파일과 **바이트 단위 완전 일치**(10구간 → 8장). 검은 글 속에 낀 빨간 조각이 문단째 탈락하면서 연출 지시문이 구조만으로 걸러진다. `StyledRun`은 **`{text, color, paragraph}` 셋**으로 확정(05가 요구한 "문단 내 시작 위치"는 문단 경계로 묶으면서 불필요해져 뺌). 참조 구현 [`prototypes/subtitle_rules.py`](prototypes/subtitle_rules.py), 입력→출력 정답 쌍 9개는 티켓 안에 `StyledRun` 리터럴로
- [화면 구성과 조작 흐름 — 사람 검수를 포함해서](issues/06-screen-and-review.md) — **한 화면, 2단, 읽기 전용.** 갈래 여섯을 세워 F로 확정. 최대 난제였던 "사람이 손댈 수 있는가"는 **편집 없음**으로 닫혔고(편집 갈래를 실제로 만들어 나란히 놓고 기각), 막았을 때의 위험은 **편집 대신 노출로** 갚는다 — 고칠 일은 원고를 고쳐 다시 올리므로 **원고와 자막이 영원히 한 몸**으로 남는다. 화면은 얇은 헤더(받기·미리보기) + **칩 한 줄**(걸러낸 것·모르는 색, 할 말 있는 날에만) + 2단(원고 전문 | 자막 장). 04의 노출 의무 둘은 **"원고에서 보기 →"로 원고의 그 자리로 데려가는** 동선으로 통일. 첫 화면은 라우트를 나누지 않고 **같은 자리에서 드롭존 → 결과**로 바뀌며, 받기 전 **원문 미리보기** 모달이 있다. 만들며 확인된 것 둘 — 꺾쇠 필터는 원고 3편에서 **정말 0건**이고, 모르는 색이 **자막 한 장을 실제로 삼키는 것**(8장→7장)을 눈으로 봤다. 프로토타입 [`app/prototype/subtitle-screen/`](../../app/prototype/subtitle-screen/)
- [나비CG 임포트 파일 규격 확정](issues/01-nabi-cg-import-format.md) — **엑셀도 CSV도 아닌 컬럼 없는 순수 `.txt`**. UTF-8 with BOM + CRLF, **자막 한 장 = 빈 줄로 구분**, 헤더·순번·시간 필드 없음, 문서화된 글자수 제한 없음. 매뉴얼(`~/Downloads/NABI_2.5.pdf`) 확인에 더해 **담당자가 실전에 쓴 임포트 파일과 그 원본 hwp 짝을 확보**해 입력→출력 정답 쌍으로 검증했다. 부수 수확 둘: 빨간 `<사진을 띄운다.>`를 담당자가 **버렸고**(빨강≠자막), 동일 자막이 두 번 나가므로 **중복 제거 금지**

- [확장을 감당할 최소 뼈대 — 라우팅과 모듈 경계](issues/07-minimal-skeleton.md) — **뼈대는 도구 폴더 하나다.** 자막 추출기의 전부가 `app/subtitle-extractor/`(+ `_lib/`, `_components/`)에 앉고 **그 밖에 새로 그은 경계는 없다** — 공용 디렉터리도, 포맷 추상화도, 상태 계층도, `src/`도, Out of scope 항목을 위한 빈자리도 없다. 라우팅만 예외로 `/` = 도구 목록: 방송실 다음 도구가 **가정이 아니라 예정**임이 확정돼 목록이 현재 요구가 됐다. 상태는 `page.tsx`의 `useState` 하나(읽기 전용 화면이라 상태를 바꾸는 경로가 하나뿐), 컴포넌트 자름은 06의 것 그대로. **Vitest를 지금 넣는다** — 규칙 층 회귀는 화면에 티가 안 나므로(8장→7장) 눈으로 못 잡는다. 작업 중 드러난 것 하나 — 프로토타입 `fixtures.json`에 **설교 3편 전문이 들어 있고 저장소는 아직 git 초기화 전**이라, **원고는 커밋하지 않고**(gitignore, 대조 테스트는 없으면 skip) 저장소 공개 여부 결정을 묶지 않는다. `app/prototype/`은 배포에 노출되므로 삭제하되 `toNabiTxt`와 `variant-f` 화면은 **옮긴다** — 사람이 확인해 확정한 것을 다시 타이핑하면 확인된 것이 미확인으로 되돌아간다

- [배포 방식과 저장소 셋업](issues/08-deploy-and-repo.md) — **`chambitstudio.com` → Cloudflare Pages, public 저장소, push하면 자동 배포.** 먼저 미확인 전제부터 세웠다 — 방송실 PC는 **Windows에 최신 Edge/Chrome, 정책 없음**이라 브라우저 파싱 결정이 실물에서 성립한다. 도메인은 개인 명의로 사되 **자동갱신 + 다년 등록**으로 갱신 위험을 선결제한다(매일 예배에 걸린 도구라 조용한 만료가 곧 사고). `.studio`는 `.com`의 3배 값을 안 해서 기각, `chambit.church`는 **교회 정체성 네임스페이스를 방송부 도구가 차지하지 않으려고** 기각. 호스트는 07이 앱을 전부 브라우저에 앉힌 덕에 `output: 'export'`가 공짜여서 **열린 문** — 그중 CF Pages를 고른 건 Vercel Hobby의 **비상업 조항 회색지대**를 피하려고. 트리거는 자동 배포("배포를 까먹음"이 "실수 커밋"보다 잦고, Vitest가 빌드 앞에 선다). **이 티켓이 발견한 것 — 07이 막은 구멍 옆에 두 번째 구멍이 있었다**: 04의 정답 쌍 9개에 원고 문장이 박혀 있고 그게 곧 유닛 테스트라 커밋될 수밖에 없다. 그래서 원고를 **전문(커밋 안 함) / 조각(커밋함)** 두 겹으로 가른다 — 빨간 텍스트는 정의상 회중 앞 화면에 띄우는 문장이라 조각은 공개돼도 무방. public이 되면서 원고 유출이 "되돌리기 어렵다"에서 **"불가능하다"**로 바뀌었으므로, gitignore를 믿지 않고 **`git init` 전에 `app/prototype/`을 먼저 삭제**하는 순서 자체를 안전장치로 쓴다(+ `*.hwp`/`*.hwpx`/`*-nabi.txt` 이중 방어)

## Not yet specified

- **원고 형식의 일관성** — 원고 **3편 전부**가 예외 없이 처리됨을 확인했고(빨간 구간 10/19/22개 → 자막 8/16/19장), 셋 다 **한글 2020이 만든 HWP 5.1.0.1**이었다. "항상 hwp로 오는가"와 "표가 든 원고" 위험은 `입력 파일 포맷 정책`에서 상당 부분 걷혔고, **"쪼개짐 양상이 원고마다 다르다"는 미확인도 `빨간색 판정 규칙과 자막 쪼개는 단위`가 문단 경계로 흡수해 사라졌다** — 조각이 몇 개로 나든 문단이 같으면 한 장이다. **남은 미확인은 하나** — 색 외의 서식(굵게·형광펜)이 의미를 갖는지. 그리고 04가 넣은 방어 조항 둘(꺾쇠 필터, 공백 예외)은 **실물 발동 사례가 0건**이라 실전 운용 중에만 검증된다.
- **방송실 PC 환경** — `배포 방식과 저장소 셋업`이 걷었다. Windows·최신 Edge/Chrome·정책 없음이 확인돼 브라우저 파싱 전제가 실물에서 섰다.

(배포 방식과 저장소 셋업은 티켓으로 승격돼 이 안개를 떠났고, 이제 resolved다. **남은 안개는 전부 실전 운용 중에만 걷히는 것들이라 티켓으로 승격되지 않는다** — 이 맵의 목적지인 "구현 가능한 스펙"을 막는 결정이 하나도 남지 않았다.)

## Out of scope

- **찬양 가사·성경 구절·광고 자막** — 설교 자막과 입력 경로가 완전히 달라 별도 설계가 필요하다. 첫 도구가 실전에서 돌아간 뒤 별도 effort로.
- **화면 자료(CG·이미지) 제작** — 텍스트 자막이 아닌 그래픽 제작은 성격이 다른 문제.
- **인수인계 관리·FAQ·나비CG 사용법 문서** — 방송부 플랫폼에 언젠가 붙을 기능이지만, 읽고 쓰는 콘텐츠라 자막 추출기와 성질이 다르다. 이 맵의 목적지 밖.
- **방송 중 실시간 자막 조작** — 나비CG의 역할이며 이 앱이 침범하지 않는다.
- **로그인·계정 관리** — 사용자 1명, 서버에 저장되는 데이터 없음. 지킬 대상이 없어 지금은 불필요.
- **hwpx 입력 지원** — `입력 파일 포맷 정책`에서 v1 밖으로 밀어냈다. 목사님께 hwpx 저장을 부탁할 수 없어 **들어올 경로 자체가 없는** 포맷이고, 검증할 실물 설교 원고도 없다. `parseHwp` 경계 덕에 나중에 붙이는 비용이 작으므로, 필요해지는 날 별도로 개발한다.
- **hwp→hwpx 변환 시 빨간색 보존 검증** — hwpx를 받지 않기로 하면서 검증할 이유가 사라졌다. `입력 파일 포맷 정책`이 티켓을 파지 않고 함께 닫았다.
