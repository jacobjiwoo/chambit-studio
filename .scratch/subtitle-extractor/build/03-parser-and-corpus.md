# 03 — 파서 층 + 전 파이프라인 바이트 대조

**What to build:** `.hwp` 바이트가 들어가면 나비CG 임포트 파일 바이트가 나온다. 담당자가 실제로
만들어 예배에 쓴 파일과 **바이트 단위로 일치**한다. 화면은 아직 없지만 파이프라인 전부가
여기서 성립하고, 그 사실이 테스트로 증명된다.

**Blocked by:** 02 — Vitest + 규칙 층 (파서의 출력을 태울 규칙 층이 있어야 파이프라인이 닫힌다).

**Status:** resolved — 커밋 `fcf0630`

## 파서 층

`parseHwp(bytes) => StyledRun[]` **함수 하나**다. 포맷 추상화(인터페이스·팩토리·레지스트리)를
만들지 않는다 — 구현체가 하나뿐인 추상화는 추측이다. v1은 `.hwp` 전용이며 `.hwpx`는 받지 않는다.

부품 둘로 성립한다 — OLE2 복합 파일 리더(`cfb`)와 raw inflate(`fflate`, wbits=-15). 참조 구현이
파이썬 131줄이므로 TypeScript로 120줄 남짓이다. `@rhwp/core`(WASM 7.7MB)는 정적 사이트에 균형이
맞지 않아 쓰지 않는다. 참조 구현은 `.scratch/subtitle-extractor/prototypes/extract_red.py`.

### 입력 판정 3단 — 확장자를 믿지 않고 내용으로 한다

1단 — 이게 hwp인가. 셋 다 통과해야 한다.

| # | 검사 |
|---|---|
| 1 | OLE 매직 8바이트 `D0 CF 11 E0 A1 B1 1A E1` |
| 2 | `FileHeader` 스트림 존재 |
| 3 | 그 스트림 오프셋 0의 32바이트 시그니처 `HWP Document File` |

2단 — 읽을 수 있는 hwp인가. `FileHeader` 오프셋 36의 플래그 비트를 본다.

| 비트 | 의미 | 처리 |
|---|---|---|
| 0 | 압축 | **거부 아님** — ON이면 raw inflate, OFF면 그대로 읽음 |
| 1 | 암호 설정 | 거부 |
| 2 | 배포용 문서 | 거부 |
| 4 | DRM 보안 | 거부 |

3단 — **버전 가드를 두지 않는다.** major가 5면 minor와 무관하게 일단 시도하고, 실제로 깨지면
그때 실패를 보고한다. major 3(한글 97)은 구조가 아예 달라 거부한다.

### 읽는 것은 스트림 2개, 레코드 3종뿐

| 스트림 | 레코드 | 쓰임 |
|---|---|---|
| `DocInfo` | 21 `CHAR_SHAPE` | offset 52의 COLORREF(`0x00BBGGRR`) → `#RRGGBB` |
| `BodyText/Section*` | 67 `PARA_TEXT` | UTF-16LE 본문 |
| `BodyText/Section*` | 68 `PARA_CHAR_SHAPE` | (문자위치, charShapeID) 쌍의 배열 |

레코드 헤더 4바이트 = tagID(10bit) | level(10bit) | size(12bit), size가 `0xFFF`면 다음 4바이트가
실제 크기. 이미지·표 서식·수식·스타일·글머리표는 태그가 달라 그냥 지나친다. 표 셀 안의 문단도
같은 `BodyText` 스트림에 `PARA_TEXT`로 평평하게 들어오므로 순서대로 훑기만 하면 딸려온다.

**제어문자가 위치 계산에 포함된다** — extended/inline 제어문자는 8 WCHAR, 나머지는 1 WCHAR다.
이걸 틀리면 색 경계가 어긋난다. 섹션이 여럿이면 이름 순으로 이어 읽고 `paragraph`는 문서 전체를
통틀어 단조 증가한다.

**`text`를 파서가 손대지 않는다** — trim도 정규화도 없다. 조각별 trim은 `… 우리일까보냐 ` +
`그러나 우리가 …`를 붙여버린다.

### 결과 셋을 구분해 반환한다

성공 / 실패(거부 사유별: 암호 · 배포용 · DRM · hwp 아님 · 파싱 깨짐) / **빈 결과**. 빨간 글자
0개는 오류가 아니다 — 파싱은 성공했고 자막이 0장인 것이다. 08이 이 구분을 그대로 화면에 쓴다.

## 대조 테스트 — 원고가 있을 때만 돈다

gitignore된 로컬 fixture 폴더에서 `.hwp` 원본을 직접 읽어 **파일이 들어가고 파일이 나오는**
가장 높은 seam을 검증한다.

| 원고 | 검증 |
|---|---|
| 십자가의 도 하나님의 능력 (+ 담당자 정답 `-nabi.txt`) | **바이트 완전 일치** |
| 지혜와 명철을 얻으라 | 자막 16장 |
| 복음을 위하여 | 자막 19장 |

**바이트 일치가 이 프로젝트에서 가장 값진 테스트다.** BOM·CRLF·빈 줄 구분까지 포함해 담당자가
실제로 예배에 쓴 파일과 같다는 뜻이며, 규칙이 여전히 **사람의 판단을 재현하는지**를 본다.

**파서 전용 테스트는 두지 않는다** — 기대값 자체가 원고 조각이라 커밋 범위가 늘어난다. 가장
높은 seam이 파서를 덮는다.

- [x] `cfb`와 `fflate`가 의존성에 추가돼 있다
- [x] `parseHwp(bytes) => StyledRun[]`이 있고, 그 밖의 포맷 추상화는 만들지 않았다
- [x] 입력 판정 3단이 확장자가 아닌 내용으로 이뤄지고, 거부는 **사유별로** 구분돼 나온다
- [x] 압축 플래그 ON/OFF 양쪽을 읽는다
- [x] 제어문자 폭(8 WCHAR / 1 WCHAR)이 반영돼 색 경계가 어긋나지 않는다
- [x] 섹션이 여럿이어도 `paragraph`가 문서 전체를 통틀어 단조 증가한다
- [x] 빨간 글자 0개가 실패가 아니라 **빈 결과**로 구분돼 나온다
- [x] `corpus.test.ts`가 담당자 정답 파일과 **바이트 완전 일치**를 확인한다
- [x] 나머지 원고 2편에서 자막 16장 · 19장이 나온다
- [x] 로컬 원고가 없으면 **실패가 아니라 skip**이다 (`describe.skip`)

## 남긴 것

**결과 셋의 자리.** `parseHwp`는 `{ ok: true, runs } | { ok: false, reason }`을 반환한다.
빈 결과를 사유로 만들지 않고 **성공 안에 두었다** — 빨간 글자 0개는 파서가 알 수 있는 것이
아니라 규칙 층을 태워야 나오는 사실이고(파서는 색을 셀 뿐 빨강을 모른다), 성공 안에 두면
타입만 봐도 실패와 헷갈릴 수 없다. 08이 `reason`으로 안내 문구를 고르고, `subtitles.length`
0으로 빈 결과 화면을 고른다.

**거부 사유 하나를 합쳤다.** 매직 8바이트는 맞는데 OLE 컨테이너가 열리지 않는 경우를
`broken`이 아니라 `not-hwp`로 보냈다. `FileHeader`를 볼 방법조차 없으면 1단(이게 hwp인가)을
통과한 적이 없기 때문이다. major가 5가 아닌 경우도 같은 이유로 `not-hwp`다.

**참조 구현과 두 군데 다르다.**

- `CHAR_SHAPE` 레코드가 56바이트보다 짧으면 참조는 건너뛰는데, 여기서는 검정을 대신 넣는다.
  배열 인덱스가 곧 charShapeID라 하나만 빠져도 그 뒤의 색이 전부 한 칸씩 밀린다.
- 섹션 정렬이 이름 순(참조)이 아니라 뒤의 **숫자 순**이다. 이름 순은 `Section10`을
  `Section2`보다 앞세운다.

원고 3편에 짧은 레코드가 없고 섹션도 전부 하나뿐이라, 두 차이가 실물에서 드러난 적은 없다.

**깨진 파일이 빈 결과로 새지 않게 막았다.** 버전 가드를 뺀 대가로 "실제로 깨지면 그때 보고"가
유일한 안전망인데, 레코드 순회가 스트림 밖을 가리키는 크기를 만나면 조용히 멈추는 첫 구현은
반쯤 읽은 원고를 성공으로 내보냈다. 08이 그것을 "자막 0장"이라 안내하면 담당자가 색 표시를
의심하며 원고를 뒤진다. 지금은 던지고 `broken`이 된다. `BodyText/Section*`이 아예 없는 경우도
같다.

**커밋하지 않은 확인.** corpus가 덮지 못하는 경로를 원고를 손으로 변조해 태워봤다 —
거부 4종(hwp 아님 · 암호 · 배포용 · DRM) · 압축 OFF · 버전 5.9.9.9 관대함 · 버전 3.0 거부 ·
빨간 글자 0개 · 잘린 섹션 · `BodyText` 없음 · `DocInfo` 훼손. **섹션 2개**(`Section0`를
복제해 붙인 사본)에서 자막 8장→16장, 마지막 문단 113→227로 문단 번호가 이어지는 것도 확인했다.
티켓이 "파서 전용 테스트는 두지 않는다"고 정했으므로 그 스크립트는 저장소에 남기지 않았다.

**따라서 이 경로들은 지금 어떤 테스트도 지키지 않는다.** 원고 3편이 전부 압축 ON · 섹션 1개
· 정상 파일이라 corpus로는 닿지 않는다. 회귀가 조용할 자리이고, 08이 거부 화면을 세울 때
합성 바이트로 이 자리를 덮는 것을 다시 볼 만하다.
