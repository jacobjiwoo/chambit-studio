# 02 — Vitest + 규칙 층

**What to build:** `StyledRun[]`을 넣으면 자막 장 · 걸러낸 것 · 모르는 색 셋이 나온다. hwp
파일 없이 어디서나 `pnpm test`로 검증된다.

규칙 층을 먼저 세우는 이유는 그 위가 데이터만 갈아 끼우면 되기 때문이고, 테스트가 값을 하는
이유는 이 층의 회귀가 **조용하기** 때문이다 — 자막이 8장이어야 하는데 7장이 나와도 화면은
멀쩡해 보인다.

**Blocked by:** 01 — 프로토타입 이식 · 삭제 · `git init` (저장소가 안전해지기 전에는 아무것도
커밋하지 않는다. 이 티켓의 테스트 파일에는 원고 조각이 박힌다).

**Status:** ready-for-agent

## 경계

```ts
type StyledRun = {
  text: string;       // 원고 그대로. trim·정규화 없음 (앞뒤 공백이 병합에 필요하다)
  color: string;      // "#RRGGBB" 대문자 6자리
  paragraph: number;  // 0부터. 문서 전체를 통틀어 단조 증가
};
// 문서 등장 순서대로 담긴다
```

이 층은 hwp를 전혀 모른다. OLE도 레코드 태그도 zlib도 여기 없다.

## 규칙 여섯 줄

```
1. 빨강 = #FF0000 정확히 일치. 그 외의 색은 자막이 아니다
2. 한 문단의 (공백만인 조각을 뺀) 모든 조각이 빨강이면 → 그 문단이 자막 한 장
3. 그 문단의 조각을 전부 순서대로 이어붙이고, 앞뒤 공백만 자른다. 안쪽은 원고 그대로
4. 남은 것 중 <...>로만 이루어진 자막은 버린다
5. 쪼개지 않는다. 중복을 제거하지 않는다. 원고 등장 순서가 곧 자막 순서다
6. 검정도 #FF0000도 아닌 색이 원고에 있으면 화면에 알린다 (자막으로는 쓰지 않는다)
```

구현에서 놓치면 안 되는 것 셋 — **조각별로 strip한 뒤 join하면 안 된다**(날것으로 concat한 뒤
전체를 한 번만 strip), **2번의 공백 예외는 자막을 잃지 않는 방향으로만 작동한다**(없으면 문단
끝의 검은 공백 하나에 자막이 통째로 사라진다), **길이로 쪼개지 않는다**(153자도 한 장).

참조 구현은 `.scratch/subtitle-extractor/prototypes/subtitle_rules.py`다. `to_subtitles()`가
뱉는 셋이 이 층의 출력과 같아야 한다.

## 테스트

`빨간색 판정 규칙과 자막 쪼개는 단위`(`issues/04-red-text-rules.md`)가 확정한 **입력→출력 정답
쌍 9개**를 `StyledRun` 배열 리터럴로 옮겨 적는다. 발명이 아니라 옮겨 적기다.

| # | 무엇 |
|---|---|
| 1 | 문단 전체 빨강 → 그대로 한 장 (끝의 `\n`만 잘린다) |
| 2 | 문단 안 3조각 병합 — **첫 조각 끝의 공백이 살아 있어야 한다** |
| 3 | 2조각 병합 |
| 4 | 검은 글 속 지시문 → 문단째 탈락 |
| 5 | 문단 맨 앞의 지시문 → 마찬가지로 탈락 |
| 6 | 중복 자막 → **둘 다 유지**, 순서는 `paragraph` 오름차순 |
| 7 | 153자 → 쪼개지 않는다 |
| 8 | 연속 공백 → 그대로 내보낸다 |
| 9 | 미발동 방어 조항 둘 — 문단 끝 검은 공백 예외, 독립 문단 꺾쇠 필터 |

9번은 실물에 사례가 없다. 규칙의 **의도를 고정하기 위한** 케이스이며, 특히 꺾쇠 필터는 실전에서
자막이 사라졌을 때 가장 먼저 의심할 자리이므로 그 동작이 코드에 박혀 있어야 한다.

- [x] Vitest가 설치돼 있고 `pnpm test`로 돈다
- [x] `rules.ts`가 `StyledRun[]`을 받아 자막 장 · 걸러낸 것 · 모르는 색 셋을 반환한다
- [x] 정답 쌍 9개가 `rules.test.ts`에 `StyledRun` 리터럴로 들어가 있고 전부 통과한다
- [x] 걸러낸 것(빨갛지만 자막이 되지 못한 조각 + 그 문단)이 함께 검증된다 — 화면의 노출
      의무이므로 자막만 맞고 이게 비면 담당자가 규칙의 실수를 영영 못 본다
- [x] 모르는 색(조각 + 색값 + 문단 인덱스)이 함께 검증된다
- [x] `rules.ts`가 hwp 포맷에 대해 아무것도 모른다 — OLE·레코드·zlib 관련 코드가 없다

## 남긴 것

**출력 형태.** `toSubtitles(runs) => { subtitles: string[], dropped, unknownColors }`.

- `subtitles`는 문자열 배열이다 — 참조 구현과 같고 `toNabiTxt(string[])`에 그대로 들어간다.
  문단 번호를 달지 않았다. 05의 상호 하이라이트가 요구하면 그때 넣는다
- `dropped`는 `{ fragment, paragraph, context }`다. `context`가 그 조각이 있던 **문단 전문**이며,
  담당자가 "왜 이게 빠졌는지"를 볼 유일한 통로다
- `unknownColors`는 `{ text, color, paragraph }` — 문서 등장 순서

**`view.ts`와 이름이 겹친다 — 04가 정리한다.** `Dropped`·`UnknownColor`가 양쪽에 있고
`Dropped.paragraph`는 뜻이 정반대다(여기 문단 인덱스, `view.ts` 문단 전문). `view.ts`는 스스로
잠정이라 적어 두고 04로 넘긴 파일이므로 지금 건드리지 않고 양쪽에 주석만 남겼다.

**참조 구현과 한 군데 다르다.** 모르는 색의 `text`를 trim해서 담는다 — 참조는 조각을 날것으로
들고 있다. 걸러낸 조각과 같은 모양으로 화면에 나가는 편이 낫다고 봤고, 자막 판정에는 쓰이지
않는 값이다. 원고 3편에 모르는 색이 0건이라 어느 쪽도 실물로 검증된 적은 없다.

**정답 쌍 [6]의 문단 번호.** 04의 리터럴(12 · 40 · 34)과 그 아래 주석("정답 파일에서는 두 인용이
1번·3번 자리")이 서로 어긋난다. 티켓이 규칙으로 못 박은 **문단 오름차순**을 따라 12 · 34 · 40으로
검증했다. 실물 순서의 재확인은 03의 바이트 대조가 한다.

**참조 구현과의 대조(저장소 밖).** 원고 3편을 참조 파서로 떠 `StyledRun[]`을 만든 뒤 이 층에
태워 `subtitle_rules.py`의 셋과 대조했다 — 자막 8 · 16 · 19장, 걸러낸 것 2 · 3 · 0개, 모르는 색
0개로 **전부 일치**. 원고가 커밋에 들어가면 안 되므로 이 대조는 저장소에 남기지 않는다. 03의
`corpus.test.ts`가 로컬 fixture로 이 자리를 대신한다.
