# 04 — 올린다 → 받는다

**What to build:** 담당자가 `.hwp` 원고를 브라우저에 끌어다 놓으면 자막이 몇 장 나왔는지 보이고,
받기 버튼을 누르면 나비CG에 그대로 넣을 수 있는 파일이 떨어진다. **잘 돌아가는 날의 두 걸음이
여기서 완성된다.**

이 티켓이 끝나면 담당자가 실전에 쓸 수 있다. 05~08은 그 위에 검수와 안전망을 얹는 것이다.

**Blocked by:** 03 — 파서 층 + 전 파이프라인 바이트 대조.

**Status:** ready-for-agent

## 화면

첫 화면은 라우트를 나누지 않는다. 드롭존이 화면을 채우고 있다가 파일을 올리면 **같은 자리가**
결과로 바뀐다. 헤더의 `다른 파일`로 언제든 돌아온다.

받기 버튼은 **얇은 헤더**에 둔다. 검은 히어로 배너는 2단에서 원고와 자막을 세로로 밀어낸다.
헤더에 경쟁자가 없으므로 얇아도 주인공이다. 헤더는 어느 화면에서든 **지금 보고 있는 파일이
무엇인지** 보여준다.

자막 장은 순번 · **전문**(잘리지 않는다) · 글자 수를 보여준다. 153자짜리 자막이 나온 날에도
그게 무엇인지 알아야 하고, 유난히 긴 자막을 방송 전에 알아채야 목사님께 문단을 나눠 달라고
부탁할 수 있다.

## 상태

`page.tsx`의 `useState` **하나**다. 화면이 읽기 전용이라 상태를 바꾸는 경로가 문자 그대로
하나다 — 파일이 들어온다. 결과가 한 번 만들어진 뒤로는 변하지 않고 트리 깊이가 2단이라 prop
drilling이 없다. Context·reducer·store는 값을 치를 대상이 없다.

## 프로토타입 타입을 다시 본다

`Doc`/`Block`/`Verdict`는 프로토타입이 화면을 그리려고 발명한 모양이라 규칙 층의 진짜 출력과
일치하는지 검증된 적이 없다. 확정된 타입은 `StyledRun` 하나뿐이다. 규칙 층 실출력에 맞춰
다시 정하고, 화면이 필요로 하는 모양이 있으면 규칙 층 출력에서 화면 쪽에서 유도한다 —
규칙 층 출력을 화면 사정으로 비틀지 않는다.

**편집 기능은 없다.** 자막을 지우거나 고치거나 순서를 바꾸거나 되살릴 수 없다. 고칠 일이 있으면
원고를 고쳐 다시 올린다. 그래야 원고와 자막이 영원히 한 몸으로 남는다. 화면 어딘가에서 이것이
고장이 아니라 설계임을 담당자가 알 수 있어야 한다.

- [ ] 드래그 앤 드롭과 파일 고르기 버튼이 **둘 다** 동작한다
- [ ] 파일을 놓는 순간 추출이 자동으로 시작된다 — "변환하기" 같은 단계가 없다
- [ ] 드롭존에 "원고는 이 컴퓨터 밖으로 나가지 않습니다"가 쓰여 있다
- [ ] 원고 처리가 전부 브라우저 안에서 일어난다 — 네트워크 요청이 나가지 않는다
- [ ] 헤더가 얇고, 파일명 · 자막 장 수 · 받기 버튼이 거기 있다
- [ ] 자막 장이 순번 · 전문 · 글자 수와 함께 나비CG에 들어갈 순서 그대로 나온다
- [ ] 자막 전문이 잘리지 않는다 (153자짜리도 전부 보인다)
- [ ] 받기 버튼이 화면에서 가장 눈에 띈다
- [ ] 받은 파일이 UTF-8 BOM · CRLF · 자막 사이 빈 줄 하나 · 끝에 개행 없음이다
- [ ] 받은 파일 이름이 원고 파일명에서 확장자를 떼고 `-자막.txt`를 붙인 것이다
- [ ] 자막 순서가 원고 등장 순서와 같고, 같은 자막이 두 번 나오는 원고에서 **두 번 다** 나온다
- [ ] 헤더의 `다른 파일`로 언제든 처음으로 돌아간다 — 새로고침이 필요 없다
- [ ] 문서 상태가 `page.tsx`의 `useState` 하나다 (Context·reducer·store 없음)
- [ ] 자막을 고치거나 지우거나 순서를 바꾸는 수단이 화면에 없다
