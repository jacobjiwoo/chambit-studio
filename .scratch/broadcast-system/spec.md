# 방송 시스템 문서 — 스펙

Status: ready-for-agent

[`map.md`](map.md)의 결정을 구현할 수 있는 형태로 옮긴 것이다. 근거는 map에 있고, 여기서는 **무엇을 만드는지**만 적는다. 작업 단위는 map의 티켓 다섯(01–05)이고, 01·02와 03·04가 동시에 돈다.

## Problem Statement

방송부 봉사자는 방송실 장비가 무엇이고 어떻게 이어져 있는지, 예배 때 무엇을 해야 하는지 한곳에서 보고 싶다. 지금까지 이 내용은 한 사람의 Claude 프로젝트 안 "방송부 시스템 핸드북"(용어집, 장비 목록표, 업그레이드 제안)에만 있었다. 다른 팀원과 사역자는 볼 수 없고, 방송실에서 휴대폰으로 펼쳐 볼 수도 없다.

문서는 아직 완성본이 아니다. 장비마다 "확인 필요"가 많고, 선임에게 들은 설명과 직접 확인한 사실이 섞여 있다. 그대로 공개하면 내부 네트워크 주소가 드러나고, 선임 설명을 평가한 문장이 팀원에게 그대로 보인다.

또 chambit-studio에는 이미 `/docs/nabi`라는 문서 사이트가 있지만 그 사이드바·목록 코드는 NABI 매뉴얼 전용이라 다른 문서가 쓸 수 없다.

## Solution

핸드북을 chambit-studio의 `/docs/broadcast-system`("방송 시스템")으로 옮긴다. 이 저장소가 문서의 유일한 원천이 되고, 이후 장비 조사와 정리도 여기서 한다.

- 메인 화면 도구 목록의 "방송 시스템" 카드에서 들어간다.
- 왼쪽 사이드바에 페이지가 한 단계로 늘어선다(용어집, 장비 목록표). 첫 페이지는 이 문서가 무엇인지와 페이지 링크 목록을 보인다.
- 미확인 정보는 숨기지 않고 "확인 필요" 배지로 보인다. 무엇이 미확인인지를 배지가 감싼다.
- 공개 전에 걸러 낸다. 내부 네트워크 주소는 지우고, 사람의 설명을 평가한 문장은 사실과 미확인만 남기는 중립 표현으로 바꾼다.
- 업그레이드 제안은 사이트에 올리지 않고 저장소의 작업 문서로만 둔다.
- 이 문서를 다루는 에이전트는 문서 폴더의 작업 지침을 자동으로 읽는다.

## User Stories

### 들어가기와 둘러보기

1. 방송부원으로서, 메인 화면에서 "방송 시스템" 카드를 눌러 문서로 들어가고 싶다. 주소를 외우지 않아도 되기 때문이다.
2. 방송부원으로서, 카드에 한 문장 설명이 있길 원한다. 들어가기 전에 무엇을 다루는 문서인지 알 수 있기 때문이다.
3. 방송부원으로서, 문서가 비어 있는 동안에는 메인 화면에 카드가 없길 원한다. 들어갔다가 빈 화면을 보는 일이 없기 때문이다.
4. 방송부원으로서, 첫 페이지에서 이 문서가 방송실 장비·연결·운영을 다룬다는 것을 짧게 읽고 싶다. 어디서부터 볼지 정할 수 있기 때문이다.
5. 방송부원으로서, 첫 페이지에서 이 문서가 계속 고쳐지는 문서라는 것을 알고 싶다. 틀린 곳을 발견해도 놀라지 않고 알려 줄 수 있기 때문이다.
6. 방송부원으로서, 첫 페이지에서 "확인 필요" 배지의 뜻을 알고 싶다. 배지가 붙은 정보를 얼마나 믿을지 판단할 수 있기 때문이다.
7. 방송부원으로서, 첫 페이지에 모든 페이지의 링크 목록이 있길 원한다. 사이드바를 열지 않고도 원하는 페이지로 갈 수 있기 때문이다.
8. 방송부원으로서, 사이드바에서 모든 페이지를 정해진 순서(용어집, 장비 목록표 순)로 보고 싶다. 문서 전체 구성을 한눈에 볼 수 있기 때문이다.
9. 방송부원으로서, 지금 보고 있는 페이지가 사이드바에서 강조되길 원한다. 문서 안 어디에 있는지 알 수 있기 때문이다.
10. 방송부원으로서, 휴대폰 폭에서도 사이드바와 본문을 읽을 수 있길 원한다. 방송실에서 휴대폰으로 펼쳐 보기 때문이다.
11. 방송부원으로서, 브라우저 탭 제목이 "<페이지> — 방송 시스템"이길 원한다. 탭이 여러 개일 때 구분할 수 있기 때문이다.
12. 방송부원으로서, 아직 쓰지 않은 문서(신호 흐름도, 운영 체크리스트, 문제 해결 FAQ)는 메뉴에 없길 원한다. 눌렀다가 빈 페이지를 보지 않기 때문이다.

### 용어집

13. 방송부원으로서, 방송부 공식 용어를 한 페이지에서 보고 싶다. 선임과 같은 말로 소통할 수 있기 때문이다.
14. 방송부원으로서, 장비 이름이 문서 전체에서 용어집과 같길 원한다. 같은 장비를 다른 이름으로 읽고 헷갈리지 않기 때문이다.
15. 방송부원으로서, 장비에 적힌 영어 원어와 한국어 풀이를 함께 보고 싶다. 장비 라벨과 문서를 맞춰 볼 수 있기 때문이다.

### 장비 목록표

16. 방송부원으로서, 장비마다 이름·제조사·모델·위치·용도·입출력 연결·비고를 표로 보고 싶다. 장비를 찾아 무엇을 하는지 바로 알 수 있기 때문이다.
17. 방송부원으로서, 장비 목록표가 파트(전원, 영상·온라인 송출 등)별로 나뉘고 각 파트로 바로 가는 앵커가 있길 원한다. 긴 표에서 필요한 곳으로 바로 갈 수 있기 때문이다.
18. 방송부원으로서, 장비 목록표가 한 페이지이길 원한다. 방송실에서 페이지 안 검색으로 장비를 빠르게 찾을 수 있기 때문이다.
19. 방송부원으로서, 온라인 송출 신호 흐름을 "출발 장비 → 도착 장비 (케이블/신호 종류)" 형식으로 읽고 싶다. 송출에 문제가 생겼을 때 흐름을 따라 원인을 좁힐 수 있기 때문이다.
20. 방송부원으로서, 표 칸 안의 줄바꿈이 원래대로 보이길 원한다. 한 칸에 여러 연결이 있어도 읽을 수 있기 때문이다.
21. 방송부원으로서, 장비 목록표 끝의 "확인 필요 목록"을 보고 싶다. 다음에 방송실에서 무엇을 확인할지 알 수 있기 때문이다.

### 확인 필요 표시

22. 방송부원으로서, 미확인 정보 옆에 "확인 필요" 배지가 붙길 원한다. 확인된 사실과 추측을 구분할 수 있기 때문이다.
23. 방송부원으로서, 배지가 무엇이 미확인인지(예: 출발 장비)를 감싸 보이길 원한다. 문장 전체가 아니라 어느 부분이 미확인인지 알 수 있기 때문이다.
24. 방송부원으로서, 배지가 표 칸 안에서도 글줄에 붙어 보이길 원한다. 표 모양이 깨지지 않기 때문이다.
25. 방송부원으로서, 감쌀 대상이 분명하지 않은 곳에는 배지만 보이길 원한다. 미확인이라는 사실은 여전히 알 수 있기 때문이다.
26. 방송부원으로서, "추정"·"선임 설명"·"사용자 확인"은 배지가 아니라 글자로 보이길 원한다. 배지 종류의 범례를 외우지 않아도 되기 때문이다.
27. 문서 작성자로서, 미확인 정보를 하나의 표시 방법으로 쓰고 싶다. 나중에 미확인 목록을 자동으로 모을 수 있기 때문이다.

### 공개와 걸러 내기

28. 방송부 책임자로서, 공개 사이트에 내부 네트워크 주소(LED 프로세서 IP 등)가 없길 원한다. 교회 내부망 정보가 드러나지 않기 때문이다.
29. 방송부 책임자로서, 선임의 설명을 평가한 문장이 사실과 미확인만 남긴 중립 표현으로 바뀌길 원한다. 팀원·사역자와 공유해도 사람을 평가하는 글이 되지 않기 때문이다.
30. 방송부 책임자로서, 설명이 사실과 다를 수 있다는 근거는 평가가 아니라 "확인할 거리"로 남길 원한다. 정보는 잃지 않고 어조만 바뀌기 때문이다.
31. 방송부 책임자로서, 걸러 내기 전 원래 파일이 저장소에 한 번도 커밋되지 않길 원한다. public 저장소라 히스토리에서 지울 수 없기 때문이다.
32. 방송부 책임자로서, 에이전트가 무엇을 걸러 냈는지 원래 문장을 되풀이하지 않는 요지로 보고 싶다. 걸러 낸 결과를 확인하되 걸러 낸 내용이 다시 커밋되지 않기 때문이다.
33. 방송부 책임자로서, 에이전트가 공개가 걸리는 다른 내용을 발견하면 혼자 바꾸지 말고 물어 주길 원한다. 공개 판단은 사람이 하기 때문이다.
34. 방송부 책임자로서, 걸러 낸 결과를 내가 확인한 뒤에 Claude 프로젝트의 원래 파일이 "저장소로 옮겼다" 안내로 바뀌길 원한다. 확인 전에 원래 자료를 잃지 않기 때문이다.
35. 방송부 책임자로서, 방송실 사진 원본이 커밋되지 않고 페이지에 쓰는 사진만 WebP로 올라가길 원한다. 방송실 내부가 통째로 공개되지 않고 저장소가 무거워지지 않기 때문이다.

### 업그레이드 제안

36. 방송부 책임자로서, 업그레이드 제안이 공개 사이트에 없길 원한다. 재정 논의 전의 제안이 주소만으로 열리지 않기 때문이다.
37. 방송부 책임자로서, 업그레이드 제안이 저장소의 작업 문서로 남길 원한다. 문서 원천이 한곳이기 때문이다.
38. 방송부원으로서, 사이트 페이지가 업그레이드 제안을 가리킬 때 그것이 사이트 밖(GitHub)이라는 것을 알고 싶다. 링크를 눌렀다가 다른 곳으로 가도 당황하지 않기 때문이다.
39. 방송부 책임자로서, 업그레이드 제안의 문제 진단은 그대로 옮겨지길 원한다. 장비 구조에 대한 내용이라 걸러 낼 대상이 아니기 때문이다.

### 문서를 고치는 사람과 에이전트

40. 문서 작성자로서, 새 페이지를 더할 때 MDX 파일 하나와 frontmatter(`title`, `description`, `slug`, `order`)만 쓰면 되길 원한다. 사이드바와 첫 페이지 목록을 따로 고치지 않아도 되기 때문이다.
41. 문서 작성자로서, frontmatter 실수(폴더와 다른 `slug`, 겹치는 `order`, 150자를 넘는 `description`, 빠진 키)가 빌드에서 멈추길 원한다. 화면은 멀쩡한데 링크 하나만 404가 되는 일이 없기 때문이다.
42. 문서 작성자로서, 장비 목록표 안의 표가 MDX로 깨지지 않고 렌더되길 원한다. 원래 마크다운 표를 그대로 옮길 수 있기 때문이다.
43. 에이전트로서, 이 문서 폴더의 파일을 다룰 때 작업 지침을 자동으로 읽고 싶다. 역할, 기록 규칙, 공개 규칙을 매번 설명받지 않아도 되기 때문이다.
44. 에이전트로서, 지침에서 장비 이름의 기준이 용어집 페이지라는 것을 알고 싶다. 새 장비를 적을 때 같은 이름을 쓸 수 있기 때문이다.
45. 에이전트로서, 지침에서 연결을 "출발 장비 → 도착 장비 (케이블/신호 종류)"로 적고 미확인은 배지로 쓴다는 것을 알고 싶다. 나중에 데이터로 뽑기 쉬운 형태로 쓰기 때문이다.
46. 에이전트로서, 지침에서 업그레이드 제안은 사이트 밖 작업 문서에 "현재 문제 → 영향 → 제안 → 대략적 비용" 순서로 쓴다는 것을 알고 싶다. 사역자·재정 담당자가 읽을 수 있게 쓰기 때문이다.
47. 에이전트로서, 지침에서 전기·앰프·고소 작업이 얽히면 위험을 먼저 짚으라는 것을 알고 싶다. 봉사자가 다치지 않기 때문이다.
48. 코드 작업자로서, `CONTEXT.md`에서 "방송 시스템"이 무엇인지와 방송 장비 용어는 그 문서의 용어집이 정한다는 것을 알고 싶다. 코드 용어와 방송 용어를 섞지 않기 때문이다.

### NABI 매뉴얼

49. NABI 매뉴얼 독자로서, 방송 시스템 문서가 생긴 뒤에도 `/docs/nabi`의 사이드바, 첫 페이지 링크, 현재 절 강조가 전과 같길 원한다. 쓰던 문서가 바뀌지 않기 때문이다.
50. 코드 작업자로서, 두 문서가 같은 사이드바·레이아웃 코드를 쓰길 원한다. 한쪽만 고쳐서 생김새가 어긋나는 일이 없기 때문이다.
51. 코드 작업자로서, NABI에만 있는 것(Chapter 두 단계)은 NABI 안에 남길 원한다. 방송 시스템이 쓰지 않는 개념이 공용 코드로 새지 않기 때문이다.

## Implementation Decisions

### 공용 문서 모듈 (티켓 01)

- `/docs/nabi`와 `/docs/broadcast-system`이 함께 쓰는 것을 두 라우트의 가장 가까운 공통 조상인 `/docs`의 private folder로 올린다. 사촌 라우트의 private folder import는 lint가 막는다.
- 올리는 것은 실제로 둘이 같은 것뿐이다: frontmatter 읽기(YAML 파싱, 빈 키 검사, `order` 정수 검사, `description` 150자 검사), `order` 정렬과 중복 검사, 링크 목록 표시, 사이드바 표시, 레이아웃 껍데기(사이드바 + 본문).
- NABI에만 있는 것은 NABI에 남긴다: `chapter` 키와 Chapter 키 목록, Chapter → 절 두 단계 묶기, Chapter 첫 페이지 누락 검사.
- 공용 frontmatter 키는 `title`, `description`, `slug`, `order` 넷이다. NABI는 그 위에 `chapter`를 더해 검사한다.
- 동작을 바꾸지 않는 리팩터다. 빌드한 NABI HTML이 전후로 같아야 한다.

### 방송 시스템 페이지 목록과 레이아웃 (티켓 04)

- 방송 시스템 문서는 한 단계다. 라우트 바로 아래 폴더 하나가 페이지 하나이고, 폴더 이름이 `slug`다.
- 목록은 **원문 목록 → 페이지 링크 목록** 순수 함수 하나로 만든다. 입력은 (폴더 이름, `page.mdx` 원문) 쌍의 목록, 출력은 `order` 순의 (`title`, `href`, `order`) 목록이다. 디스크 읽기는 이 함수 밖의 얇은 loader가 한다(NABI의 `toNav`/`loadNav` 분리와 같은 모양).
- 함수는 다음에서 빌드를 멈춘다: frontmatter 없음, 키 누락·형식 오류, `description` 150자 초과, `slug`와 폴더 불일치, `order` 중복. 에러 메시지에 파일 경로를 넣는다.
- private folder(`_`로 시작)와 `page.mdx`가 없는 폴더는 건너뛴다. 첫 페이지(`/docs/broadcast-system` 자체)는 목록에 들지 않는다.
- 사이드바와 첫 페이지 링크 목록은 둘 다 이 함수의 결과를 쓴다. 손으로 쓴 목록은 두지 않는다.
- 레이아웃 metadata title 템플릿은 `%s — 방송 시스템`, 기본값은 `방송 시스템`이다.
- 첫 페이지는 배지의 뜻을 `<Unconfirmed />`로 직접 보인다. 그래서 04는 02에도 막힌다.
- 04는 문서 페이지(`glossary/`, `equipment/`)를 만들지 않는다. 03과 동시에 돌기 때문이다. 확인용 샘플 페이지는 커밋하지 않는다.

### `Unconfirmed` 배지 (티켓 02)

- 01을 기다리지 않는다. 03이 배지만 있으면 되도록 레이아웃(04)과 떼었다.

- 전역 컴포넌트로 두고 MDX 전역 컴포넌트에 등록해 import 없이 쓴다. `Callout`과 같은 자리이고, 왜 전역인지 주석에 적는다.
- 인터페이스: `<Unconfirmed>감쌀 내용</Unconfirmed>` 또는 `<Unconfirmed />`. 감싼 내용은 그대로 보이고 "확인 필요" 글자의 회색 계열 인라인 배지가 붙는다. 내용이 없으면 배지만 보인다.
- 인라인 요소라 표 칸과 문장 안에서 줄을 바꾸지 않는다.
- 배지는 한 종류뿐이다. "추정"·"선임 설명"·"사용자 확인"은 배지로 만들지 않는다.

### 작업 지침과 규칙 (티켓 02)

- 방송 시스템 문서 폴더에 중첩 `CLAUDE.md`를 둔다. 그 폴더 파일을 읽을 때만 로드된다.
- 원래 Claude 프로젝트 지침(역할, 범위, 작업 순서, 결과물 4종, 기록 규칙, 용어, 업그레이드 형식, 안전)을 저장소에 맞게 옮긴다. 바꿀 것: 미확인은 `<Unconfirmed>`, 결과물은 이 폴더의 페이지, 장비 이름 기준은 용어집 페이지, 업그레이드 제안은 사이트 밖 작업 문서, 공개 규칙(내부 주소 금지, 사람 설명 평가 금지, 사진 원본 금지·WebP만), 문체는 저장소 언어 규칙을 따름. 저장소 규칙이나 lint와 겹치는 것과 Claude가 기본으로 하는 것은 쓰지 않는다.
- 프로젝트 구조 규칙의 `app/` 표에 "에이전트 지침: `CLAUDE.md`"를 더하고, Claude Code 공식 문서의 중첩 `CLAUDE.md` 설명을 근거 링크로 단다.
- `CONTEXT.md`에 "방송 시스템" 항목을 더한다. 방송 장비 용어는 그 문서의 용어집 페이지가 정한다는 것까지 적는다. 용어집 자체는 `CONTEXT.md`에 합치지 않는다.

### 문서 옮기기 (티켓 03)

- 용어집은 `order: 1`, 장비 목록표는 `order: 2` 페이지가 된다. 업그레이드 제안은 `.scratch/broadcast-system/` 아래 작업 문서가 된다.
- 내용은 바꾸지 않는다. 걸러 내기와 형식 변환만 한다: 원래 머리(최종 수정·근거·표기 규칙) → frontmatter와 본문 첫 문단, "확인 필요" → `<Unconfirmed>`, 표 칸 `<br>` → `<br />`, 문서 사이 참조 → 새 위치.
- 장비 목록표의 파트는 H2로 나눠 앵커가 생기게 한다. "확인 필요 목록"은 손으로 쓴 그대로 둔다.
- 원래 파일은 저장소 밖에서만 다룬다. 걸러 낸 결과만 커밋한다.
- 결과 보고(티켓 Answer)는 걸러 낸 것의 요지, 감싸지 못한 곳, 사람에게 물을 것을 표로 두고, 원래 문장을 옮겨 적지 않는다.
- Claude 프로젝트의 원래 파일 정리는 사람이 걸러 낸 결과를 확인한 뒤에 한다.

### 메인 화면 카드 (티켓 05)

- 메인 화면 도구 목록에 "방송 시스템" 카드를 더한다. 링크는 `/docs/broadcast-system`, 설명은 기존 카드처럼 한 문장이고 실제 페이지에 맞춘다.
- 03·04가 끝난 뒤에 더한다. 따로 돈 03과 04가 합쳐진 모습(사이드바 순서, 현재 페이지 강조, 첫 페이지 링크 목록)을 여기서 처음 확인한다.

## Testing Decisions

- 좋은 테스트는 겉 동작만 본다. 입력 원문을 주고 나온 목록이나 던진 에러를 확인한다. 내부 helper를 따로 부르거나 중간 자료 구조를 검사하지 않는다.
- **단위 테스트 seam은 하나다: 원문 목록 → 페이지 링크 목록 함수.** vitest로 정렬, `slug`·폴더 불일치, `order` 중복, `description` 150자, 키 누락, frontmatter 없음, private folder 무시를 검사한다. 디스크를 읽지 않고 원문 문자열을 직접 넣는다.
- 공용으로 올린 frontmatter 읽기·정렬 함수의 기존 테스트는 대상 파일 옆으로 따라 옮기고, 그대로 통과해야 한다. NABI 전용으로 남는 Chapter 묶기 테스트는 NABI에 남는다.
- 선례: NABI 매뉴얼 `pages.test.ts`(frontmatter 헬퍼로 원문을 만들어 `toNav`에 넣고 에러 문구를 확인), 찬양 PPT `_lib`의 순수 함수 테스트들.
- React 렌더 테스트 도구(testing-library, jsdom)는 들이지 않는다. `Unconfirmed` 배지, 레이아웃, 사이드바 강조, 메인 카드는 `pnpm build`가 만든 `out/` HTML에서 확인한다:
  - 표 칸 안의 `Unconfirmed`가 배지 글자와 감싼 내용을 함께 내보낸다.
  - 사이드바와 첫 페이지 링크 목록이 frontmatter 순서대로 나온다. 실제 페이지로는 05에서 본다.
  - `out/docs/nabi/**` HTML이 리팩터 전후로 같다.
- 모든 티켓은 `pnpm lint`, `pnpm typecheck`, `pnpm build`(테스트 포함)가 통과해야 끝난다.

## Out of Scope

- 신호 흐름도, 운영 체크리스트(예배 전·중·후), 문제 해결 FAQ 작성. 쓰면 페이지로 더한다.
- 장비·연결을 데이터 파일로 빼서 렌더링하거나 시각화하는 일. 신호 흐름도를 설계할 때 정한다(map Fog).
- `Unconfirmed`를 모아 미확인 목록 페이지를 자동으로 만드는 일(map Fog).
- 업그레이드 제안을 사이트에 올리는 일, 접근 제한(Cloudflare Access 등).
- 사이트 검색, 다크 모드, 디자인 손질.
- NABI 매뉴얼의 동작이나 내용 변경.
- 사진을 페이지에 넣는 일. 규칙만 정하고, 실제 사진은 필요할 때 더한다.

## Further Notes

- 원래 파일은 저장소에 없다. 티켓 03은 Claude 프로젝트 문서를 읽거나 사람에게 받아 저장소 밖 작업 복사본으로 다룬다.
- 걸러 내기는 사람이 확인해야 끝난다. 티켓 03은 에이전트가 하되 마지막 확인은 사람 몫이다.
- `/docs/nabi`는 외부 PDF를 원문 그대로 옮긴 완성본이고, 이 문서는 우리가 계속 고치는 문서다. 그래서 공용으로 올리는 것은 껍데기와 frontmatter 처리뿐이고, 문서 성격에 따른 차이(Chapter, 배지)는 각자 둔다.
