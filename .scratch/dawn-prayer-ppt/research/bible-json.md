## 0. 결론 요약

### 신뢰성 — 조건부로 믿을 수 있다. 고쳐야 할 것이 정확히 몇 개인지 다 세었다

| | 실측 | 판정 |
|---|---:|---|
| 대한성서공회 개역개정과 **완전 일치하는 절** | **30,716 / 31,088 = 98.8034%** | |
| **없어진 절** | **0** | ✅ 한 절도 빠지지 않았다 |
| 중복 키 · 빈 값 | **0 · 0** | ✅ |
| 책·장·절 구조가 정본과 어긋나는 곳 | **0** (66권 1,189장 31,088항목 전부 일치) | ✅ |
| **본문 어구가 다른 절** | **205** (0.66%) | ⚠️ **판차 차이**(§2-3) |
| 띄어쓰기만 다른 절 | 95 (0.31%) | ⚠️ 판차 차이 |
| **문자가 깨진 절** | **16** (`?` 하나씩) | ❌ 고쳐야 한다. **전량 특정됨**(§3-6) |
| 화면에 띄우면 안 되는 기호가 섞인 절 | 난하주 15 · 마침표 41 · NUL 3 · 대괄호 9 | ❌ **전량 특정됨**(§3) |
| 키가 깨진 항목 | **1** (`요18:이`) | ❌ **요 18:38 후반부가 절 번호를 잃었다**(§3-8) |

**한 문장 요약** — 이 파일은 **대한성서공회 개역개정을 긁어 만든 것이고**(§1-1에서 출처를 특정했다), **구조는 정본과 완전히 일치하며 빠진 절이 하나도 없다.** 문제는 두 가지다: **(a) 현행 4판이 아니라 그 이전 판을 긁었고**(어구가 다른 205절), **(b) 긁는 과정에서 생긴 결함 88건이 남아 있다** — 그런데 **88건 전부가 이 문서에 낱낱이 열거돼 있다.** 즉 이 데이터의 위험은 "어디가 틀렸는지 모른다"가 아니라 "**여기를 고치면 된다**"로 바뀌었다.

### 무게 — 구조를 아무리 손봐도 안 줄어든다. 5.1 MB의 88.5%는 본문 글자다

| | raw | gzip -9 | **br q4 (Cloudflare 실측 등가)** | br q11 (사전압축 시) |
|---|---:|---:|---:|---:|
| 원본 그대로 | 5,119,699 | 1,368,729 | **1,270,745** | 1,007,362 |
| 정제 + minify (키 유지) | 4,961,656 | 1,356,944 | **1,260,929** | 1,000,956 |
| 중첩 배열 `[[[절…]…]…]` | 4,624,681 | 1,250,781 | **1,160,755** | 919,792 |
| **순수 텍스트 (절 = 한 줄)** | **4,559,989** | **1,243,594** | **1,152,903** | **915,946** |
| 신약만 — 순수 텍스트 | 1,073,032 | 301,913 | **283,082** | 231,707 |
| **장 파일 1개 (중앙값)** | **3,704** | **1,484** | **1,554** | 1,283 |

- **구조 오버헤드는 전체의 11.5%뿐이다.** 키(4.8%) + JSON 구두점·들여쓰기·CRLF(6.7%). 이걸 **0으로 만들어도 4.56 MB**다. 티켓이 기대한 "키 축약·배열화"의 총 절감은 **raw 10.9% / 전송 9.3%**에 그친다.
- **줄이는 유일한 레버는 압축이고, 그건 이미 공짜로 켜져 있다.** 5.12 MB → **전송 1.27 MB**(Cloudflare 실측 기준). 정제·배열화까지 다 하면 **1.15 MB**.
- **본문을 덜어내는 것만이 자릿수를 바꾼다.** 신약만이면 전송 **283 KB**, 장 단위로 쪼개 필요한 장만 받으면 **1.5 KB**.
- **글자당 바이트**로 보면: raw **3.76 B/한글자**, 전송 **0.93 B/한글자**. UTF-8 한글이 3.00 B이므로 **raw 기준 오버헤드는 25%가 전부이고, 이 데이터에는 "부푼 설정"이 없다.** **여기서 깎을 살은 없다** — 무게는 본문 그 자체다.

## 1. 이 파일의 정체 — 출처를 특정했다

### 1-1. (확인됨) 대한성서공회 개역개정 읽기 페이지를 긁은 것이다

세 가지 증거가 같은 곳을 가리킨다.

**증거 ①  파일이 개역개정과만 맞는다 (실측).** 같은 60장을 두 판본과 대조:

| 대조 대상 | 완전 일치 |
|---|---:|
| **개역개정** `version=GAE` | **1,547 / 1,565 = 98.85%** |
| 개역한글 `version=HAN` | 207 / 1,565 = **13.23%** |

**증거 ②  `요18:이`라는 깨진 키의 생성 기전이 공회 페이지 HTML에 그대로 있다.** 공회는 요 18:38의 본문 **중간에 소제목을 끼워 넣는다**:

```html
<span class="number">38&nbsp;&nbsp;&nbsp;</span>빌라도가 이르되 진리가 무엇이냐 하더라<br /><br /><br />
<font class="smallTitle">십자가에 못 박도록 예수를 넘겨 주다(마 27:15-31; …)</font><br />
<font size='1'></font>이 말을 하고 다시 <font class="area">유대</font>인들에게 나가서 이르되 …
```

긁는 쪽이 소제목에서 절이 끊긴 줄 알고 새 항목을 열었고, 재개된 본문의 **첫 글자 `이`를 절 번호로 집어삼켰다.** 그래서 키가 `요18:이`가 되고 값이 `" 말을 하고 다시…"`로 시작한다. 다른 어떤 출처로도 이 사고는 재현되지 않는다.

**증거 ③  선행 공백이 공회의 소제목 위치와 완벽히 겹친다** — §3-1.

**추가 정황.** 파일에 남은 `(없음)`·`(셀라)`·`(6하반-8상반 없음)`·대괄호·난하주 마커 `1)`는 전부 공회 페이지의 표기 그대로다. 파일 안에 **출처·판차·라이선스를 적은 필드는 없다** — 최상위가 절 키뿐인 평면 객체라 넣을 자리 자체가 없다.

### 1-2. 구조 — 평면 객체, 키 안에 책·장·절

```json
{
  "창1:1": " 태초에 하나님이 천지를 창조하시니라",
  …
  "계22:21": "주 예수의 은혜가 모든 자들에게 있을지어다 아멘"
}
```

| 항목 | 실측 |
|---|---|
| 최상위 | **객체**(배열 아님). 2칸 들여쓰기 pretty-print |
| 항목 수 | **31,089** (중복 키 0 — 원문 텍스트에서 키 줄을 세어 확인) |
| 키 문법 | `<책약어><장>:<절>` — **구분자·공백 없음**. `삼상1:1`, `요일5:21`, `옵1:1`(1장짜리 책도 장 번호를 쓴다) |
| 값 | 문자열 하나. 중첩·메타데이터·절 번호 필드 없음 |
| 정렬 | **정경 순서로 완전히 단조 증가** (책·장·절 전부. 순서 뒤바뀜 0) |
| 인코딩 | **UTF-8, BOM 없음.** 개행 **CRLF 31,090개**(LF 단독 0, CR 단독 0) |
| 값 안의 개행/탭 | **0** — 한 절이 한 줄이다 |
| NBSP·ZWSP·BOM 문자 | **0** |

**약어표는 들어 있지 않다.** 66개 약어는 키 접두사로만 존재한다. 앱이 자기 표를 들고 있어야 한다 — 이건 [`06-reference-input-syntax`](../issues/06-reference-input-syntax.md)의 직접 입력이다.

### 1-3. 약어 66개 — 공회 표기와 일치한다 (실측)

```
창 출 레 민 신 수 삿 룻 삼상 삼하 왕상 왕하 대상 대하 스 느 에 욥 시 잠 전 아 사 렘 애 겔 단
호 욜 암 옵 욘 미 나 합 습 학 슥 말
마 막 눅 요 행 롬 고전 고후 갈 엡 빌 골 살전 살후 딤전 딤후 딛 몬 히 약 벧전 벧후 요일 요이 요삼 유 계
```

공회 페이지가 소제목 안에 다는 **상호참조 링크**(`마 26:47-56` 등)에서 약어를 긁어 대조했다. **41종이 등장했고 불일치 0.** 나머지 25권은 상호참조에 안 나왔지만 조어 규칙이 완전히 같다.

**티켓 06이 알아야 할 함정 하나** — 이 약어들은 **접두사가 겹친다**: `요`⊂`요일`/`요이`/`요삼`, `삼상`/`삼하`, `고전`/`고후`, `살전`/`살후`, `딤전`/`딤후`, `대상`/`대하`, `왕상`/`왕하`. 겹치는 쪽이 전부 **한글로 이어지고 숫자가 아니므로** `^(\D+?)(\d+):(\d+)$` 정규식으로는 갈린다. 하지만 **사람이 치는 입력**(`요1서`, `요한일서`, `삼상 1:1`)은 이 표로 안 잡힌다.

## 2. 정확성 — 전수 대조 결과

### 2-1. 방법

공회 읽기 페이지 `korbibReadpage.php?version=GAE&book=<code>&chap=<n>`을 **1,189장 전부** 내려받아(실패 0), HTML에서 절 번호와 본문을 뽑고 파일과 1:1로 맞췄다. 대조할 때 양쪽 모두 공백을 정규화하고 NUL을 제거했다. 소제목 블록과 난하주 본문(`<div class=D2>`)·난하주 마커(`<a class=comment>`)는 공회 쪽에서 제거했다 — **파일이 그것들을 뺀 상태이기 때문이고, 실제로 뺐는지도 이 대조로 같이 검증된다.**

### 2-2. 결과

```
대조한 절            31,088   (파일 31,089개 중 깨진 키 요18:이 하나만 대조 불가)
완전 일치            30,716   98.8034%
불일치                  372    1.1966%
공회에 있는데 파일에 없는 절     0
파일에만 있는 절                1   ← 요18:이
```

**372건의 정체 (전량 분류)**

| # | 분류 | 건수 | 성격 |
|---|---|---:|---|
| A | **문자 손실 `?`** | **16** | ❌ 데이터 손상. §3-6 |
| B | **난하주 마커 잔존** | **15절 / 마커 16개** | ❌ 긁기 잔재. §3-3 |
| C | **마침표 삽입** | **41** | ❌ 긁기 잔재. §3-4 (파일의 마침표 44개 중 41개가 여기) |
| D | 띄어쓰기만 다름 | 95 | ⚠️ 판차 차이 |
| E | **본문 어구가 다름** | **205** | ⚠️ 판차 차이 |

A·B·C 72건은 **긁는 과정의 사고**이고 기계적으로 고칠 수 있다. D·E 300건은 성격이 다르다 —

### 2-3. **뒤집힌 전제 하나 — 이 파일은 개역개정이 맞지만 "현행 개역개정"은 아니다**

티켓은 *"실제와 완전히 동일한지"* 를 물었다. 답은 **"어느 실제냐"** 다.

**띄어쓰기 차이(D, 95건)의 무늬가 판차를 지목한다** (공회 ←→ 파일):

```
조롱거리 ←→ 조롱 거리 (6)   신성모독 ←→ 신성 모독 (5)   이 후에 ←→ 이후에 (5)
노략거리 ←→ 노략 거리 (4)   이 후에는 ←→ 이후에는 (4)   벧호론 ←→ 벧 호론 (5)
놋 제단 ←→ 놋제단 (4)      만 이천 ←→ 만이천            삼천육백 ←→ 삼천 육백
```

전부 **한글 맞춤법 정비**의 흔적이다. 개역개정은 **1998년 초판** 이후 여러 차례 고쳐졌고 **현재 통용본은 2005년 4판**이다(<https://ko.wikipedia.org/wiki/개역개정판>; 공회 자신은 <https://www.bskorea.or.kr/prog/trans_feature.php> 에서 1998년 개정 원칙 여덟 항목만 싣고 판차는 밝히지 않는다).

**어구 차이(E, 205건)도 같은 방향을 가리킨다.** 몇 개만:

| 절 | 공회(현행) | 파일 |
|---|---|---|
| 왕하23:33 · 25:6 · 25:20 · 25:21 | **리블라** | **립나** ← 개역한글의 표기 |
| 창18:19 | 의와 공도를 | 공의와 정의를 |
| 신29:4 | 오늘**까지** | 오늘 |
| 레25:21 | 쓰기에 **족하게** | 쓰게 |
| 겔28:11 | 여호와의 말씀이 또 내게 임하여 | 여호와께서 이같이 말씀하시되 또 내게 임하여 |
| 고후4:8 | **욱여쌈**을 당하여도 | **우겨쌈**을 당하여도 ← 개역한글 표기 |
| 삼상25:18 · 왕상18:32 | **스아** | **세아** |
| 대상15:17 | 베레**갸** | 베레**야** |

`립나`·`우겨쌈`은 **개역한글의 독법**이다. 즉 파일은 개역한글에서 아직 덜 떨어진, **4판 이전 개역개정**을 담고 있다.

**이게 왜 중요한가.** 예배당에서 회중이 들고 있는 성경은 십중팔구 **4판**이다. 이 파일로 슬라이드를 만들면 **31,088절 중 300절(0.97%)에서 화면과 손 안의 책이 다르게 읽힌다.** 매일 25절씩 돈다면 **넉 달에 한 번꼴로 한 절**이 어긋난다. 틀린 성경은 아니지만 *"어제와 다른 성경"* 이다.

**초판인지 2판인지 3판인지는 특정하지 못했다.** 공회는 현행본만 온라인으로 서비스하고, 판차별 대조표를 공개하지 않는다. 확정하려면 종이 성경 실물이 필요하다.

> ⚠ **추가 측정(2026-08-09) — 이 절의 방향 판단은 취소한다.** 205건 전량에서 다른 낱말만 뽑아 개역한글(HAN)과 3자 대조한 결과, **개역한글이 공회 편인 것 90건 / 파일 편인 것 38건**이다. 위 표가 근거로 든 `립나`·`우겨쌈`은 38 쪽이고 대부분 표기·고유명사 차이인 반면, 반대 방향 90건은 어구 자체가 다르다(`의와 공도`↔`공의와 정의`, `온전히 좇았음이라`↔`충성하였음이라`). **단일 판차 이력은 한 방향으로만 흐르므로 *"파일 = 4판 이전"* 은 성립하지 않는다** — 파일은 어느 판본도 아닌 유포본일 가능성이 크다. 전량 목록은 [`bible-json-3way.md`](bible-json-3way.md), 경위는 [티켓 11의 중간 기록](../issues/11-which-printing.md)에 있다.

## 3. 화면에 띄우면 안 되는 것 — 전수 목록

티켓이 *"핵심"* 이라고 한 항목이다. **전부 셌고 전부 열거했다.**

### 3-1. **선행 공백 2,414개 — 쓰레기가 아니라 소제목 경계다** ⚠️ 전제가 뒤집혔다

티켓은 첫 값의 선행 공백을 보고 *"데이터 정제가 안 돼 있다는 신호"* 라고 적었다. 정제가 안 된 건 맞지만 **그 공백에는 정보가 있다.**

31,088절 전부에 대해 "공회 페이지에서 이 절 바로 앞에 소제목이 있는가"와 "파일 값이 공백으로 시작하는가"를 교차시켰다:

| | 파일에 선행 공백 O | 선행 공백 X |
|---|---:|---:|
| **공회에서 소제목 직후** | **2,413** | 15 |
| 소제목 직후 아님 | **0** | 28,660 |

- **정밀도 100.000% — 오탐이 0이다.** 28,660개의 평범한 절 중 공백으로 시작하는 것이 **단 하나도 없다.**
- 재현율 99.4% (2,413 / 2,428).
- 나머지 1개는 `요18:이`(그 자체가 소제목 사고의 산물)로 2,414가 채워진다.

즉 **`값[0] === ' '` 는 "이 절에서 개역개정의 새 단락(소제목)이 시작한다"와 동치다.** 개역개정에는 소제목이 **2,429개** 있고 파일은 그 텍스트를 **하나도 담지 않았지만**(§3-9), 위치는 이 공백으로 살아남았다.

**두 갈래 귀결** — (1) 화면에 띄우기 전에 **반드시 trim해야 한다**(공백으로 시작하는 슬라이드가 2,414장 나온다). (2) trim하기 전에 **플래그로 떠 두면 공짜로 얻는 구조 정보**다. 버릴지 살릴지는 [`09-placement`](../issues/09-placement.md)·[`07-verse-overflow-splitting`](../issues/07-verse-overflow-splitting.md)가 판단할 몫이다.

후행 공백은 **0개**. 값 내부 이중 공백은 **2개**(`렘3:22`, `눅20:42`).

### 3-2. `(없음)` 13절 — 정본 표기다

`마17:21` `마18:11` `마23:14` `막9:44` `막9:46` `막11:26` `막15:28` `눅17:36` `눅23:17` `행8:37` `행15:34` `행28:29` `롬16:24`

공회도 똑같이 `(없음)`이라고 찍는다. **데이터 결함이 아니다.** 다만 **이 13절을 슬라이드로 만들면 화면에 "(없음)"만 뜬다.** 새벽기도 본문 범위가 이 절을 지나갈 때 어떻게 할지는 정해야 한다.

### 3-3. 난하주 마커 15절 — 긁기 잔재다 ❌

개역개정 전체에 난하주 마커가 **1,889개** 있고 파일은 그중 **1,873개를 제대로 지웠다.** 남은 **16개가 15절에** 박혀 있다:

`시72:2`(재판1)) `잠13:7`(부1)·가난1)) `사7:15`(때3)) `사15:2`(메드바1)) `사21:14`(영접2)) `렘40:7`(유아1)) `욜2:18`(여기4)) `욜2:20`(하4)) `마27:49`(하더라3)) `막14:68`(나갈새6)) `눅9:55`(꾸짖으시고2)) `빌2:18`(기뻐6)) `히2:7`(씌우시며3)) `히13:25`(있을지어다2)) `벧후3:18`(있을지어다3))

**난하주 본문이 값에 섞여 들어온 건 1건도 없다.** 마커만 남았다. `/\d\)/` 로 지우면 끝난다 — 본문에 다른 용도의 `숫자)`는 없다(파일 전체 숫자 문자는 18개뿐이고 전부 이 마커 아니면 `행24:6`의 `(6하반-8상반 없음)`이다).

### 3-4. 마침표 44개 — 개역개정에는 마침표가 없다 ❌

개역개정 본문은 문장 끝에 마침표를 찍지 않는다. 파일의 마침표 **44개**는 전부 **절 안쪽의 단락 경계**에 들어가 있다 — 긁는 쪽이 `<br>` 두 개를 `. `로 바꾼 흔적이다. 공회 HTML을 뒤져 확인한 결과:

- **14개**는 그 절 **안에 소제목이 들어 있는** 자리 (`창35:22`=「야곱의 아들들」, `삼상4:1`=「언약궤를 빼앗기다」, `막6:6`, `눅9:43`, `눅23:56`, `행8:1`, `행9:19`, `행10:23`, `롬16:20`, `요12:36`, `삼하12:15`, `삼하19:8`, `사59:15`, `렘3:22`)
- **30개**는 소제목 없는 **단락 경계** (`사15:1` "모압에 관한 경고라**.** 하룻밤에…", `잠10:1` "솔로몬의 잠언이라**.** 지혜로운…", `느1:1`, `옵1:1`, `딤전3:16` 등)

**요 18:38에서는 이 처리가 실패해 절이 통째로 쪼개졌다**(§3-8). 같은 사고의 성공 케이스가 44개, 실패 케이스가 1개다.

### 3-5. NUL 문자 30개 ❌ — JSON에 ` `으로 들어 있다

| 절 | 개수 | 위치 |
|---|---:|---|
| `삿21:25` | 7 | 사사기 **마지막 절** 끝 |
| `습3:20` | 9 | 스바냐 **마지막 절** 끝 |
| `벧전5:14` | 14 | 베드로전서 **마지막 절** 끝 |

셋 다 **책의 마지막 절 꼬리**다. 왜 이 세 권만인지는 못 밝혔다. 원시 바이트에 `\x00`은 없고 JSON 이스케이프 ` `이 30번 나온다 — **JSON 파서를 통과하므로 조용히 살아남고**, 파워포인트 텍스트 상자에 그대로 들어간다.

### 3-6. **문자 손실 16개 — KS X 1001 완성형을 통과한 흔적이다** ❌

16개 절에 `?`가 하나씩 있고, 전부 **고유명사의 한 음절**이 날아간 자리다:

| 잃은 글자 | 건수 | 절 |
|---|---:|---|
| **웻** | 11 | `창10:26`(하살마웻) `삼하23:31` `대상1:20` `대상8:36` `대상9:42` `대상11:33` `대상12:3` `대상27:25` `스2:24` `느7:28` `느12:29` (전부 아스마웻/하살마웻) |
| **훕** | 4 | `창46:21`(훕빔) `대상7:12` `대상7:15` `대상24:13`(훕바) |
| **쁄** | 1 | `사62:4`(쁄라) |

**기전을 특정했다.** 웻·훕·쁄은 **KS X 1001 완성형 2,350자 밖**이다(EUC-KR로 넣으면 2바이트가 아니라 8바이트 조합형 이스케이프가 된다). 그리고 결정적으로 —

> **파일 안 1,361,591개 한글 음절 중 KS X 1001 밖의 음절이 단 하나도 없다.**

즉 이 데이터는 어느 단계에서 **KS X 1001 완성형(CP949 확장이 아닌 순수 EUC-KR)** 을 통과했고, 밖에 있던 글자는 전부 `?`가 됐다. **그래서 손실은 이 16개가 전부다** — 살아남은 밖-음절이 0이므로 더 숨어 있을 수 없다. (남는 잔여 위험: `?`가 아니라 **다른 글자로 조용히 치환**된 경우. 전수 대조 372건 중 그런 무늬는 없었다.)

### 3-7. 대괄호 9절 — 정본 표기다

`막16:9` `막16:20` `눅24:51` `눅24:52` `요5:3` `요5:4` `요7:53` `요8:11` `롬3:5`

개역개정이 **고대 사본에 없는 부분**을 감싸는 표기이고 공회도 똑같이 찍는다. 다만 **여는 괄호와 닫는 괄호가 여러 절에 걸쳐 있다** (`막16:9`에 `[`만, `막16:20`에 `]`만). **절 단위로 슬라이드를 만들면 짝이 없는 대괄호가 화면에 뜬다.**

### 3-8. `요18:이` — 절 하나가 번호를 잃었다 ❌

```
요18:38  "빌라도가 이르되 진리가 무엇이냐 하더라"
요18:이  " 말을 하고 다시 유대인들에게 나가서 이르되 나는 그에게서 아무 죄도 찾지 못하였노라"
```

정본 요 18:38은 **둘을 합친 한 절**이다. 지금 상태로는 (a) 키가 파싱 불가이고 (b) **`요18:38`을 띄우면 절의 절반만 나온다.** 사람이 알아채기 어려운 종류의 오류다.

### 4-1. 항목 31,088 ≠ 절번호 31,101 — 병합절 11개 때문이다

개역개정은 한국어 어순 때문에 **여러 절을 한 항목으로 붙여 인쇄한다.** 공회 페이지도 파일도 똑같이 `18-19` 식으로 표기한다 — **긁기 오류가 아니라 정본 표기다.** 공회 신명기 6장을 직접 열어 확인했다(<https://www.bskorea.or.kr/bible/korbibReadpage.php?version=GAE&book=deu&chap=6&sec=1>).

| 키 | 절 번호 |
|---|---:|
| `신6:18-19` `신15:4-5` `신30:9-10` `대상16:12-13` `시105:5-6` `렘33:10-11` `겔24:4-5` `행15:25-26` `롬9:1-2` | +1씩 (9개) |
| `시92:1-3` `렘32:3-5` | +2씩 (2개) |
| | **합계 +13** |

**[`06-reference-input-syntax`](../issues/06-reference-input-syntax.md)에 그대로 넘어가는 함정이다.** 목사님이 *"신명기 6장 19절"* 이라고 하면 키 `신6:19`는 **존재하지 않는다.** 앱은 병합절 11개를 알고 있어야 하고, 그 절을 띄우면 화면에는 **두세 절이 한 장에** 뜬다(그리고 이 셋이 §6의 최장 절 1·2·3위다).

### 4-2. **31,102는 이 데이터의 수치가 아니다 — 차이는 정확히 `행24:7` 하나다**

공회 개역개정을 세면 **절 번호 31,101개**다. 널리 인용되는 31,102와 **정확히 1 차이**이고, 그 1의 정체를 특정했다:

```
행24:6  "그가 또 성전을 더럽게 하려 하므로 우리가 잡았사오니 (6하반-8상반 없음)"
행24:7  ← 존재하지 않는다. 공회에도, 파일에도
행24:8  "당신이 친히 그를 심문하시면 …"
```

**개역개정은 사도행전 24:7이라는 절 번호를 아예 인쇄하지 않는다.** 그래서 사도행전이 1,006절이다(KJV 계열 절 배열은 1,007). 참고로 **요한3서는 15절**로, KJV 계열의 14절과 다르다 — 절 배열 자체가 미묘하게 다른 곳이 둘 있다는 뜻이다.

**31,102의 출처는 1차 자료로 확인하지 못했다.** 대한성서공회 사이트 어디에도 총 절수를 명시한 페이지를 찾지 못했고, 이 숫자를 싣고 있는 것은 나무위키와 개인 블로그다. **따라서 이 맵에서는 31,102를 쓰지 말고, 실측한 31,101(절 번호) / 31,088(인쇄 항목) / 31,089(이 파일의 항목 수, `요18:이` 포함)를 쓸 것.**

### 5-2. **Cloudflare가 실제로 무엇을 내려보내는지 재고 왔다** (중요)

로컬 `brotli q11`로 재면 916 KB지만 **그건 이 사이트가 내려보내는 값이 아니다.** `chambitstudio.com`의 실제 정적 자산으로 확인:

```
GET /_next/static/chunks/0-40zia-3e4jt.js   (raw 23,874 B)
  Accept-Encoding: br     → content-encoding: br    7,644 B
  Accept-Encoding: gzip   → content-encoding: gzip  7,469 B
  Accept-Encoding: zstd   → 압축 안 됨              23,874 B
```

같은 파일을 로컬에서 압축해 보면 **br q3 = 7,806 / q4 = 7,619 / q11 = 6,614**. 즉

> **Cloudflare Pages의 실시간 brotli는 대략 q4다.** q11이 아니다. 그리고 이 사이트에서는 **gzip이 brotli보다 작게 나왔다**(7,469 < 7,644). zstd는 (문서상 Free 기본값임에도) 적용되지 않았다.

그래서 이 문서의 전송량 표는 **br q4를 기준선**으로 잡는다. brotli q11로 미리 구워 `_headers`로 `Content-Encoding: br`을 붙이는 길이 남아 있고, 그 경우 **1.15 MB → 916 KB(−20%)** 가 되지만 **Pages에서 끝까지 동작하는지는 확인하지 못했다**(부록 B).

- 근거: <https://developers.cloudflare.com/speed/optimization/content/compression/> (Free는 Zstandard, Pro/Business는 Brotli가 기본. 압축 품질은 문서에 없음), <https://developers.cloudflare.com/rules/compression-rules/>

| 분할 단위 | 파일 수 | 전송 합계(br q4) | **파일 하나(중앙값)** | 최대 |

- **그런데 배포 총량은 사용자가 내는 값이 아니다.** 새벽기도 한 번에 필요한 건 보통 **한 장**이고, 그건 **br q4 기준 중앙값 1.5 KB, 최악 5.1 KB**다. 통짜 1.15 MB 대비 **약 750배 적다.**

- Cloudflare Pages 파일 수 제한은 **무료 20,000 / 유료 100,000**이므로 1,189개도 여유롭다.

## 7. 빌드 게이트로 만들 수 있는가 — **된다, 그리고 두 종류다**

`expect()`로 빌드를 막는 수법이 그대로 통한다. 다만 **성경 데이터에는 성격이 다른 게이트 두 벌이 필요하다.**

### 7-1. 구조 게이트 — 네트워크 없이 즉시 돈다 (권장)

정본 수치를 상수로 박고 데이터가 그것과 어긋나면 빌드를 깬다. 실측이 이미 나와 있으므로 기대값이 전부 확정돼 있다:

| 검사 | 기대값 | 근거 |
|---|---|---|
| 책 수 / 장 수 / 항목 수 | 66 / 1,189 / 31,089 | §4 |
| 권별 장·절 수 | §4의 66행 표 | 대한성서공회 실측 |
| 장별 절 번호 연속성 | 빈 곳 없음, 단 `행24:7` 제외 | §4-3 |
| 중복 키 · 빈 값 | 0 / 0 | §4-3 |
| **금지 문자** | ` ` 0개, `?` 0개, `.` 0개, `/\d\)/` 0건 | §3 |
| **선행·후행 공백** | 0건 (별도 플래그로 옮긴 뒤) | §3-1 |
| **키 문법** | 전부 `^(약어)(\d+):(\d+(-\d+)?)$` 통과 | §1-2 |
| 절 길이 상한 | ≤ 287자 (병합절 해소 시 ≤ 194자) | §6 |
| **글자당 바이트** | ≤ 3.40 B/한글자 (raw), ≤ 0.95 B/한글자 (br q4) | §5-1 — *색인 티켓이 세운 자를 그대로 옮긴 것* |

**성경 본문은 늘지 않는다.** 콘텐츠와 함께 느는 데이터라면 "늘어 커지는 것은 정당하다"를 허용해야 하지만, **여기서는 절대 크기를 그냥 고정해도 된다.** 숫자가 움직였다면 그건 성장이 아니라 사고다.

### 7-2. 본문 게이트 — 이 조사의 결과물을 그대로 쓴다

전수 대조 스냅샷을 저장해 두고 회귀만 본다. **네트워크 호출은 빌드에 넣지 말 것**(공회 사이트에 의존하게 되고 새벽에 배포가 깨진다).

- 정제 후 전체 본문의 **SHA-256 하나**를 상수로 박는다. 한 글자라도 바뀌면 깨진다.
- 알려진 결함 88건을 **명시적 허용 목록**으로 들고, 목록이 줄면(고쳐지면) 통과, **늘면 깨진다.**
- 공회와의 재대조는 **수동 스크립트**로 남긴다(부록 A). 4판 대응이나 데이터 교체를 할 때만 돌린다.

### 7-3. 게이트가 못 잡는 것

**"글자는 맞는데 뜻이 틀린" 경우는 어떤 기계 검사로도 안 잡힌다.** §2-3의 판차 차이 300건이 정확히 그런 종류다 — 전부 문법에 맞는 한국어이고, 성경처럼 읽히고, 다만 회중이 든 책과 다르다. **이건 게이트의 일이 아니라 데이터 출처 결정의 일이다.**

## 8. 남은 위험을 어떻게 좁히나 — 표본 검증 설계

전수 대조로 *"현행 공회본과 어디가 다른가"* 는 끝났다. **남은 질문은 하나다: 파일이 담고 있는 그 판본은 정확히 무엇이고, 그 판본으로서는 옳은가.** 여기엔 종이가 필요하다.

**설계 — 목표 30~40절, 30분 안에 끝난다.**

| 층 | 뽑는 법 | 절 수 | 무엇을 확인하나 |
|---|---|---:|---|
| **1. 결함 확정 표본** | §3의 결함 목록에서 계열별 대표 | **10** | `?` 3개(웻·훕·쁄), NUL 3개, `요18:이`, 병합절 2개, `(없음)` 1개 |
| **2. 판차 판별 표본** | §2-3의 어구 차이 205건에서 **무작위 15절** | **15** | 종이가 공회 편인가 파일 편인가. **이 15절이 판차를 확정한다** |
| **3. 무작위 대조** | 31,089절에서 균등 무작위 | **10** | 전수 대조가 못 본 계열의 사고가 있는지 |
| **4. 실전 표본** | 최근 4주 새벽기도 본문 범위 전체 | 100 내외 | 실제로 쓰는 범위에서의 체감 오류율 |

**대조 대상은 종이 성경 실물이어야 한다** — 온라인 공회본은 이미 전수로 썼으므로 새 정보가 0이다. 방송부가 쓰는 강대상 성경이면 가장 좋다(회중이 보는 것과 같으므로).

**판정 기준.** 층 2에서 **15절 중 12절 이상이 파일 쪽과 같으면** 파일은 그 교회가 쓰는 판본과 일치하는 것이고 §2-3의 위험은 사실상 해소된다. **공회 쪽과 같으면 데이터를 4판으로 갈아야 한다** — 그러면 이 파일은 버려지고 티켓 05의 입력이 바뀐다.

**표본 크기 근거.** 전수 대조로 오류율이 이미 1.20%로 확정돼 있으므로, 층 3은 "새로운 오류 계열의 부재"만 보면 된다. 10절로 잡을 수 있는 건 **발생률 26% 이상인 계열**뿐이다(1−0.74¹⁰ ≈ 95%) — 그런 계열은 전수 대조에서 이미 다 드러났다. 층 3은 **확증이 아니라 위생 점검**이고, 그렇게 읽어야 한다.

## 부록 B — 확인 못 한 것 / 추론임을 밝히는 것

- **(확인 못 함) 파일이 개역개정 몇 판인가.** 초판(1998)·2판·3판 중 하나이고 4판은 아니라는 것까지가 한계다. 공회가 현행본만 온라인 서비스하고 판차별 대조표를 공개하지 않는다. **§8 층 2가 이걸 겨냥한 설계다.**
- **(확인 못 함) 정확히 어느 사이트/도구가 이 파일을 만들었는가.** 출처가 공회 개역개정 페이지라는 것은 §1-1로 확정했지만, 긁은 주체·시점·중간 배포 경로는 파일 안에 흔적이 없다. `요18:이`와 KS X 1001 손실을 검색어로 삼으면 원 배포처를 찾을 수 있을 가능성이 있다(시도하지 않았다).
- **(확인 못 함) NUL 30개가 왜 하필 삿·습·벧전의 마지막 절에만 붙었는가.** 세 권의 공통점(사사기·스바냐·베드로전서)을 찾지 못했다.
- **(추론) `?` 16개가 손실의 전부다.** 파일에 KS X 1001 밖 음절이 0개라는 실측에 기반한다. **조용한 치환**(밖-음절이 `?`가 아니라 다른 완성형 글자로 바뀌는 경우)까지는 배제하지 못한다. 다만 전수 대조 372건 중 그런 무늬(한 음절만 다른 고유명사)는 없었다.
- **(확인 못 함) Cloudflare Pages에서 미리 brotli q11로 구운 파일을 `_headers`로 `Content-Encoding: br`을 붙여 내려보낼 수 있는가.** 된다면 전송이 1,153 → 916 KB(−20%)가 된다. **배포해 보지 않았다.** Cloudflare 문서는 사전압축 자산을 다루지 않는다.
- **(확인 못 함) Cloudflare가 왜 이 사이트에 zstd를 적용하지 않는가.** 문서상 Free 플랜 기본값은 Zstandard인데 `Accept-Encoding: zstd`에 비압축으로 응답했다. 플랜·경로·MIME 중 무엇 때문인지 확인하지 못했다. (`application/json`은 압축 대상 MIME 목록에 있으므로 bible.json 자체는 압축될 것으로 본다 — **이것도 실제 배포 전에는 추론이다.**)
- **(추론) br q4가 Cloudflare의 실제 품질이다.** JS 청크 하나(23,874 B)에서 CF 출력 7,644 B가 로컬 q3(7,806)와 q4(7,619) 사이에 떨어진 것으로 추정했다. **파일 하나로 추정한 값**이고, 크기·내용에 따라 달라질 수 있다. 이 문서의 전송량 표는 그만큼의 오차를 안고 있다.
- **(확인 못 함) 31,102의 출처.** 대한성서공회 사이트에서 총 절수를 명시한 페이지를 찾지 못했다. 실측 31,101과의 차이가 `행24:7`이라는 것까지만 확정했다.
- **(범위 밖) 저작권.** 맵이 명시적으로 논외로 뒀다([`map.md` Out of scope](../map.md)). 이 조사는 다루지 않았다.
