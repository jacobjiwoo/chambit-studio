# bible.json 검증과 개역개정 데이터의 실제 모습

Type: research
Status: resolved

## Question

손에 있는 개역개정 JSON이 **믿을 수 있는 데이터인지**, 그리고 **5.1 MB를 얼마나 줄일 수 있는지** 확정한다.

차팅에서 나온 것 — 인터넷에서 받은 파일이고 담당자 스스로 *"실제와 완전히 동일한지는 검증이 필요한 상태"* 라고 했다. 이 데이터가 틀리면 도구가 매일 새벽 **회중 앞 화면에 틀린 성경을 띄운다.** 이 맵에서 오류의 대가가 가장 큰 자리다.

**~~선행 조건 — 파일 접근.~~ 해소됐다.** 실물이 `.scratch/dawn-prayer-ppt/bible.json`에 있다(5,119,699 바이트, 2026-08-07 이동). `.gitignore` 64행이 이 경로 하나를 명시적으로 무시한다 — 커밋되지 않는다. (원래 `~/Downloads`에 있었고 macOS TCC가 막아 차팅 세션에서 읽지 못했다.)

**첫 200바이트에서 이미 보인 것 두 가지** — 조사의 출발점이다:

- 구조는 **평면 객체**이고 키가 `"창1:1"` 형태다. 책 약어 + 장 + `:` + 절. 즉 책·장·절이 **파싱해야 하는 문자열 안에** 있고 중첩 구조가 아니다
- 첫 값이 **공백으로 시작한다** — `" 태초에 하나님이 천지를 창조하시니라"`. 데이터 정제가 안 돼 있다는 신호이므로 **전수로 확인할 것**(앞뒤 공백, 이중 공백, 비정상 문자)

### 조사할 것 — 데이터의 정체

- JSON 구조. 최상위가 배열인가 객체인가, 책·장·절이 어떤 키로 표현되는가
- **책 이름 표기** — `창세기`인가 `창`인가 `Gen`인가. 약어 표가 함께 들어 있는가. 이건 `본문 범위 입력 문법`의 직접 입력이다
- 실제 책 수·장 수·절 수. 개역개정의 정본 수치와 대조한다 (정본 수치도 조사 대상이다 — 차팅 중 에이전트가 `31,102절`을 언급했으나 **검증되지 않은 숫자**이므로 그대로 믿지 말 것)
- 출처가 어디인지 추적 가능한가. 판(개역개정 / 개역개정4판)이 명시돼 있는가
- 인코딩, 개행, 특수문자 — 원문의 소제목·난하주·`[]` 같은 편집 기호가 본문에 섞여 있는가. **화면에 띄우면 안 되는 것이 데이터에 섞여 있는지**가 핵심이다

### 조사할 것 — 정확성 검증 방법

- 전수 대조는 비현실적이다. **표본 검증 설계**를 제안할 것 — 몇 절을, 어떻게 고르고, 무엇과 대조하는가
- 기계적으로 잡을 수 있는 이상 징후(빈 절, 중복 절, 비정상적으로 짧거나 긴 절, 누락된 장)를 훑고 개수를 보고할 것
- 이 검증을 **빌드 게이트로 만들 수 있는가.** `expect()`로 빌드를 막는 수법이 성경 데이터에도 통하는지

### 조사할 것 — 무게

여기가 이 맵의 최대 위험과 맞닿는다. 사이트는 **서버 없는 정적 배포**이고, 이 저장소는 방문자가 내려받는 바이트를 **수십 KB 단위로** 재 왔다. 5.1 MB는 그 기준선과 자릿수가 다르다.

- 5.1 MB의 내역 — 본문 글자가 몇 바이트이고 JSON 구조 오버헤드가 몇 바이트인가
- 줄이는 수단별 **실측 절감치**: 키 축약, 배열화, 책·장 단위 분할, gzip/brotli(정적 호스팅이 전송 시 압축하므로 **전송 크기와 원본 크기를 따로 잴 것**), 바이너리 포맷
- **신약만 / 자주 쓰는 책만** 같은 부분 적재가 의미 있는 절감인가 — 새벽기도가 어느 범위를 도는지 모르므로 절감치만 내고 판단은 넘길 것
- 절 길이 분포 — 최소·최대·중앙값·상위 백분위. **`절이 넘칠 때 어떻게 쪼개나`가 이걸로 넘치는 절 개수를 계산한다.** 가장 긴 절 상위 20개를 길이와 함께 나열할 것

## Answer

전문: [`research/bible-json.md`](../research/bible-json.md) (브랜치 `docs/dawn-prayer-ppt-02-bible-json`, 커밋 `ddb9c90`)

**표본을 설계하러 갔다가 전수를 댔다.** 대한성서공회 개역개정(GAE) 1,189장을 전부 내려받아 **31,088절을 1:1로 대조**했다. 티켓이 *"전수 대조는 비현실적"* 이라고 적은 전제가 깨졌다 — 6분이면 된다.

**신뢰성 — 조건부로 믿을 수 있고, 고칠 것이 정확히 몇 개인지 다 세었다.**

- **일치 98.8034%**(30,716/31,088). **없어진 절 0, 중복 0, 빈 값 0.** 구조는 정본과 **완전 일치**(66권·1,189장·31,088항목, 66권 전부)
- **출처를 특정했다** — 공회 개역개정 읽기 페이지 스크레이프다. 파일 대 개역개정 98.85% vs 개역한글 13.23%, 그리고 깨진 키 `요18:이`의 **생성 기전이 공회 HTML 안에 그대로 있다**(소제목이 요 18:38 본문 한가운데를 끊는다)
- **뒤집힌 전제 ①** — 선행 공백 2,414개는 *"정제가 안 된 신호"* 가 아니라 **소제목 경계**다. 31,088절 교차 검증에서 **오탐 0/28,660**, 재현율 99.4%. 화면에는 반드시 trim해야 하지만, **버리기 전에 플래그로 떠 두면 공짜로 얻는 구조 정보**다
- **뒤집힌 전제 ②** — 이 파일은 개역개정이 맞지만 **현행 4판(2005)이 아니다.** 어구 205절 + 띄어쓰기 95절이 현행과 다르고, `립나`/`우겨쌈` 같은 개역한글 독법이 남아 있다. **300절(0.97%)에서 화면과 회중이 든 책이 다르게 읽힌다** — 매일 25절이면 넉 달에 한 번꼴. 몇 판인지는 종이 없이 확정 못 했다
- **결함 88건 전량 열거** — `?` 16(KS X 1001 완성형 통과 흔적. **파일에 완성형 밖 음절이 0개라 이게 손실의 전부다**), 난하주 마커 15절, 마침표 41(개역개정에 마침표는 없다), NUL 30자 3절, 대괄호 짝 어긋남 9절, `요18:이` 1건. 정본 표기라 건드리면 안 되는 것도 갈라 뒀다: `(없음)` 13, `(셀라)`, 병합절 11
- **빌드 게이트 된다.** 성경은 늘지 않으므로 **절대 크기를 그냥 고정해도 된다**. 구조 게이트는 네트워크 없이 즉시, 본문 게이트는 SHA-256 + 결함 허용 목록으로

**정본 수치 — `31,102`는 이 데이터의 수치가 아니다.** 공회를 전수로 세면 **66권 · 1,189장 · 인쇄 항목 31,088 · 절 번호 31,101**이고, **차이 1은 `행24:7`**이다(개역개정은 이 절 번호를 아예 안 찍고 24:6 끝에 `(6하반-8상반 없음)`만 적는다). 31,102는 1차 자료로 확인되지 않는다 — **이 맵에서 쓰지 말 것.**

**무게 — 5.1 MB의 88.5%가 본문 글자다. 깎을 살이 없다.**

- 내역: 한글 1,361,591자×3B = **79.8%**, 공백 8.6%, 키 4.8%, JSON 구두점·들여쓰기·CRLF 6.7%. **구조를 0으로 만들어도 4.56 MB**
- **키 축약은 헛수고**(압축 후 0.1%). **배열화가 유일하게 의미 있는 구조 변경**(전송 −8.7%). 순수 텍스트는 배열화 대비 **0.7%**뿐
- **실패한 수단 셋** — EUC-KR(raw −30%지만 **전송 −4.7%**), 14비트 음절 팩킹(**전송 +25.5%. 오히려 커진다**), zstd(Cloudflare가 이 사이트에 적용하지 않는다 — 실측)
- **Cloudflare 실측** — `chambitstudio.com`은 **br q11이 아니라 대략 q4**로 압축한다(이 사이트에선 gzip이 brotli보다 작게 나왔다). 그래서 전송 기준선은 **1,270 KB**(원본) / **1,153 KB**(정제·배열화)이지 916 KB가 아니다
- **자릿수를 바꾸는 건 본문을 덜어내는 것뿐** — 신약만 전송 **283 KB**, 장 단위로 필요한 장만 받으면 **중앙값 1.5 KB / 최악 5.1 KB**(총 배포량은 +66%로 늘지만 그건 사용자가 내는 값이 아니다). **판단은 05로 넘긴다**

**절 길이 분포**(07의 직접 입력) — 최소 4 · 최대 287 · 중앙값 54 · p90 92 · p99 131. 상자 100자면 넘치는 절 **1,990개(6.40%)**, 120자면 **631개(2.03%)**, 140자면 **158개(0.51%)**, **300자면 0개**. 장당 절 수 중앙값 24(= 한 벌 24~26장). **최장 3개가 전부 병합절이다** — 맵의 *"이미 있던 경계는 절이다"* 가 여기서만 성립하지 않는다. 넘침 규칙을 만들기 전에 **병합절 11개를 원래 절로 되돌릴 수 있는지**부터 볼 것. 4위부터는 진짜 한 절이고 상한 194자

**남은 위험과 그걸 좁히는 표본 설계** — 남은 질문은 *"파일이 담은 그 판본이 이 교회가 쓰는 판본인가"* 하나이고, **종이 성경이 있어야 답한다.** 30~40절 4층 설계를 §8에 남겼다. 핵심은 어구 차이 205건에서 뽑은 **15절**이고, 12절 이상이 파일 쪽이면 위험 해소, 공회 쪽이면 **데이터를 갈아야 하고 05의 입력이 바뀐다.**
