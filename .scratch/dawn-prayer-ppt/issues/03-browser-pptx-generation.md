# 브라우저에서 편집 가능한 .pptx를 만드는 법

Type: research
Status: resolved

## Question

서버 없이 브라우저 안에서 `.pptx`를 만드는 길들을 조사하고, **각 길이 무엇을 요구하고 무엇을 포기하게 하는지** 확정한다.

이 앱이 처음 지는 무게다. 자막 추출기의 출력은 컬럼 없는 순수 `.txt`였고 조판은 나비CG 몫이었다. 여기선 조판이 파일 안에 들어간다.

**포기할 수 없는 제약 둘** — 차팅에서 확정됐다:

1. **서버가 없다.** `output: 'export'`, Cloudflare Pages. 전부 클라이언트에서
2. **파워포인트에서 열어 고칠 수 있어야 한다.** 슬라이드를 이미지로 굽는 길은 이 조건 하나로 탈락한다. 진짜 텍스트 상자여야 한다

### 조사할 것 — 갈래들

**(가) 라이브러리로 백지에서 생성** — `pptxgenjs` 등. 브라우저 지원 범위, 번들 크기, 한글 폰트 처리, 텍스트 상자 속성(자동 맞춤·줄간격·자간) 제어 가능 범위, 배경 이미지 삽입 방법.

**(나) 물려받은 파일을 템플릿으로 갈아끼우기** — 기존 `.pptx`를 zip으로 열어 인트로·아웃트로 슬라이드는 **바이트째 남기고** 가운데 절 슬라이드만 생성해 끼운다. 차팅에서 유력하다고 본 길이다(디자인을 다시 저작할 필요가 사라진다). 확인할 것:

- 슬라이드 추가·삭제 시 손대야 하는 파일 전부 — `ppt/slides/`, `ppt/_rels/`, `presentation.xml`, `[Content_Types].xml`, `docProps/app.xml` 등. **하나라도 어긋나면 파워포인트가 "복구 필요" 대화상자를 띄운다**
- 절 슬라이드의 원본이 될 슬라이드를 **복제**하는 접근이 가능한가 (레이아웃·마스터 참조가 따라오는가)
- 템플릿 파일을 앱이 **번들에 갖고 있어야 하나, 사용자가 올려야 하나.** 후자면 *"방송부 여럿이 돌아가며"* 에 걸린다 — 당번마다 템플릿 파일을 챙겨야 한다
- 라이브러리가 이 작업을 지원하는가, 아니면 직접 XML을 다뤄야 하는가

**(다) 직접 OOXML 작성** — `fflate`가 **이미 의존성에 있다**(zip). 최소한의 `.pptx`가 요구하는 파일 목록과 각각의 필수 최소 내용, 그 분량이 대략 몇 줄인지.

### 조사할 것 — 갈래를 가르는 사실들

- **한글 폰트.** 생성한 파일을 예배당 PC에서 열었을 때 폰트가 유지되려면 무엇이 필요한가. 폰트 임베딩이 `.pptx`에서 가능한가, 그 값(파일 크기·라이선스)은. 아니면 **PC에 이미 깔린 폰트를 참조하는 것으로 충분한가**
- **자동 맞춤(autofit).** `normAutofit`으로 "넘치면 자동 축소"를 켜면 우리가 폰트 메트릭을 재지 않아도 되는가. 켰을 때 파워포인트가 실제로 어떻게 동작하는지, 그리고 **파일을 열기 전에는 축소 결과를 알 수 없다는 점**이 문제가 되는지. 이건 `절이 넘칠 때 어떻게 쪼개나`의 판을 통째로 바꿀 수 있는 사실이다
- **길이 판정을 하려면** 브라우저에서 텍스트 폭을 재는 수단(Canvas `measureText`, `document.fonts`)이 파워포인트의 실제 렌더와 얼마나 일치하는가. 오차의 크기
- 각 갈래의 **번들 증가분**을 실측할 것. 이 저장소는 방문자가 내려받는 바이트를 수십 KB 단위로 재는 저장소다
- 생성 결과를 **실제 파워포인트(그리고 한컴오피스·LibreOffice·Google Slides)에서 열어** 깨지지 않는지 확인할 방법

### 산출물

`.scratch/dawn-prayer-ppt/research/pptx-generation.md`. 조사는 `docs/dawn-prayer-ppt-03-pptx-generation` 브랜치에서 진행 중이다(2026-08-07 착수). 가능하면 **실제로 열리는 최소 `.pptx`를 만들어 보고** 그 결과를 첨부할 것 — 이 저장소는 조사가 실물을 만들어 확인하는 관례가 있다. 갈래 중 무엇을 고를지는 결정하지 말고 `생성 방식 — 템플릿이냐 백지냐`에 넘긴다.

## Answer

**세 갈래 전부 성립한다. 서버 없이 되고, 셋 다 진짜 텍스트 상자를 만든다.** 갈리는 것은 **디자인을 어디서 가져오느냐**뿐이다. 조사가 `fflate`만으로 **실제로 열리는 최소 `.pptx`(13파트 / XML 9,446 B / zip 5,843 B)를 만들어** 확인했고, ISO/IEC 29500-4:2016 XSD 13/13 통과 + Apple `Office.qlgenerator` 렌더 + python-pptx가 `MSO_SHAPE_TYPE.TEXT_BOX`로 읽어냄까지 봤다.

| 갈래 | 번들 증가분 (gzip, esbuild 실측) | 자작량 | 지는 위험 |
|---|---:|---|---|
| **(가) pptxgenjs 4.0.1 백지 생성** | **126,467 B** | 거의 0 | jszip을 통째로 끌고 온다 |
| **(나) 템플릿 수술 (`fflate`)** | **7,339 B** | ≈110줄 | 템플릿 실물이 앱 안에 있어야 한다 |
| **(다) 손수 OOXML (`fflate`)** | **6,764 B** | ≈140줄, XML 9.4 KB | 마스터·배경을 다시 저작해야 한다 |

**번들 차이는 갈래가 아니라 zip 라이브러리 하나에서 나온다.** `pptxgenjs@4.0.1`이 `jszip@^3.10.1`을 dependencies에 두고 ESM 빌드 첫 줄에서 import한다 → **저장소에 이미 있는 `fflate` 위에 두 번째 zip 구현이 얹혀 +119,703 B(gzip).** 직전 커밋이 깎아낸 87 KB의 **1.42배**다. 다만 라우트별 코드 스플리팅이 되므로 **비교 대상은 사이트 총량이 아니라 "이 페이지 하나를 여는 값"** 이다.

**`pptx-automizer`(유일한 템플릿 병합 라이브러리)는 브라우저에서 못 쓴다** — `require("fs")` 7곳, `extract-zip` 의존, `browser` 필드 없음. **(나)를 고르면 라이브러리 없이 자작이다.**

### 뒤집은 것 넷

1. **맵의 "둘째 위험"(조판을 우리가 책임진다)이 크게 줄었다.** 한글 본문 폰트는 **11,172개 음절 전부가 같은 advance 폭**을 갖는다(맑은 고딕에서 정확히 `1.0 em`, 본문 폰트 9종 전부 확인). **Canvas `measureText`도 `document.fonts`도 필요 없다** — 폰트당 상수 하나 + 공백·문장부호 폭 몇 개면 줄바꿈이 정확히 떨어진다. 실물 렌더로 검증: 예측 21자, 실측 21자
2. **`normAutofit`은 대책이 아니다.** `fontScale`은 **생산자가 계산해 파일에 박는 값**이다(ISO/IEC 29500-1 원문). Apple 렌더러는 `noAutofit`/`normAutofit`/`fontScale=25%`/`spAutoFit` 넷의 렌더가 **SHA-256까지 동일**하다. pptxgenjs의 `fit:'shrink'`는 빈 `<a:normAutofit/>`만 내보낸다(`fontScale` 줄이 소스에 주석 처리돼 있고 저자 노트가 붙어 있다)
3. **폰트 임베딩은 불필요하고, 하려 해도 브라우저에선 사실상 못 한다.** 맑은 고딕은 Windows Vista~11 전부 + Office(Mac 포함)에 들어 있다. 반대로 임베딩은 EOT/MicroType Express를 요구하고([MS-OE376]) 원본 폰트가 13,457,192 B다. **단 (나)는 예외** — 템플릿에 임베딩된 폰트 파트가 **바이트째 보존**되는 것을 확인했다
4. **템플릿 수술이 손대는 패키지 파일은 3개다** — `[Content_Types].xml` · `ppt/_rels/presentation.xml.rels` · `ppt/presentation.xml`. 티켓이 나열한 `docProps/app.xml`은 **안 건드려도 된다**(슬라이드 수가 `0`이고 종횡비가 거짓말을 해도 열린다). 42개 파트 — 테마·마스터·레이아웃 11개·배경 이미지 둘·인트로/아웃트로 — 가 **바이트째 남는다**

### 맵이 몰랐던 것

**이 개발자는 이미 pptxgenjs로 교회용 PPT를 만든 전례가 있다** — `~/dev/projects/praise-pdf-to-ppt/`의 `build-pptx.mjs`가 찬양 악보 슬라이드를 굽고 `output/`에 6곡이 떨어져 있다(2026-07-08). **단 Node 스크립트다**(브라우저가 아니다). 조사가 그 산출물로 pptxgenjs의 스키마 위반(`notesMasterIdLst`가 `sldIdLst` 뒤)을 찾아냈다 — 파워포인트는 그래도 받아준다. **"백지 생성"은 이 저장소에서 미지의 길이 아니다.**

### 못 한 것 — 그래서 티켓 10이 생겼다

**파워포인트 본체로 못 열어봤다.** PowerPoint 16.111.3·Keynote·한컴이 다 깔려 있지만 macOS TCC가 Apple Event(`-10003`)와 화면 기록을 둘 다 막는다(맵이 `~/Downloads`에서 만난 것과 같은 벽). 정직한 주장은 *"독립 OOXML 구현이 렌더했고 ISO 스키마를 통과했다"* 이지 *"열린다"* 가 아니다. 그 밖에 미확정: 파워포인트가 **열 때** `fontScale`을 재계산하는가, 파워포인트의 줄높이 상수(Apple 렌더러는 폰트 크기의 1.224배로 측정됐고 폰트 자체 메트릭 어느 것과도 안 맞는다), LibreOffice·Google Slides·한컴 거동.
