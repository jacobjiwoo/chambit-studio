# 절이 넘칠 때 어떻게 쪼개나

Type: grilling
Status: open
Blocked by: 01

## Question

한 절이 텍스트 상자에 다 안 들어갈 때 **무엇을 하는가.**

차팅에서 담당자의 답은 **"그런 절이 없었다 / 생각 안 해봤다"** 였다. 즉 이건 결정이기 전에 **아직 안 세어진 것**이다.

### 먼저 센다 — 규칙을 발명하기 전에

이 티켓의 첫 절반은 결정이 아니라 산수다.

- `새벽기도 PPT 실물 확보와 조판 실측`이 **텍스트 상자 크기와 폰트 크기**를 준다
- `bible.json 검증`이 **절 길이 분포**를 준다
- 둘을 곱하면 **넘치는 절이 전체 몇 개인가**가 정확한 숫자로 떨어진다

**그리고 곱하기가 조사 03 덕에 쉬워졌다.** 티켓을 열 때는 *"넘칠지 판정하려면 폰트 메트릭을 재야 한다"* 고 봤는데 **그게 필요 없다** — 한글 본문 폰트는 **11,172개 음절 전부가 같은 advance 폭**을 갖는다(맑은 고딕에서 정확히 `1.0 em`, 본문 폰트 9종 전부). 폰트당 상수 하나 + 공백·문장부호 폭 몇 개면 줄바꿈 위치가 떨어지고, 실물 렌더로 예측 21자 / 실측 21자가 확인됐다. **Canvas `measureText`도 `document.fonts`도 안 쓴다.** 남은 미확정은 **줄높이 상수** 하나다(Apple 렌더러는 폰트 크기의 1.224배였는데 폰트 자체 메트릭 어느 것과도 안 맞았다 — 파워포인트가 같은 값인지 미확인).

세고 나서야 이 티켓의 크기를 안다. **0개에 가까우면 규칙이 필요 없고**(경고만 띄우고 사람에게 넘긴다), 수백 개면 규칙이 도구의 중심이 된다. 세기 전에 규칙을 짓지 말 것.

### 절반은 이미 세어졌다 (02, resolved)

절 길이 분포 — **최소 4 · 최대 287 · 중앙값 54 · p90 92 · p99 131.** 장당 절 수 중앙값 24(= 한 벌 24~26장).

| 상자에 들어가는 글자 수 | 넘치는 절 |
|---:|---:|
| 100자 | **1,990개 (6.40%)** |
| 120자 | **631개 (2.03%)** |
| 140자 | **158개 (0.51%)** |
| 300자 | **0개** |

**남은 절반은 `새벽기도 PPT 실물 확보와 조판 실측`이다** — 상자 크기와 폰트 크기가 나오면 위 표에서 이 티켓의 크기가 바로 읽힌다. 조사 03이 폰트 상수(한글 음절 전부가 같은 폭)를 확정했으므로 **글자 수 → 줄 수 계산은 곱하기 한 번**이다.

### 그리고 맵의 전제 하나가 여기서만 깨진다

**최장 3개(`렘32:3-5`·`렘33:10-11`·`신30:9-10`)가 전부 병합절이다** — 개역개정이 정본에서 여러 절을 한 항목으로 찍은 것이고 **11개 있다.** 맵이 *"이미 있던 경계는 절이다"* 라고 적었는데 **여기서만 성립하지 않는다**(경계가 애초에 뭉개진 채로 왔다). **넘침 규칙을 발명하기 전에 병합절 11개를 원래 절로 되돌릴 수 있는지부터 볼 것** — 되돌려지면 최장이 **287자에서 194자로 떨어지고** 넘침 문제 자체가 작아진다.

### 갈래들 (센 뒤에 고른다)

- **여러 장으로 쪼갠다** — 어디서 끊나. 문장 부호? 어절? 길이 균등?
- **글자 크기를 줄인다** — 한 절은 무조건 한 장. ~~`03` 조사가 `normAutofit`이 이걸 공짜로 해주는지 확인해 온다~~ → **공짜가 아니다.** `fontScale`은 **생산자가 계산해 파일에 박는 값**이고(ISO/IEC 29500-1 원문), Apple 렌더러는 `normAutofit`을 통째로 무시한다(네 경우의 렌더가 SHA-256까지 동일). 즉 이 갈래를 고르면 **축소 비율을 우리가 계산해야** 하며, 그건 넘침 판정을 하는 것과 같은 일이다. ~~다만 파워포인트 본체는 다르게 굴 수 있다~~ → **확인됐다. 파워포인트도 안 줄인다**(`생성물이 파워포인트에서 실제로 열리는가`, `af-bare.pptx`). **공짜 갈래는 없다.**
- **여러 절을 한 장에 몰기도 한다** — 짧은 절은 묶고 긴 절은 가른다. 그러면 "절 단위"라는 전제 자체가 바뀐다
- **아무것도 안 한다** — 넘치는 절을 화면에 표시하고 사람이 파워포인트에서 손본다. 산출물이 어차피 **편집 가능해야 한다**는 것이 이미 확정됐으므로 이 갈래가 생각보다 강할 수 있다

### 미리 옮겨 둔 교훈

자막 추출기 맵에서 최대 난제였던 "쪼개는 단위"는 **병합 규칙을 발명할 문제가 아니라 경계를 어디에 그을지의 문제**였고, 답은 원고에 **이미 있던 경계(문단)** 였다. 여기서 이미 있는 경계는 **절**이다. 절 경계를 넘어서는 규칙을 만들기 전에 그것부터 의심할 것.

### 입력

- `새벽기도 PPT 실물 확보와 조판 실측` — 상자 크기, 폰트 크기, **autofit 설정이 이미 켜져 있는지**
- `bible.json 검증과 개역개정 데이터의 실제 모습` — 절 길이 분포, 가장 긴 절 상위 20개
