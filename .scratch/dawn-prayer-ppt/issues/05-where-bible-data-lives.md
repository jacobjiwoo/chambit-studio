# 성경 데이터가 어디에 사는가 — 5.1 MB와 정적 배포

Type: grilling
Status: open
Blocked by: 02, 11

## Question

개역개정 본문 데이터를 **어디에 두고 언제 불러올 것인가.**

이 맵의 **최대 위험**이 앉은 자리다. 서버가 없으므로 데이터는 번들에 실리거나, 조각내어 요청되거나, 사용자 기기에 들어가야 한다. 셋 다 값이 다르다.

### 판이 이렇게 생겼다

- 원본 **5,119,699 바이트(5.1 MB)**
- 사이트는 **서버 없는 정적 배포**(Cloudflare Pages, `output: 'export'`)
- 저장소의 **직전 커밋이 색인을 292 KB → 205 KB로 깎은 커밋**이다. 5.1 MB는 그 24배다. 이 저장소의 무게 기준선이 얼마나 엄격한지가 그 커밋에 적혀 있다
- 그 커밋이 남긴 교훈 하나 — *"진짜 자는 **글자당 바이트**다"*. 여기서도 총 바이트만 보고 판단하면 안 된다

### 갈라야 할 것

- **한 번에 다 싣나, 필요한 것만 불러오나.** 후자면 책·장 단위로 쪼개 정적 파일로 올리고 요청 시 가져온다. 그러면 **새벽 5시에 네트워크가 필요해진다** — `.pptx` 파일 방식을 고른 이유가 *"인터넷·브라우저에 의존하면 되돌릴 시간이 없다"* 였는데, 데이터를 쪼개면 그 의존이 다시 들어온다. 이 모순을 정면으로 다룰 것
- **사용자 기기에 캐시하나.** 브라우저 저장소에 한 번 넣어두는 길. **차팅에서 이미 약점이 드러났다** — *"방송부 여럿이 돌아가며"* 라 당번마다·기기마다 첫 실행이 발생하고, 하필 그걸 새벽 5시에 처음 겪는 사람이 생긴다. 이 약점을 감수할 만한 이득이 있는지, 아니면 첫 방문 때 조용히 채우는 식으로 우회되는지
- **얼마나 줄일 수 있나.** `bible.json 검증`이 수단별 절감치를 실측해 온다. **전송 크기(brotli 후)와 원본 크기를 구분해서** 판단할 것 — 정적 호스팅이 전송 시 압축한다
- **저장소에 커밋하나.** `.gitignore`에 `*.json` 규칙이 없다. 5.1 MB가 git 히스토리에 들어가는 것과 빌드 때 받아오는 것은 다른 문제다
- **무게의 상한을 정할 것인가.** 나비CG 문서 맵은 색인에 게이트를 세웠다(`expect()`가 빌드를 막는다). 성경 데이터에도 같은 장치가 필요한지, 필요하다면 무엇을 재는 게이트인지

### 조사가 판을 좁혀 놓았다 (02, resolved)

**질문이 하나로 줄었다.** *"어떻게 압축하나"* 는 닫혔다 — **5.1 MB의 88.5%가 본문 글자**라 구조를 0으로 만들어도 4.56 MB이고, 영리한 수단 셋(EUC-KR·14비트 팩킹·zstd)이 전부 실패했다(팩킹은 **+25.5%로 오히려 커진다**). 키 축약 0.1%. **배열화만이 유일한 구조적 이득(전송 −8.7%)이고, 그 뒤로는 본문을 덜어내는 것 외에 자릿수를 바꾸는 길이 없다.**

**Cloudflare 실측이 기준선을 바꿨다** — `chambitstudio.com`은 br q11이 아니라 **대략 q4**로 압축한다(이 사이트에선 gzip이 brotli보다 작게 나왔다).

| | 전송 크기 (실측) |
|---|---:|
| 원본 그대로 | **1,270 KB** |
| 정제 + 배열화 | **1,153 KB** |
| 신약만 | **283 KB** |
| 장 하나 (중앙값 / 최악) | **1.5 KB / 5.1 KB** |

**남은 질문은 단 하나 — 전부 내려보낼 것인가.** 장 단위로 쪼개면 사용자가 내는 값이 1.5 KB로 떨어지지만 **새벽 5시에 네트워크가 필요해진다**(총 배포량도 +66%). `.pptx` 파일 방식을 고른 이유가 *"인터넷·브라우저에 의존하면 되돌릴 시간이 없다"* 였다는 점과 정면으로 부딪히는 자리다.

**빌드 게이트는 된다 — 그리고 나비CG 색인과 결정적으로 다르다.** 성경은 늘지 않으므로 **절대 크기를 그냥 고정해도 된다**(색인은 콘텐츠가 늘면 같이 느니까 글자당 바이트로 재야 했다). 구조 게이트는 네트워크 없이 즉시, 본문 게이트는 SHA-256 + 결함 허용 목록으로.

### 이 티켓이 같이 처리할 것 — 데이터 정제

조사가 **결함 88건을 전량 열거**했다: `?` 16(완성형 통과 흔적, 파일에 완성형 밖 음절이 0개라 **이게 손실의 전부임이 증명됐다**), 난하주 마커 15절, 마침표 41(개역개정에 마침표는 없다), NUL 30자 3절, 대괄호 짝 어긋남 9절, 깨진 키 `요18:이` 1건(**요 18:38이 지금 반쪽만 나온다**). 건드리면 안 되는 정본 표기도 갈라 뒀다(`(없음)` 13, `(셀라)`, 병합절 11).

그리고 **선행 공백 2,414개는 버릴 쓰레기가 아니라 소제목 경계다**(오탐 0/28,660). 화면에는 trim해야 하지만 **버리기 전에 플래그로 떠 두면 공짜로 얻는 구조 정보**다 — 실을 데이터 모양을 정할 때 같이 결정할 것.

**저작권은 이 티켓의 판단 근거가 아니다.** 맵이 Out of scope로 명시했다. 차팅 세션에서 *"성경을 사용자 브라우저에 살게 한다"* 가 처음에는 저작권 회피책으로 제안됐으나, 저작권이 논외가 되면서 그 갈래는 **순수하게 무게 문제로만 평가된다.** 법적 논거를 이 티켓에 다시 들여오지 말 것.
