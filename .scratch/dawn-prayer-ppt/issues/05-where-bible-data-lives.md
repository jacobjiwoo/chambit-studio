> **11이 이 티켓의 할 일을 하나 지웠다 (2026-08-10).** `bible.json`이 **대한성서공회 본문으로 이미 교체돼 있다** — 종이 성경이 4판으로 확인돼 유포본을 버렸다. 그러면서 **결함 88건이 같이 사라졌다**(아래 *데이터 정제* 절은 이제 대부분 지난 이야기다). 무게 숫자는 1% 안쪽으로 그대로이므로 **저울은 안 흔들린다.** 남은 질문은 여전히 하나 — **전부 내려보낼 것인가.**

## Question

이 맵의 **최대 위험**이 앉은 자리다. 서버가 없으므로 데이터는 번들에 실리거나, 조각내어 요청되거나, 사용자 기기에 들어가야 한다. 셋 다 값이 다르다.

### 판이 이렇게 생겼다

- 원본 **5,119,699 바이트(5.1 MB)**
- 사이트는 **서버 없는 정적 배포**(Cloudflare Pages, `output: 'export'`)

### 갈라야 할 것

- **한 번에 다 싣나, 필요한 것만 불러오나.** 후자면 책·장 단위로 쪼개 정적 파일로 올리고 요청 시 가져온다. 그러면 **새벽 5시에 네트워크가 필요해진다** — `.pptx` 파일 방식을 고른 이유가 *"인터넷·브라우저에 의존하면 되돌릴 시간이 없다"* 였는데, 데이터를 쪼개면 그 의존이 다시 들어온다. 이 모순을 정면으로 다룰 것
- **사용자 기기에 캐시하나.** 브라우저 저장소에 한 번 넣어두는 길. **차팅에서 이미 약점이 드러났다** — *"방송부 여럿이 돌아가며"* 라 당번마다·기기마다 첫 실행이 발생하고, 하필 그걸 새벽 5시에 처음 겪는 사람이 생긴다. 이 약점을 감수할 만한 이득이 있는지, 아니면 첫 방문 때 조용히 채우는 식으로 우회되는지
- **얼마나 줄일 수 있나.** `bible.json 검증`이 수단별 절감치를 실측해 온다. **전송 크기(brotli 후)와 원본 크기를 구분해서** 판단할 것 — 정적 호스팅이 전송 시 압축한다
- **저장소에 커밋하나.** `.gitignore`에 `*.json` 규칙이 없다. 5.1 MB가 git 히스토리에 들어가는 것과 빌드 때 받아오는 것은 다른 문제다
- **무게의 상한을 정할 것인가.** 나비CG 문서 맵은 색인에 게이트를 세웠다(`expect()`가 빌드를 막는다). 성경 데이터에도 같은 장치가 필요한지, 필요하다면 무엇을 재는 게이트인지

### 판이 잘못 그려져 있었다

이 티켓은 스스로를 *"맵의 최대 위험"* 이라 적었고, 남은 질문을 **"전부 내려보낼 것인가"** 하나로 좁혀 놓았다. 그 질문이 무거웠던 이유는 단 하나 — 쪼개면 *"새벽 5시에 네트워크가 필요해진다"* 는 것이었다.

**그 장면은 존재하지 않는다. PPT는 전날 밤 집에서 만든다.** 맵이 `.pptx` 파일 방식을 고른 근거였던 *"미리 만들어 옮긴다"* 의 **"미리"가 전날 밤**이라는 것이 이 세션에서 확인됐다. 그리고 **본문이 전날 밤보다 늦게 오는 날은 없다.** 그래서 교회 회선도, 되돌릴 수 없는 시각도, 이 티켓의 판단 근거가 아니다.

**티켓의 문장 하나는 엄밀히 틀렸다** — *"쪼개면 네트워크 의존이 다시 들어온다"*. 이 앱은 웹페이지이므로 **네트워크 의존은 이미 있다**(페이지를 여는 데 필요하다). 쪼개기가 바꾸는 것은 의존의 **크기와 실패 시점**뿐이고, 실패 시점이 되돌릴 수 있는 시각이면 그 차이는 값을 못 한다.

**남은 것은 무게뿐이고, 무게는 아무도 안 아프게 한다.** 전송 1,255 KB를 내는 사람은 전날 밤 여유 있는 회선 앞에 앉은 한 사람이다. 쪼개기(책 단위 11 KB)는 실측상 배포 총량을 +4.5%밖에 안 늘리는 싼 수단이었지만, **살 이유가 없어졌으므로 안 산다.**

### 실은 모양 — 책 중첩 배열

측정(현재 `bible.json`, gzip -9):

| 모양 | raw | 전송 |
|---|---:|---:|
| 지금 파일 그대로 | 5,057 KB | 1,363 KB |
| 가. 평면 dict `{"창1:1":"…"}` | 4,964 KB | 1,358 KB |
| 나. 장 배열 `{"창1":[…]}` | 4,637 KB | 1,257 KB |
| **다. 책 중첩 `{"창":[[…],[…]]}`** | **4,627 KB** | **1,252 KB** |
| 라. 키까지 전부 배열 | 4,627 KB | 1,252 KB |

**(다)를 고른다.** −106 KB는 이 저장소가 커밋 하나를 통째로 써서 깎은 87 KB보다 크다 — 자기가 세운 기준을 자기가 안 지키면 그 기준이 죽는다. **책 약칭 키는 남긴다**(라 ≈ 다, gzip 후 0.5 KB 차이). 읽을 수 있는 데이터가 공짜면 남긴다.

**배열화가 밟는 것 — 병합절 11개.** 평면 dict는 키가 절 번호를 들고 있어 저절로 풀리지만, 배열은 `arr[i]`의 `i+1`이 절 번호라는 가정을 만든다. 병합절 뒤로는 전부 한 칸씩 밀린다(신명기 6장은 25절인데 배열은 24칸, `arr[18]`은 19절이 아니라 20절이다). 그래서 **예외표를 데이터에 같이 싣는다** — gzip 후 **166 바이트**다.

```
신6:18-19  신15:4-5  신30:9-10  대상16:12-13  시92:1-3  시105:5-6
렘32:3-5  렘33:10-11  겔24:4-5  행15:25-26  롬9:1-2
```

**선행 공백은 trim하고 소제목 플래그로 명시한다.** 명시하는 값이 **+2.9 KB**(1,251,063 + 4,092 = 1,255,155 vs 유지 시 1,252,219). 그 3 KB로 사는 것은 **보이지 않는 문자에 의미가 실려 있는 상태를 없애는 것**이다. 텍스트 파이프라인은 어디서든 기본으로 trim한다 — 조판에서 한 번, PPTX XML에 넣으며 한 번, 미리보기에서 한 번. 그중 아무 데서나 한 번 trim되면 2,424개의 구조 정보가 **에러 없이 조용히** 사라지고, 사라져도 아무도 모른다.

### 놓는 자리 — `public/`, 해시 이름, `import`가 아니라 `fetch`

```
public/bible.<해시8자>.json               ← 데이터
public/_headers                            ← Cache-Control: public, max-age=31536000, immutable
app/dawn-prayer-ppt/bible-manifest.ts      ← export const BIBLE_URL = "/bible.<해시8자>.json"
```

**이름에 해시를 박는 것은 캐시를 위해서가 아니라 사고를 막기 위해서다.** `/bible.json`에 1년 캐시를 걸어 놓고 나중에 내용을 갈면 이미 받아간 브라우저가 **1년 동안 옛 성경을 쓴다** — 화면과 회중이 든 책이 다르게 읽히는, `파일의 판본이 우리 교회 성경과 같은가`가 방금 닫은 바로 그 위험이다. 이름이 내용을 따라가면 그 사고가 **구조적으로 불가능**해지고, `immutable`도 거짓말이 아니라 사실이 된다.

부수 이득 하나 — **두 번째 방문부터는 네트워크를 아예 안 탄다**(`must-revalidate`와 달리 `immutable`은 재검증 시도조차 안 한다). "전날 밤보다 늦게 오는 날은 없다"가 뒤집히는 날이 와도 같은 기기라면 다운로드가 다시 일어나지 않는다. 산 적 없는 보험이 딸려 온 셈이다.

**`import`하지 않고 `fetch`한다.** import하면 4.6 MB가 라우트 청크에 녹아 (1) 코드 한 줄만 고쳐도 성경이 새 URL로 다시 내려가고, (2) JSON.parse보다 느린 JS 파서를 타고, (3) 빌드 산출물에서 성경과 코드가 구분되지 않는다.

**매니페스트는 손으로 안 적는다.** 재생성 스크립트가 데이터와 `bible-manifest.ts`를 같이 뱉고, 게이트가 둘이 서로를 가리키는지 확인한다.

### 저장소가 들고 있는 것 — 산출물과 만드는 법, 재료는 아니다

**커밋한다:** 배포 산출물 + `tools/`의 재생산 스크립트.
**커밋 안 한다:** 캐시 33 MB, 중간 형태 `bible.json` 5.1 MB. (`.gitignore` 갱신 완료)

git은 blob을 zlib으로 눌러 저장하므로 4.6 MB JSON이 실제로 늘리는 것은 **약 1.25 MB**다(`.git` 2.3 MB → 3.6 MB). 그리고 **`11`이 판본을 확정했으므로 이 파일은 다시 안 바뀐다** — blob 하나가 한 번 들어가고 끝이지 커밋마다 쌓이지 않는다.

*"205 KB를 깎느라 커밋 하나를 쓴 저장소"* 와 충돌해 보이지만 **자가 다르다.** 그 205 KB는 **모든 방문자가 매번 내는 값**이었고, 이 1.25 MB는 **개발자가 clone 한 번 할 때 내는 값**이라 방문자는 한 푼도 안 낸다. 색인 다이어트 커밋이 남긴 교훈이 *"총 바이트 말고 진짜 자를 봐라"* 였으니, 여기서 진짜 자는 **누가·언제·얼마나 자주 내느냐**다.

**빌드 때 받아오는 안은 기각한다** — 배포가 공회 서버에 매달린다. 그 서버가 느리거나 죽은 날 `chambitstudio.com` 배포가 죽고, 커밋마다 남의 서버에 1,189 요청을 날리고, 빌드에 6분이 붙는다. 저작권은 맵이 Out of scope로 뒀으므로 *"커밋 안 하면 안전"* 이라는 논거는 여기서 쓸 수 없다.

### 게이트 — 문지기 하나, 진단 여럿

막을 사고가 성격이 다른 둘이다.

**하나, 파일이 조용히 바뀐다.** 4.6 MB를 손으로 고칠 사람은 없지만 prettier가 재포맷하거나 에디터가 개행을 바꾸는 일은 일어난다. → **SHA-256 고정.** 성경은 다시 안 바뀌므로 해시를 못 박는 것이 정직하다.

**둘, 데이터와 앱의 전제가 어긋난다.** 스크립트를 고쳐 재생성했을 때 예외표가 실제 위치와 안 맞거나 플래그가 범위 밖을 가리킬 수 있다. **해시는 이걸 못 잡는다** — "바뀌었다"만 말하고 "새 파일이 옳으냐"는 안 말하며, 재생성은 해시가 바뀌는 게 정상이라 그 순간 문지기가 통째로 무력해진다. → **구조 불변식**이 해시를 갈아끼운 직후를 검사한다:

```
66권 · 1,189장 · 31,088항목 · 정경 순
병합절 예외표 11개가 가리키는 자리가 실제로 존재한다
소제목 플래그 2,424개가 전부 유효 범위 안이다
앞뒤 공백 0 · 빈 값 0
public/에 성경 파일이 정확히 하나
데이터 파일명과 bible-manifest.ts가 서로를 가리킨다
```

**크기 상한은 따로 두지 않는다** — SHA-256이 이미 함의하고, 숫자를 둘 이상 관리하면 둘이 어긋난다. (티켓이 *"절대 크기를 고정해도 된다"* 고 적은 것은 맞지만, 해시가 더 강한 같은 약속이다.)

**`public/`에 성경 파일이 정확히 하나**는 해시 이름을 고른 대가로 새로 생긴 사고를 막는다 — 재생성하면 **새 이름으로 새 파일이 생기고 옛 파일이 안 지워져** 저장소에 4.6 MB가 조용히 둘이 된다.

### 이 세션이 실제로 한 일 — 재생산 수단을 건져냈다

**성경 데이터를 만드는 법 전체가 지워질 디렉터리에 있었다.** `~/.claude/jobs/0bd0c26c/tmp/`는 job이 삭제되면 같이 사라지는데, 거기에 `fetchall.py`·`rebuild2.py`·캐시 1,189장이 전부 있었다. 파일만 남고 **그걸 어떻게 만들었는지가 사라질** 참이었다.

건져서 [`tools/`](../tools/)에 넣었다:

```
tools/fetch-bskorea.py   공회 1,189장 → cache/       (커밋함)
tools/parse-bskorea.py   cache/ → ../bible.json      (커밋함)
tools/canon.json         66권 약칭·정식이름·코드·장수 (커밋함, 4.8 KB)
tools/README.md          출처와 주의사항             (커밋함)
tools/cache/             33 MB                       (gitignore)
```

**옮기면서 고친 것 셋:**

1. **76 KB짜리 `list.js` 의존을 4.8 KB `canon.json`으로 대체.** 공회 JS를 통째로 커밋하는 대신 필요한 것만 뽑았다 — 66권의 약칭·**정식 이름**(`창세기`)·공회 코드·장 수. 합이 1,189장인 것을 assert한다. **부수 이득: `본문 범위 입력 문법과 오입력 처리`가 정한 "고르는 목록"이 쓸 표가 그대로 여기 있다** — 앱은 `창`이 아니라 `창세기`를 보여줘야 하는데 `bible.json`에는 약칭밖에 없었다.
2. **캐시 디렉터리를 훑는 대신 정경이 있어야 한다고 말하는 파일만 읽는다.** 옛 시도가 남긴 잔재(요나의 `jon_*` — 정본 코드는 `jnh`다)에 면역이고, **빠진 장이 있으면 조용히 넘어가는 대신 걸린다.**
3. 하드코딩된 절대경로를 스크립트 기준 상대경로로.

**건진 것이 작동하는지 확인했다** — 건져낸 스크립트로 재생성한 결과가 기존 파일과 **바이트째 동일**하다(`cmp` 통과). 항목 31,088 · 소제목 경계 2,424 · 결함 0.

```
SHA-256  48b859ae50b4b68cdd6af781100586f39abf4ac5e2d7f146bbd9f556f3368bc5
크기     5,057,258 B  (중간 형태. 배포본은 이걸 변환한 것이다)
```

### 딸려 나온 것 — `06`의 규칙 하나가 지금 틀렸다

`본문 범위 입력 문법과 오입력 처리`가 *"절 번호가 숫자인 키만 목록에 올린다"* 고 정했다. 깨진 키 `요18:이`를 막으려던 규칙인데, **`11`이 데이터를 갈면서 그 대상이 사라졌다.** 규칙만 남아서, 그대로 쓰면 **정본에 멀쩡히 있는 병합절 11개**(신6:18-19, 롬9:1-2 …)를 목록에서 떨어뜨린다. 06에 정정을 붙였다.

### 안 한 것

배포본을 실제로 만드는 변환(책 중첩 + trim + 플래그 + 예외표), `_headers`, 매니페스트, 게이트 코드 — 전부 **구현이라 `/to-spec` → `/implement`로 넘긴다.** 이 세션이 건져낸 122줄은 목적지를 짓는 일이 아니라 **이미 있는 것을 잃지 않는 일**이라 여기서 했다.
